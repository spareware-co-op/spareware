# 21. Determinism

*Part of the [Spare Kit geometry kernel architecture](../ARCHITECTURE.md). Decided in [G01](../../../kit/notes/G01-geometry-kernel.md); section numbers match across the set.*

Evidence: [05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 7 and [03](../../../kit/notes/G01-evidence/03-rust-kernels-crates.md) section 5.

**What Rust already guarantees.** Addition, subtraction, multiplication, division, remainder, square root, fused multiply-add (only when written as `mul_add`), casts and comparisons follow IEEE 754 exactly on every supported target, and Rust never fuses a multiply and an add on its own (RFC 3514). Kernel crates are `no_std`, and `core` has no `f64::mul_add` or `sqrt`, so kernel code writes a fused multiply-add as `geom_num::math::fma` and a square root as `math::sqrt`. Both are `libm`'s, correctly rounded as IEEE 754 requires, whether `libm` uses the processor's instruction or its own routine (6.4).

**What the kernel must police, and how:**

| Hazard | Rule | Enforced by |
| --- | --- | --- |
| Maths functions (`sin`, `cos`, `atan2`, `exp`, `powi` and so on) differ by platform | Only from the kernel's own maths module, `geom_num::math` (6.4): correctly rounded CORE-MATH ports in the kernel's own source for the proven functions (`sinpi`, `cospi`, `exp`, `ln`, `atan2`; G05), and the pure-Rust `libm` crate for `sqrt`, `fma`, rounding and, kept apart in `math::unproven`, the functions with no proven bound. What correct rounding rests on is below the table | Kernel crates are `no_std` (the standard ones are not even available); `clippy` disallowed-methods |
| NaN sign and payload are not deterministic, even in WebAssembly | No public kernel function returns NaN, and none makes one from finite inputs. Scalars are checked at construction. Inside `geom_num::math` the CORE-MATH ports compute on raw doubles and make only the canonical NaN, `0x7ff8_0000_0000_0000`. Two parts of `geom-num` take or give raw doubles by design, with fixed bits: the error-free transformations of `geom_num::eft`, which return NaN only where IEEE 754 itself does (a NaN input, ∞ − ∞, 0 · ∞), and `ExactSum::round_ieee` (G25), Neal's IEEE result, which may be NaN or infinite. Kernel code feeds `eft` only checked scalars, and takes `ExactSum::round`, never `round_ieee` | A NaN-free scalar type, `Real`, whose only constructor refuses NaN and the infinities; fuzzing; a test that the ports make only the canonical NaN. Debug tripwires are planned (G24). G02 has none: behind that one constructor, a tripwire on a `Real` could never fire (31.7) |
| `max` and `min` may return either zero sign | Use the kernel's own total-order helpers | `clippy` disallowed-methods |
| Other zeros whose sign IEEE 754 leaves to the computation's history | One zero: a zero `sinpi` or `cospi`, a zero second part of an error-free transformation, a zero interval bound and an exact zero `ExactSum` are all +0 (G02, G05, G25). Every other maths function keeps IEEE 754's sign of zero: `sqrt(−0)`, `floor(−0)`, `ceil(−0.5)`, `round_ties_even(−0.25)` and `atan2(−0, x)` for x > 0 are −0. Golden hashes hash bits, so this rule is part of the same-answer promise; it waits for acceptance (31.7) | Tests of each function at its zeros |
| Relaxed and "algebraic" operations, relaxed SIMD | Forbidden | `clippy` disallowed-methods; no relaxed SIMD feature |
| Parallel float reductions change order | Fixed chunk sizes independent of thread count, results collected in order, no float reduction across chunks | One shared parallel helper; a thread-count test (1, 2, 3 and 8 threads); `clippy` disallowed-methods bans `Iterator::sum` and `Iterator::product` for every element type, integers included, so a sum is written in a stated order or goes through `ExactSum` (23.4) |
| Hash map iteration order is random | No iteration over hash maps | `clippy` disallowed-types for `HashMap` and `HashSet` in kernel crates |
| Random numbers, clocks, and process or thread identity | One generator, `geom_num::rng` (Philox4x32-10, G32), whose seed, stream and position are explicit inputs, the seed recorded in the operation log (16.3, 17.10). No entropy, clock, memory address, process or thread id, or randomly seeded hasher | `clippy` disallowed-methods and disallowed-types in every kernel crate's `clippy.toml`, a copy of `geom-num`'s: std's `RandomState`, `SystemTime`, `Instant`, `process::id`, `thread::current` and random module, the x86 RDRAND, RDSEED and RDTSC intrinsics, and the entry points of `rand`, `rand_core`, `getrandom`, `hashbrown`, `foldhash`, `fastrand` and rayon's thread index. Memory addresses stay a review rule |
| Tie-breaks by memory address | Never. Ties break by persistent name | Code review rule; tests that shuffle allocation |
| Targets that break IEEE (i586 x87, 32-bit ARM NEON flushing denormals) | Excluded from the guarantee | Documented platform list |

**A `clippy` ban can lapse in silence.** An entry whose path no longer resolves, such as a std path a later toolchain renames, makes clippy print "`<path>` does not refer to a reachable function" (or "type"). Under clippy 0.1.99 that is a warning which neither `-D warnings` nor `RUSTFLAGS=-D warnings` turns into an error, and a `no_std` build does not print it at all (G32). So the merge gate is to fail CI on that message (28.8, piece "Merge gate: licences, lints and builds"); until it does, a lapsed ban goes unnoticed.

**What correct rounding rests on.** The CORE-MATH ports give the same bits on every target because the same Rust code runs everywhere. That any later correct implementation gives the same bits, "fixed by specification", holds only where correct rounding is proven. For `sinpi`, `cospi`, `exp` and `ln` it is proven for every input with fewer than 44, 44, 48 (33 for results below 2^-1059) and 55 identical bits after the round bit, and for every input in CORE-MATH's published worst-case lists, which the tests check one by one. That the lists hold every harder input is CORE-MATH's search result, not a proof, and two lists qualify it: `exp.wc` covers "most inputs", and `log.wc` "should have all". `atan2` has two arguments, so its hard cases cannot be listed at all. Every input is proven within ½ + 2^-45.6 ulp (`sinpi`, `cospi`), ½ + 2^-49.2 ulp (`exp`; ½ + 2^-34 below 2^-1059), ½ + 2^-56.6 ulp (`ln`) and ½ + 2^-128 ulp (`atan2`), and every result is proven faithful, so certified enclosures are sound either way (G05, `math.rs`). A hard case the lists missed would mean a future fix changes bits, which only a new operation version or edition may do (28.13).

**Checked on every pull request:** an operation-log replay corpus runs on x86-64 Linux, Windows and macOS, aarch64 Linux and macOS, and wasm32 under wasmtime and Node, in debug and release, with `-C target-cpu=native`, and with 1, 2, 3 and 8 threads. The SHA-256 of each canonical output must match the golden value. This is the method Rapier and Box2D use to keep their physics deterministic ([05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 7).

**What the kernel's CI runs today** (G02's `kernel.yml`): six native legs, the five above plus Windows on aarch64 (`windows-11-arm`), and wasm32-wasip1 under wasmtime and Node. Windows on Arm joins the guarantee only if the owner accepts it (32.4, option C). Three gaps remain, each for piece "Determinism matrix and golden store" or "CI matrix and check tiers" to close:

- wasm32-wasip1 has no threads, so on wasm32 the tests at 2, 3 and 8 threads are skipped (`geom-math`'s and `geom-num`'s, G03, G05) or run every task on the calling thread (`geom-run`'s test pool, G04). Only a threaded WebAssembly target (wasm32-wasip1-threads, or browser workers, 23.4) can run them (31.7).
- On wasm32 the debug leg runs `geom-num`'s golden digest only: the whole suite takes well over an hour there without optimisation. The release leg runs the whole suite.
- Goldens other than `geom-num`'s `tests/determinism.rs`, such as `geom-run`'s, `geom-math`'s and the seeded generator's, run only inside the whole-suite legs, not in the `target-cpu=native`, overflow-checks-off or wasm32 debug legs. `geom-math`'s, `geom-run`'s and the seeded generator's goldens, and the digest of G25's double-double and `ExactSum` tests, are still 64-bit FNV-1a values, not SHA-256 (G03, G04, G32, G25; 31.7).
