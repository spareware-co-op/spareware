Papers are cited by DOI, each checked against Crossref.

A mesh is a surface made of flat polygons, usually triangles. Every program needs meshes: to draw, to exchange with tools that read only triangles, to simulate, and to answer "do these two things hit each other?" quickly across a whole building or a whole car. Most kernels treat meshes as approximate floating-point copies with a tolerance. Spare Kit does not. A Spare Kit mesh is exact data on the grid, decided by the same exact predicates as the rest of the kernel, and it carries a proven bound on how far it is from the shape it stands for. Only the copy sent to the screen is approximate, and it is a different type that no operation accepts.

Two crates do this work (section 27):

- `geom-mesh`: the exact mesh, watertight tessellation, levels of detail, mesh booleans and modelling operations, healing of imported meshes, and volume meshes for simulation.
- `geom-spatial`: spatial queries on the shared box tree (19.9), distance, clearance, clash, contact over time, and the instance tree for huge assemblies.

## 19.2 The exact mesh

An exact mesh is a surface of flat polygons. Its data model is adapted from Manifold's, the best-tested open one ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md), section 2), with changes that make it exact and deterministic and let it hold everything a boolean or an import can produce.

- **Half-edges, stored as parallel arrays.** A half-edge is one side of an edge: it belongs to one face and points one way. Manifold keeps half-edges as structure-of-arrays (one array of start vertices, one of paired half-edges, one of property vertices) instead of one record each, which is compact and fast to scan ([shared.h L246-L348](https://github.com/elalish/manifold/blob/d056b8fb70de8c8e6d6bee2e639b71c20aa08d01/src/shared.h#L246-L348)). We keep that. Manifold's faces are always triangles, found by arithmetic (three half-edges each). Ours are polygons with holes: a face owns a run of loops, the first its outer boundary and the rest its holes, and each loop owns a run of half-edges in order. A wall face with a window in it is one face with two loops.
- **Plane-based polygons.** Every face points to its supporting plane, and every half-edge to an **edge plane**, a second plane through that edge. This is the polygon form of EMBER and its integer plane arithmetic ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md), section 5): a corner is the meeting of the face's plane and two consecutive edge planes, so a polygon can be cut again without constructing anything. A face made from grid points takes as each edge plane the plane through the edge that contains the face's dominant coordinate axis. Its coefficients (at most a 42-bit normal and an 85-bit offset) are smaller than a face plane's (83 and 125 bits, [05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 4), so every predicate stays within section 6.2's 384 bits.
- **Vertices are grid points or meetings of three planes.** A vertex is explicit (an `i64` grid point) or implicit (three planes, kept exactly as section 6.3 requires). An implicit vertex whose coordinates turn out to be whole grid steps is stored as a grid point, so one point never has two forms. Planes live in a pool, each stored canonically (common factors removed, sign fixed), so the same plane always has the same bits.
- **Non-manifold edges.** Where more than two faces meet at an edge (two solids touching along a line, a cellular model, the General bodies of section 8.1), each half-edge is paired with its neighbour in exact radial order around the edge, the rule section 11.7 uses for fins, so every pair bounds one cell.
- **Property vertices.** A property vertex carries display data (normal, texture coordinates, colour) apart from the geometric vertex, so a texture seam or a shading crease does not split the surface and break its closure. This is Manifold's `propVert` idea. Properties are display data and never take part in a decision.
- **Provenance runs.** A run is a contiguous range of faces from one source: one B-rep face, one IFC face set, one boolean operand. It records the source's persistent name (a `NameId`, section 20), its role and its flags, as Manifold's runs and `TriRef` do ([mesh.h L102-L163](https://github.com/elalish/manifold/blob/d056b8fb70de8c8e6d6bee2e639b71c20aa08d01/include/manifold/mesh.h#L102-L163)). Manifold draws mesh IDs from a process-wide atomic counter, so they depend on thread timing ([impl.cpp L71-L75](https://github.com/elalish/manifold/blob/d056b8fb70de8c8e6d6bee2e639b71c20aa08d01/src/impl.cpp#L71-L75)). Ours come from the operation's `OpPath` and the source's name, so they are the same on every machine.
- **Canonical order.** The plane pool is sorted by coefficients. A grid vertex's key is its Morton code (its coordinate bits interleaved into one 123-bit number, so nearby points sort near each other). An implicit vertex's key is the smallest triple, in pool order, of independent planes through it among its faces' and edges' planes. Runs are sorted by source name and role; faces in a run by their smallest vertex key and then their whole key sequence; each loop starts at its smallest key, and holes follow in key order. Nothing is ordered by float value, memory address or hash, so a mesh's bytes depend only on its content.

```rust
/// An exact polygon mesh. Every face is flat; every vertex is a grid point or a meeting of three planes.
pub struct ExactMesh {
    planes: Vec<Plane>,          // integer a, b, c, d (i128), canonical, sorted
    verts: Vec<Vertex>,          // Grid(GridPoint) | Planes([PlaneIx; 3]), sorted by key
    face_plane: Vec<PlaneIx>,    // supporting plane of each face
    face_loops: Vec<u32>,        // loops of face f: face_loops[f]..face_loops[f + 1]; the first is the outer loop
    loop_start: Vec<u32>,        // half-edges of loop l: loop_start[l]..loop_start[l + 1], in order
    he_vert: Vec<VertIx>,        // start vertex; the end is the next half-edge's start in its loop
    he_plane: Vec<PlaneIx>,      // edge plane
    he_pair: Vec<HalfEdgeIx>,    // opposite half-edge; exact radial order on non-manifold edges
    he_prop: Vec<PropIx>,        // property vertex
    props: PropTable,            // display data only
    runs: Vec<Run>,              // { faces, source: NameId, role, flags }
    face_dev: Vec<Steps>,        // proven distance of each face from its source; 0 when exact
    class: Exactness,            // Exact, Certified(eps) or Approximate(eps), relative to the source
    kind: MeshKind,              // Closed | Open | General (non-manifold edges)
}
```

**Why polygons, not only triangles.** Boolean results have implicit vertices. Cutting a non-convex polygon with implicit corners into triangles needs orientation tests on three implicit points: about 840 bits per term (two 294-bit coordinates times a 252-bit weight, [05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 4), far past section 6.2's limit. Keeping polygons avoids those tests and keeps meshes small. Convex pieces, which is what the arrangement produces, may be fanned into triangles with no test at all; EMBER also outputs polygons. Elsewhere triangles are made only where coordinates are explicit: on grid vertices, or in floating point at the display boundary. A polygon may hold consecutive vertices on one straight edge, where a neighbour's vertex was inserted to keep the mesh conforming. The mesh recognises them by shared edge planes. That check is conservative: two different edge planes can meet along the same line, and then it misses that the vertices are in line, which is harmless.

**What it guarantees.** The validity checker (section 8.3) gains a mesh group, after the closure certificate of csgrs's hypermesh ([11](../../../kit/notes/G01-evidence/11-vetting-suggested-projects.md); [surface_arrangement.rs L4336-L4456](https://github.com/timschmidt/csgrs/blob/1bd74092cad1d8a52b2a4dc4fa1fae2bcc605586/crates/hypermesh/src/surface_arrangement.rs#L4336-L4456)): every loop closes; no edge has zero length and no face is degenerate or repeated; every vertex lies exactly on its faces' planes; every edge is used equally often in each direction, with consistent radial pairing; a `Closed` mesh has no boundary edge. The group lives in `geom-mesh::exact` and runs before any mesh is published. `geom-check` does not depend on `geom-mesh`, so the validity query across representations, in `geom-combine`, calls both (27, accepted in 32.13).

**Mass properties.** For grid vertices, six times the volume is a sum of integer determinants (each under 2^123 relative to the frame origin), and twice each face's area vector is a sum of integer cross products. Both fit 256 bits and are exact. A face's area is half that vector's length, a square root, so it is a certified interval from the exact squared length. For implicit vertices each term is an exact fraction, but adding fractions with different denominators needs integers that grow without bound, so volume is a certified interval, rounded outward. Each quantity states its class in the operation's output.

**Exactness, stated twice.** The arithmetic on a mesh is always exact. The mesh's exactness class (section 9) says how far it is from what it stands for: Exact for a flat-faced solid or a quantised import, Certified(δ) for a tessellation of curved faces, with δ kept per face.

**Raw meshes.** Imported soups that are open, non-manifold or self-intersecting are a separate type, `RawMesh`. Its vertices are grid points, because import always rounds into the frame first (19.7, step 1); only its topology is unchecked. It is the mesh counterpart of a Tolerant body: an import state that healing turns into an exact mesh. Only healing, reconstruction, display and clash accept a `RawMesh`, and clash reports surface contacts on it only (19.11), because inside and outside are undefined for an open surface.

**As built (G146).** `geom-mesh::exact` holds the arrays above as `Parts`; `ExactMesh::new` is the only way to a mesh, and it runs the whole checker group. A face and an edge plane each hold a `Facing`, a row and whether it looks the other way, because a canonical plane has one sign. An edge plane faces into its face. Grid vertices sort before three-plane ones. On a shared development machine a million triangles with a million planes of their own build and check in about 1.9 s on 1 thread and 1.1 s on 8, and check alone in 0.25 s and 0.09 s; sorting the pool is the largest step. Chapter 30's 0.5 s is not reached.

**What it never does.** No `f64` coordinates. No per-mesh epsilon: Manifold's is a relative precision times the largest coordinate of the bounding box, so the same shape is decided differently in a different place ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md), section 1). No global counters. No vertex welding inside an operation.

## 19.3 Watertight tessellation of B-reps

Tessellation turns a B-rep into an exact mesh within a requested distance δ of the true surface. Watertight means neighbouring faces share every boundary vertex bit for bit, so there are no cracks. The method is the edge-first scheme of Sheng and Hirsch ([doi:10.1016/0010-4485(92)90011-X](https://doi.org/10.1016/0010-4485(92)90011-X)) that OpenCascade documents ([mesh.md L74-L116](https://github.com/Open-Cascade-SAS/OCCT/blob/53706f78a8640c4407bdcc6752df13a270b159f2/dox/user_guides/mesh/mesh.md#L74-L116); [04](../../../kit/notes/G01-evidence/04-nurbs-surfaces.md) section 5), with proven bounds in place of heuristics.

**The bounds.**

- *Second derivatives.* For each face, a bound M on the surface's second derivative over any parameter box comes from the traits of section 7. For a NURBS patch it comes from Bernstein bounds on the derivative control nets (The NURBS Book, A3.7), using the convex-hull property. For a rational surface S = A/w (A the weighted numerator, w the weight function, bounded below by the smallest weight), the quotient rule gives S_u = (A_u − w_u·S)/w, S_uu = (A_uu − 2w_u·S_u − w_uu·S)/w and S_uv = (A_uv − w_u·S_v − w_v·S_u − w_uv·S)/w, evaluated in outward-rounded intervals, with S bounded by its control points. Subdividing a net down to a box also runs in outward-rounded intervals. This settles [04](../../../kit/notes/G01-evidence/04-nurbs-surfaces.md)'s open question on weight-aware bounds. The bound used is M = max(M_uu, M_vv) + M_uv, which bounds ‖d_u²S_uu + 2d_u·d_v·S_uv + d_v²S_vv‖ for every unit direction, because 2|d_u·d_v| ≤ 1. Analytic surfaces use closed forms. Offsets, blends and subdivision limit surfaces supply their bounds through the same traits.
- *The chordal bound.* The flat triangle through three surface points is within ½·M·r² of the surface over that triangle, where r is the radius of the smallest circle enclosing the triangle in parameter space. The module carries the two-line proof: along any unit vector e, f = e·S plus (M/2)·|x − c|² is convex, so it lies below its linear interpolant, and since the corners lie within r of the circle's centre c, f − Lf ≤ ½·M·r²; the same holds for −f. The bound is sharp when c lies inside the triangle. Waldron ([1998, doi:10.1137/S0036142996313154](https://doi.org/10.1137/S0036142996313154)) derives the sharp pointwise bounds for linear interpolation on a simplex; whether he states this exact form is unverified. By Jung's theorem every triangle fits in a circle of radius ℓ/√3, where ℓ is its longest edge, so ℓ ≤ √(6δ/M) is enough.
- *Curves.* The chord over a parameter step h is within ⅛·h²·max‖C″‖ of the curve (Filip, Magedson and Markot, [doi:10.1016/0167-8396(86)90005-1](https://doi.org/10.1016/0167-8396(86)90005-1)), with max‖C″‖ from the same Bernstein bounds, or a closed form for lines, arcs and conics.

As built (G68): `ParamSurface::second_derivative_bound` gives every kind's boxes of S_uu, S_uv and S_vv over a parameter box, from its partials there, and `SecondPartials::chord` gives M from them. A rational patch's partials are the quotient rule above in interval jets, with S taken from the patch's Euclidean control points, never from A/W of two boxes; a rational curve's C″ likewise starts from its control points. `ParamSurface::normal_derivative_bound` bounds the partials N_u and N_v of the unit normal, from the jets of S_u × S_v, its length and their quotient, each cut to |n_u|/|n|; it says `Unbounded` where the enclosure of n holds zero, so a caller that needs it subdivides (`geom-surface`'s `attack_g68.rs`: all but a few in a hundred of boxes of 1/4096 of a patch's sides are bounded where the normal is not nearly zero). Every bound is checked against exact rational values on dense samples with weights from 10⁻³ to 10³.

**A parameter grid.** Each face's (u, v) values are rounded to a fixed-point grid of 2^52 steps across its parameter box. The scale is a power of two, so conversion is one exact multiply and one rounding. Every parameter-space predicate (loop checks, the triangulation, Simulation of Simplicity) is then a fixed-size integer computation behind a generated filter, as section 6.2 requires: orientation of 53-bit differences fits `i128` and the in-circle test fits 256 bits (derivations in the module). Rounding (u, v) moves a surface point by at most the first-derivative bound times half a step, and that is added to the face's bound. There are no Shewchuk expansions and no `robust` crate here: [03](../../../kit/notes/G01-evidence/03-rust-kernels-crates.md) section 4 notes it has no overflow or underflow guard.

**The steps.**

1. **Edges first, once each, from local data only.** Each edge is sampled once, at a spacing that is the smallest of three limits: the curve's own chord bound; for each face using the edge, the length that meets δ over a strip along the edge, reduced by √3/2 so that a boundary triangle built on it still meets δ; and the face's local feature size in parameter space (Ruppert 1995, [doi:10.1006/jagm.1995.1021](https://doi.org/10.1006/jagm.1995.1021)), the certified distance from the edge's pcurve to every boundary curve of the face it does not touch, so that no chord comes near another loop. Each limit depends only on the edge and its faces' surfaces and loops, never on how a neighbour was triangulated. Parameter intervals are halved in a fixed order until all three hold. There is no random step; verb samples with `Math.random()` ([Tess.hx L121-L128](https://github.com/pboyer/verb/blob/f3ba23cdccbab77102b686021460cf9779df240f/src/verb/eval/Tess.hx#L121-L128)). A seam edge (a closed face's edge used twice, such as a cylinder's seam) is sampled once and mapped through both of its pcurves. A degenerate edge, such as a sphere's pole or a cone's apex, is one vertex, and the face fans to it.
2. **Commit to the grid.** Each sample is rounded to the grid once, by at most half a step per coordinate, and every face using the edge uses the same integer vertices. Watertightness is a fact of the data, not a tolerance. It holds even for an imported Tolerant edge whose faces disagree by up to ε_heal.
3. **Into each face's parameter space.** Samples map to each face's (u, v) through its pcurve. That assumes the pcurve and the 3D curve share a parameter. They agree within a deviation the checker certifies (section 8.3, group 2), and that deviation enters the face's bound, with the commit rounding and, for a Tolerant edge, its tolerance. The boundary polygons are checked exactly. A crossing would mean a spacing limit was computed wrongly, and returns `Internal`.
4. **Constrained Delaunay triangulation.** This is the triangulation with the fattest triangles that still keeps the boundary edges. The kernel has one, `geom-mesh::cdt`, ported from Geogram's `CDT_2d` (BSD-3-Clause, 29.3) onto the integer predicates. Ties are broken by Simulation of Simplicity in a fixed order the caller supplies, never insertion order or memory address: vertex keys here, persistent names in terrain (sections 6.2 and 17.3). With every tie broken by one rule the result is unique, so it does not depend on insertion order, as Geogram's does (17.3). It supports crossing constraints, which terrain needs and tessellation does not, because boundary edges never cross: a crossing is found by exact orientation tests and constructed exactly from the two original constraint ends, as Geogram's triangulator does ([`create_intersection`](https://github.com/BrunoLevy/geogram/blob/40d72165ceeeb0a61977d6fdf74d929bfdd77b7b/src/lib/geogram/delaunay/CDT_2d.cpp#L1717-L1745)), and is committed to the grid before any circle test, so every circle test runs on grid points within 256 bits. Geogram's open build instead tests crossing points with an approximate lifted coordinate (17.3). Terrain adds only its crossing policy, with snap rounding, and point deletion on top (section 17.3). spade (MIT or Apache-2.0) stays out of kernel crates (29.12): its routine for crossing constraints computes intersection points in floating point ([cdt.rs L1227](https://github.com/Stoeoef/spade/blob/c8befc96bbbc1898a89cb19f9f3104a848936374/src/cdt.rs#L1227)). As built (G153): `triangulate` takes sites with keys, constraints and an optional quality. Ties go by key: the lowest-ranked of four cocircular points is raised most, so the diagonal misses it. Crossings are committed in rounds over the whole set of constraints, each bending its two constraints through its rounded point, until none cross; a point on a constraint splits it. On a development machine 1M points with 10,000 breaklines a few spacings long take about 0.8 s, and with 10,000 breaklines across the model about 2.3 s.
5. **Refine inside, never on an edge.** Delaunay refinement (Ruppert 1995; Shewchuk 2002, [doi:10.1016/S0925-7721(01)00047-5](https://doi.org/10.1016/S0925-7721(01)00047-5)) inserts points inside the face, at parameter-grid points, until every triangle's longest edge meets the bound for its own box. A boundary triangle that fails gets the apex of the equilateral triangle on its boundary segment. Every vertex the triangulation can then join to that segment lies inside that apex triangle's circumcircle, so the new boundary triangle's longest edge is at most 2/√3 of the segment, and the strip limit makes it meet δ. Refinement ends because each box's target length is at least √(6δ/M) for the face's largest M, which is positive. The module carries the proof that interior points always suffice when the three edge limits hold. That proof is ours, and it is reviewed before the module merges.
6. **Check in 3D, and keep rounding harmless.** Interior samples are evaluated on the surface and committed to the grid. Rounding moves a vertex by at most (√3/2)·q, and that can collapse or flip only a triangle whose smallest altitude is under about 3.5q. So refinement never creates a triangle with an altitude under h_min = 8q, checked on the certified positions before rounding. h_min is derived from the commit rounding and adds no tolerance: 1.25 µm at q0, 50 nm at q1. It is not a number of this chapter's own: section 6.5 lists it as the proposed rung "Smallest triangle altitude, h_min", and the code takes it from the ladder module in `geom-num` once an owner accepts that rung. A triangle at least that tall keeps its orientation through rounding and turns by at most about 30°. A point closer than h_min to an existing vertex is not inserted, so inserted points stay apart and refinement always ends. After rounding, each triangle's normal, an exact integer cross product, must agree in sign with the surface normal bounded over the triangle. A disagreement near a singular point is fixed by an exact edge flip or by removing the interior vertex, never by more refinement. Finally the faces of the body are checked for crossings: two faces of a thin part that are closer than their two bounds can cross after tessellation, and they are refined until they do not.

A request names the chord bound δ (default ε_fit). It may add a normal-angle bound, for smooth shading and zebra lines on Class-A surfaces, proven from bounds on the normal's derivative, not sampled. It may add a longest edge, for simulation and textures. The result is an exact mesh of class Certified, with each face's achieved δ, one run per B-rep face named by that face, and the history of section 20.3 (each run generated from its face).

**Flat faces.** A polygonal face, flat with straight edges, is not sampled at all. It becomes a polygon on its own plane with its own exact vertices, implicit ones included, and δ = 0. A flat face with arc edges (a round hole, the top of a curved wall) has sampled edges whose committed points can lie off its plane by the commit rounding, so it is triangulated, each triangle on its own plane, within its edges' bound.

**Caching, without changing the answer.** Every cache entry is a pure function of its key. An edge's samples are keyed by its curve and ends, every adjacent face's surface and loops (they set the spacing limits), δ, the options and the kernel edition. A face's mesh is keyed by its surface and loops, the hashes of its edges' samples, δ, the options and the edition. When an edge's key changes, every face using it is re-tessellated. An incremental result is therefore the same, byte for byte, as a tessellation from scratch, and tests check that after random edit sequences. A moved door reuses its own tessellation, because its definition did not change, and re-tessellates only the host faces its opening cuts, which are flat and need no sampling. Certified tessellations can be stored with the B-rep (section 24), so a 230,000-element model opens without tessellating.

**Errors.** The loop runs inside the operation's budget. A face that cannot reach its bound without breaking h_min, for example at a cusp where two faces meet at zero angle, fails with `BoundNotReached`, naming the face, the parameter box and the bound it reached. Nothing is returned with a crack, a flipped triangle or an unproven bound.

**What it never does.** No fixed segment counts: web-ifc's 12 segments per circle ([IfcGeometryProcessor.h L26-L36](https://github.com/ThatOpen/engine_web-ifc/blob/dd44aa77e770d2584b6d4095dec0d89f4a4cf6d0/src/cpp/web-ifc/geometry/IfcGeometryProcessor.h#L26-L36)) and IfcOpenShell's one-segment arcs ([#9768](https://github.com/IfcOpenShell/IfcOpenShell/issues/9768)) are what this replaces. No normal-angle heuristics standing in for a bound, as in curvo and verb. No recovering (u, v) by Newton search, as Truck does with 100 trials ([03](../../../kit/notes/G01-evidence/03-rust-kernels-crates.md) section 1; [triangulation.rs L24-L47](https://github.com/ricosjp/truck/blob/78d699b0792b39e27c2bf073b682986701644e91/truck-meshalgo/src/tessellation/triangulation.rs#L24-L47)). No GPU trimming feeding back into geometry. And not the two patented routes to watertight trimmed surfaces, through T-splines and the "watertightCAD" reparametrisation ([09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md), section 3).

## 19.4 Levels of detail and the display boundary

A level of detail (LOD) is a coarser mesh drawn when an object is small on screen.

- **Certified levels for curved bodies.** Level k uses δ_k = 2^k·ε_fit, and the renderer picks k so that δ_k projects to under half a pixel. Each level is a full certified tessellation, cached per body and level. Where one huge body (a terrain, a long roof) needs levels per face, each edge is sampled at the finest level any of its faces needs, so faces at different levels still share every edge sample, with no cracks or T-junctions ([04](../../../kit/notes/G01-evidence/04-nurbs-surfaces.md), section 5).
- **Simplification for every display mesh.** Flat-faced bodies have δ = 0 at every level, so certified levels do nothing for them, and they are most of a building. A wall with 300 openings would stay at full detail in the distance. So any display mesh may be simplified by meshoptimizer's method: edge collapses ranked by quadric error (Garland and Heckbert 1997, [doi:10.1145/258734.258849](https://doi.org/10.1145/258734.258849)) with attribute weights, and clusters simplified with their borders locked, so independently simplified chunks still meet without cracks ([README L544-L660](https://github.com/zeux/meshoptimizer/blob/f0a684f11ead064e176775c9b796f82a55910e92/README.md?plain=1#L544-L660)). The same code builds meshlets, the small clusters a GPU culls and draws as units. Scans, terrain and distant city context use it the same way.
- **Levels by role, from the program.** A program may supply its own coarse levels by role. Spare Construct can draw a distant wall from its uncut body, with no openings, as the coarse detail levels of building tools do.
- **Ported, not linked.** meshoptimizer is MIT-licensed C++. Kernel crates are `no_std`, forbid `unsafe` and must give bit-identical results in the browser, and whether the C++ build does is unverified ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md), section C). So `geom-mesh::display` is a safe-Rust port of the simplifier and meshlet builder, keeping meshoptimizer's licence and credit. Its hash tables are used for lookups only ([simplifier.cpp L111-L195](https://github.com/zeux/meshoptimizer/blob/f0a684f11ead064e176775c9b796f82a55910e92/src/simplifier.cpp#L111-L195)), which section 8.2 allows as long as nothing iterates them; its sorts get a total order with ties broken by key. Bit-identical output also lets display chunks be cached and streamed by content hash. The renderer, outside the kernel, may still use the `meshopt` crate for vertex-cache ordering and compression.
- **The display mesh is another type.** `DisplayMesh` holds `f32` positions relative to a chunk origin on the grid, plus triangles, normals and meshlets. Chunk-relative positions matter: `f32` keeps 24 significant bits, so 100 km from the origin it resolves only about 8 mm. Its class is Approximate with the measured error, and no kernel operation accepts it, so the type system keeps display data out of decisions.

## 19.5 Mesh booleans and exact mesh operations

Mesh booleans have no algorithm of their own. `geom-mesh` hands its faces and their planes to the plane-based arrangement in `geom-poly` (section 11.3) and gets back pieces labelled with winding numbers. It keeps the pieces the selection's indicator keeps and merges them into maximal faces. EMBER's pieces are convex and leave T-junctions (a vertex in the middle of a neighbour's edge), so the merge also inserts each such vertex into the neighbour's loop, after an exact test that it lies on that edge, which makes the mesh conforming. The indicator and the merge are the same as in `geom-bool`'s rebuild, so they belong in `geom-poly`, shared by both (27, accepted in 32.13). Results are exact, never re-rounded however often they are cut, and identical on every target ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md), section 6).

- **Inputs must be closed.** The arrangement needs input whose winding number is a whole number everywhere (piecewise-constant winding number, PWN), as EMBER does ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md), section 5). Self-intersections are fine; holes are not. Open input fails with `NotClosed`, which names healing as the remedy.
- **Many operands, one arrangement.** A list of operands and a small boolean expression over their winding numbers give several results from one arrangement, the truth-DAG design of hypermesh ([winding.rs L36-L105](https://github.com/timschmidt/csgrs/blob/1bd74092cad1d8a52b2a4dc4fa1fae2bcc605586/crates/hypermesh/src/winding.rs#L36-L105)). Cutting 300 openings is one call. An expression whose result contains the outside, such as "not A", has no finite boundary and fails with `UnboundedResult`, naming the expression, as hypermesh does.
- **History and names.** A mesh operation emits the history of sections 20.2 and 20.3 at run level: each output run is unchanged, modified (trimmed, one piece kept), split (named `Split { piece: ByTools { tools, side } }` by the tool runs that cut it and the side), or merged, and deleted runs are listed. New edges are named `Bounded` by their two faces, and new corners by the faces meeting there. Faces inside an imported run have only weak ordinal names (section 20.2), so references should target runs or their carrier planes. The invariants of section 20.3 are property-tested on mesh booleans.
- **Mixed representations.** The one boolean entry point across representations is the dispatcher in `geom-combine`, the internal crate below the facade that section 11.8 proposed and chapter 27 places in layer 10 (accepted in 32.13); `engine-geometry` only exposes its schema (sections 9 and 11.8). If any operand is a mesh, B-rep operands are tessellated with a certified δ, and the result is Certified with the summed bound.

The same machinery gives:

- **Plane slices**, for 3D-printing layers and plan cuts of imported meshes: closed contours whose vertices are exact line-plane meetings, committed to the grid only on output.
- **Convex hulls**, by quickhull on grid points with exact orientation tests and Simulation of Simplicity, for the distance filter of 19.10.
- **Mesh to faceted B-rep**, an edge of the conversion graph (section 16): adjacent faces on the same canonical plane merge into one face. Planes are matched by sorting their canonical keys; web-ifc's pairwise matching stalls on large slabs ([#2097](https://github.com/ThatOpen/engine_web-ifc/issues/2097)).
- **Export, at each format's precision.** Grid points are exact decimals in millimetres (q0 is 0.00015625 mm, q1 is 0.00000625 mm), so OBJ, ASCII STL and 3MF, which store decimal text, carry grid vertices exactly. Binary STL and glTF store `f32`, so they are written relative to a chunk origin (a glTF node translation). Each value is rounded once to the nearest `f32`, so its error is at most half a unit in the last place at the chunk-relative magnitude, which the writer proves from the chunk's extent. The export is Certified by that proven rounding bound plus the tessellation bound, as section 24.10 states; Approximate is kept for simplified display meshes (19.4). Implicit vertices are committed to the grid first, and that commit rounding is added to the bound. Rounding a valid mesh can create a tiny self-intersection or a flipped triangle ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md), section 5), so the exporter re-checks the rounded mesh and reports anything rounding introduced, with its location (19.13).

## 19.6 Mesh modelling operations

Programs that work on meshes alone (3D printing, scans, games, products shaped from scans) need to edit meshes, not only draw them. Each edit is an operation with a stated class.

| Operation | Method | Class |
| --- | --- | --- |
| Decimation to a bound | Quadric edge collapses (Garland and Heckbert 1997). A collapse is accepted only when the exact envelope test of 19.8 proves the new faces lie within ε of the input and the input within ε of the new faces. Each collapse is a local operation with invariant checks and rollback, the pattern of wildmeshing-toolkit (MIT, [43d74ecf](https://github.com/wildmeshing/wildmeshing-toolkit/tree/43d74ecfe0631d3f7ee1203be6fd3c1ccb90838b)), with ties in its priority queue broken by key | Certified(ε) |
| Isotropic remeshing | Split, collapse, flip and smooth toward a target edge length (Botsch and Kobbelt 2004, [doi:10.1145/1057432.1057457](https://doi.org/10.1145/1057432.1057457)), as in the PMP library (MIT, [215975ca](https://github.com/pmp-library/pmp-library/tree/215975ca1efafab97477b18187a4a23b87529036)), under the same envelope check | Certified(ε) |
| Smoothing and fairing of scans | PMP's fairing method. It changes the shape on purpose | Approximate, measured |
| Offset, hollow, thicken | Topological Offsets (Zint et al. 2025, [doi:10.1145/3731157](https://doi.org/10.1145/3731157); MIT code at [d75b55e](https://github.com/wildmeshing/topological-offsets/tree/d75b55e4477dc95cd9e4781e0413d3a9d474d67d)), which section 13 points here. Its distance band is checked, not trusted: every result face lies inside the envelope of width d + ε and at least d − ε from the input, by the exact tests of 19.10 | Certified(the band) |
| Minkowski sum of flat solids | Both solids split into convex pieces (the arrangement's pieces are convex). Each pair's sum is the exact convex hull of sums of grid points, and all sums are united in one n-ary boolean. Implicit vertices are committed first, making the result Certified. The size grows with the product of piece counts, so it runs inside its budget. It gives the volume a translating tool sweeps | Exact on grid vertices |

**Content creation.** Film, game and product tools model on plain meshes, paint textures onto them and hand simple collision shapes to physics engines. These operations serve them:

| Operation | Method | Class |
| --- | --- | --- |
| Polygon modelling: extrude, bevel, insert and slide edge loops, bridge, fill holes, merge and split faces, mirror | The edits section 16.1 offers on subdivision nets, rebuilt for the exact mesh. New vertices are grid points or meetings of three planes (19.2), and every result passes the mesh checker group, flat faces included, before it is published; an edit that cannot keep its faces flat fails with an error naming them. Each edit names its outputs by role, such as an extrude's cap and sides (section 20) | Exact; Certified by the commit rounding where a new vertex is committed to the grid |

## 19.7 Healing and reconstructing imported meshes

Meshes from IFC files, scans and other tools are often open, inconsistently oriented, self-intersecting or full of near-duplicate vertices. Two separate operations fix them. Neither ever runs silently inside another operation, and each is recorded in the operation log with what it did and where.

**Heal** stays within ε_heal: by default 640q (0.1 mm at q0), or a value the caller sets up to the cap of 6,400q, recorded in the log.

| Step | What it does | Class |
| --- | --- | --- |
| 1. Quantise | Round coordinates into the frame, once | Exact relative to the quantised input; the rounding is reported |
| 2. Weld | Visit vertices in key order. Each joins the lowest-keyed representative within ε, measured exactly as squared integer distances; otherwise it becomes a representative. Candidates come from the cell index, but the decision is the exact distance, so cell alignment changes nothing, and representatives never move, so clusters cannot chain. Faces that become degenerate are removed and listed | Certified(the largest movement, at most ε) |
| 3. Close small holes | A boundary loop that fits inside a ball of diameter ε is closed by a fan from its lowest-keyed vertex, so every new point is within ε of the input | Certified(ε) |
| 4. Orient | Orientation floods across manifold edges from the lowest-keyed face of each patch. A closed piece faces outward by the sign of its exact volume. Each flip is recorded. Non-orientable pieces and edges that cannot be paired are reported | Exact |
| 5. Resolve | If the mesh is now closed (PWN), the arrangement of 19.5 resolves self-intersections and overlaps by winding number | Exact relative to step 4 |

The result is Exact if nothing moved, otherwise Certified with the movement reached. Heal fails with `NotClosed` (listing each open boundary, its location and its size) or `ToleranceExceeded` (a gap needing more than the cap). Its remedies name `reconstruct` and the class it would give. Heal never retries with ever-larger fuzz or dilates cutters, as IfcOpenShell does ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md), section A3).

**Reconstruct** runs only when the caller asks. The caller names a method, or the lowest class and largest deviation it accepts; the methods are then tried in the order below, and the result names the one that ran. The result is Approximate, with its deviation measured in both directions by the distance query of 19.10. It is not bound by ε_heal, because filling a large hole moves the surface by more than that.

| Method | How | What is proven |
| --- | --- | --- |
| Winding-number rebuild | The method of Jacobson, Kavan and Sorkine-Hornung ([2013, doi:10.1145/2461912.2461916](https://doi.org/10.1145/2461912.2461916)) on an exact decomposition. `geom-poly`'s subdivision cuts each box by the planes of the input faces it holds into convex cells; a box holding k planes has at most about k³/6 cells, and the subdivision keeps k small. Each cell's generalised winding number is evaluated at a point inside it, chosen by a fixed rule, as a sum of solid angles in outward-rounded arithmetic, or by the fast form of Barill et al. ([2018, doi:10.1145/3197517.3201337](https://doi.org/10.1145/3197517.3201337)) with its truncation error bounded. Cells whose interval lies above ½ are kept. Cells whose interval contains ½ are reported, never guessed. The boundary between kept and dropped cells is the result. The paper labels cells with a graph cut; ours thresholds, which is deterministic | Faces lie on input planes, so input faces survive exactly wherever they bound the result |
| Envelope remesh | The volume mesher of 19.8 inside an envelope of the caller's width; tets inside by winding number are kept and their boundary is the result | Every output point lies inside the envelope; sharp features survive |
| Signed heat | The signed heat method (Feng and Crane 2024, [doi:10.1145/3658220](https://doi.org/10.1145/3658220)) solves for a signed distance on a regular grid or a tet mesh, after step 4 has oriented the input, which the method assumes ([README L7](https://github.com/nzfeng/signed-heat-3d/blob/3638fa48a9317201b32d44db5b4cac8e651cc927/README.md?plain=1#L7)). Its zero level is contoured by section 16's dual contouring | Nothing proven; closes large holes and survives noise |

- Winding numbers are ported from libigl's MPL-2.0 core files only; its `copyleft` folder is GPL ([10](../../../kit/notes/G01-evidence/10-github-sweep.md)). Axom (BSD-3) supplies the same for trimmed NURBS ([09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md), section 3).
- signed-heat-3d is MIT, but it builds its tets with TetGen, which is AGPL ([.gitmodules](https://github.com/nzfeng/signed-heat-3d/blob/3638fa48a9317201b32d44db5b4cac8e651cc927/.gitmodules)). We take the method only. Its README compares a regular grid with tets ([L38-L46](https://github.com/nzfeng/signed-heat-3d/blob/3638fa48a9317201b32d44db5b4cac8e651cc927/README.md?plain=1#L38-L46)), so the grid version comes first and does not wait for our tet mesher. A signed distance is a field, so this method lives in `geom-field` and is reached through the conversion graph in `geom-convert` (section 16); the other two live in `geom-mesh::repair`.
- MeshFix (GPL-3) and CGAL (GPL or LGPL) are method only ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md), section C).

## 19.8 Volume meshes for simulation

Structural, thermal and flow analysis need the inside of a solid divided into simple cells, usually tetrahedra (tets).

**Tets follow fTetWild** (Hu et al. 2020, [doi:10.1145/3386569.3392385](https://doi.org/10.1145/3386569.3392385)), an envelope method built to cope with dirty input, which [10](../../../kit/notes/G01-evidence/10-github-sweep.md) section 1 lists for porting. It inserts the input triangles into a background tet mesh, letting the surface move only inside an envelope of width ε around the input. It then improves the tets by splitting, collapsing and swapping edges and by smoothing vertices, lowering the AMIPS distortion energy, never inverting a tet and never leaving the envelope. Finally it keeps the tets that are inside by winding number. It does not promise to keep every input triangle exactly; it promises that the boundary stays inside the envelope.

fTetWild is MPL-2.0, our own licence, so its code could be ported with its notices. Reading it at a pinned commit shows why we port the method onto our foundations instead of translating it line by line:

- it shuffles the input triangles with a hardware-seeded random generator unless a flag turns that off, so two runs differ ([TriangleInsertion.cpp L146-L151](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/src/TriangleInsertion.cpp#L146-L151));
- it requires GMP rationals, which are LGPL ([CMakeLists.txt L84-L86](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/CMakeLists.txt#L84-L86)), and runs TBB loops that gather results in concurrent containers ([TriangleInsertion.cpp L1102-L1103](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/src/TriangleInsertion.cpp#L1102-L1103));
- its envelope is a fraction of the bounding-box diagonal ([Parameters.h L58-L59](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/src/Parameters.h#L58-L59)), so the same part meshed inside a bigger model gets a looser envelope;
- the exact envelope is off by default ([CMakeLists.txt L49](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/CMakeLists.txt#L49)), and the default test samples points on each triangle ([LocalOperations.cpp L714-L775](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/src/LocalOperations.cpp#L714-L775)); the exact library sets the processor's rounding mode ([ip_filtered.cpp L45](https://github.com/wangbolun300/fast-envelope/blob/f50eb6c1572c5865bfab3cac1acae0e27c8b4a82/indirectPredicates/ip_filtered.cpp#L45)), which WebAssembly cannot do;
- a triangle it cannot insert is left out ([TriangleInsertion.cpp L405-L420](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/src/TriangleInsertion.cpp#L405-L420)), and whether the surface already covers it is checked by sampling ([L3172-L3180](https://github.com/wildmeshing/fTetWild/blob/8118f810478e0e65a7bf2d8cecdc5e203a876e97/src/TriangleInsertion.cpp#L3172-L3180)).

fast-envelope is MIT at `f50eb6c1`, but its `indirectPredicates/` folder has no licence notice of its own and appears to come from Attene's indirect predicates, which are LGPL (29.3; provenance unverified). Under rule 1 the strictest reading applies, so that folder is method only (rule 6) and nothing is taken from it; the envelope predicates below are re-derived from the paper. A ledger row for fast-envelope is raised for section 29.

**Spare Kit's mesher keeps the method and changes the foundations.**

- **Grid vertices.** Tet vertices are grid points, so "is this tet inverted?" is an exact `i128` orientation test.
- **Insertion.** A triangle is cut into the tets it crosses. Each cut point is rounded to the grid, and the cut is accepted only if no tet inverts, checked exactly. Otherwise the triangle stays uninserted, as in fTetWild, and is retried after the mesh improves. Any left at the end are checked with the exact envelope test, roles swapped, for being covered by the inserted surface. The rest are listed with their locations. With `RequireAllInserted`, a leftover is an error.
- **An envelope with integer corners.** This is the polyhedral envelope of Wang et al. ([2020, doi:10.1145/3386569.3392426](https://doi.org/10.1145/3386569.3392426)). Each input triangle's envelope is a convex polyhedron whose corners are grid points, inscribed in the ε-offset of the triangle, so "inside the envelope" proves "within ε". Every envelope predicate is then a grid point against a plane through grid points (`i128`), a line-plane point against a plane, or a three-plane point against a plane, section 6.2's deepest test at 379 bits. The predicates are re-derived in our own code, with no rounding modes. The width is absolute, in grid steps.
- **The grid is fine enough.** Rounding rejections become common only where tets are a few hundred grid steps across. A part with features below about 0.1 mm sitting in a q0 frame is meshed in a q1 frame, an exact conversion (multiply by 25).
- **Improvement.** Split, collapse, swap and smooth, as in fTetWild, built as local operations with invariant checks and rollback after wildmeshing-toolkit's architecture. Priority ties break by key, and maths functions come from the kernel's deterministic module.
- **Order.** Input order is a fixed sort, and parallel steps run in fixed chunks merged in order.
- **Feature curves and names.** B-rep edges are inserted as feature curves, under the same insert-or-defer rule, so boundary faces follow them. Each boundary face is tagged with the single source face whose envelope contains it, so loads and supports attach to named faces and survive edits (section 20). A face whose test names two source faces, which happens only where a feature curve could not be inserted, carries both names and is listed.
- **Several regions at once.** The input may be section 11's general-fuse arrangement, with shared faces once. Each tet takes its cell's label, so wall layers (for thermal bridging), board stack-ups and assemblies mesh with conforming interfaces.

**Output.** Every tet has strictly positive volume, exactly. Every boundary face is proven within the envelope and tagged. The class is Approximate, carrying the envelope width and the measured two-sided deviation. A quality report gives the worst dihedral angles and the energy. A design spike settles the insertion rule, the envelope's bit budget and the feature-curve rule before the large build pieces start.

**Beyond tets.**

- **Prisms and hexahedra for 2.5D bodies.** A body qualifies when every face is exactly a cap (normal along one direction) or a side (normal across it, or a surface extruded along it): walls with rectangular openings, slabs, beams, sheet-metal parts. It is meshed in layers between its cap heights, as prisms, or hexahedra where the section is rectangles. The mesh is Exact for straight sections at grid heights and Certified with curved sides. Anything else, such as a wall with an arched opening, gets tets.
- **Shells and plates** use the tessellator of 19.3 with a longest-edge limit and Ruppert's minimum angle.
- **Deferred, with owners:**

  | Need | Plan | Owner |
  | --- | --- | --- |
  | Higher-order (curved) elements | Mid-edge nodes on the true surface; validity proven by Bernstein bounds on the element's Jacobian (Johnen, Remacle and Geuzaine 2013, [doi:10.1016/j.jcp.2012.08.051](https://doi.org/10.1016/j.jcp.2012.08.051)) | `geom-mesh::tet`, a later piece |
  | Boundary-layer prisms for flow | Layers grown from the tagged boundary inside the same envelope rules | `geom-mesh::tet`, a later piece |
  | Quad and quad-dominant shell meshes | Field-aligned remeshing, Instant Meshes (BSD-3, PORT in [10](../../../kit/notes/G01-evidence/10-github-sweep.md)) | `geom-mesh`, a later piece |
  | Mid-surfaces of thin solids | From offsets and the straight skeleton | Sections 13 and 16 |
  | Line models of frames | From the roles of beams and columns | The program's domain toolkit (section 26) |
  | Tets that keep every input triangle exactly (constrained Delaunay tetrahedralisation) | Papers only: Si 2015 ([doi:10.1145/2629697](https://doi.org/10.1145/2629697)), Shewchuk's constrained Delaunay papers, and Diazzi, Panozzo, Vaxman and Attene 2023 ([doi:10.1145/3618352](https://doi.org/10.1145/3618352)). TetGen's source is AGPL and never read (29.3) | Later, after a design note |
  | All-hexahedral meshes of any solid | Open research; not promised | — |

## 19.9 The bounding-volume hierarchy

A bounding-volume hierarchy (BVH) is a tree of boxes. Each node's box encloses everything below it, so a query skips every branch whose box it misses. It is the spatial index behind selection, picking, hidden lines (section 18), point-cloud snapping (section 17), distance and clash.

We write our own, as [03](../../../kit/notes/G01-evidence/03-rust-kernels-crates.md) section 4 recommends. parry's tree is good (Apache-2.0; we study its builders), but its SIMD dot products once broke cross-platform determinism ([CHANGELOG L175-L177](https://github.com/dimforge/parry/blob/b3c3584ce9be9bf6edb821fd7548b817087131ff/CHANGELOG.md#L175-L177)). The `bvh` crate works in `f32` over nalgebra.

- **Boxes are whole grid steps.** Every box is rounded outward to whole grid steps, so its values are integers, which section 23 calls integer boxes. They are stored as `f64` for ray and distance arithmetic, which is exact because every value is below 2^53. Boxes around curved geometry come from the conservative bounds of section 7. A box never misses what it should contain.
- **Built by the binned surface-area heuristic** (Wald 2007, [doi:10.1109/RT.2007.4342588](https://doi.org/10.1109/RT.2007.4342588)): each node's split is chosen from a fixed number of bins per axis to minimise expected traversal cost. Each split is a pure function of the node's contents, ties break by key, and parallel subtrees join in a fixed left-to-right order, so the tree is the same for any thread count. Near the depth limit the builder switches to median splits in key order, so depth never exceeds the limit.
- **Refit or rebuild.** When an instance moves, its box is updated and the change passed up the tree (a refit). When the tree's cost, computed deterministically, passes a limit named in the module, it is rebuilt.
- **Answers do not depend on the tree.** Every query returns a set sorted by persistent keys. A refitted or rebuilt tree, a native or browser build, one thread or eight: the answer is the same. That also allows internal boxes to be stored as `f32` rounded outward, halving their size, if the memory benchmark of 19.12 needs it.
- **Queries.** Boxes overlapping a box; boxes within a distance of a box (for clearance); all close pairs within one set or between two; nearest objects; rays; and convex polytopes, for view volumes and section boxes. A ray from a grid point along an integer direction is answered exactly against grid faces. A screen ray in floating point is rounded to that form first, and the answer says so. Per-frame culling on the GPU belongs to the renderer.
- **Bounded traversal.** Traversal uses an explicit stack with a depth limit, never recursion, because WebAssembly stacks have no guard page (principle 13). It checks the cancellation token at fixed steps.

**Layering.** The tree knows only boxes and keys, so it sits low in the stack. It is the one box tree of the kernel, 2D and 3D, in its own crate in layer 2, `geom-bvh`, on `geom-run`, `geom-num` and `geom-math` (27, accepted in 32.13, which answers chapter 11's open question 2(b)). This section describes that tree; `geom-spatial` builds the queries above, distance, clash and the instance tree on it. Every other crate that needs a tree uses the same one: `geom-bool`'s broad phase (section 11.4), `geom-intersect`, `geom-2d`'s picks and snaps (section 14.8, in place of the R-tree first proposed there), `geom-draw`, `geom-terrain`, `geom-field`, and `geom-mesh`'s searches over faces (the envelope test, the fast winding number, crossing checks). One other structure remains, for a stated reason:

- A linear octree of grid cells sorted by Morton code indexes points, not boxes. It serves welding and other point searches, where one sort builds it and no point needs a box of its own. It lives in `geom-bvh` beside the tree, not in `geom-mesh` (27, accepted in 32.13).

## 19.10 Distance and clearance

Distance is the gap between two shapes. Clearance asks whether that gap is at least a required value c, such as the maintenance space around plant or the gap between two pipes. The rule: decide exactly where the data are exact, bound the answer where they are not, and never round a decision into a guess.

**On grid meshes, every decision is exact.** Coordinates under 2^40 make differences 41 bits, dot products about 85 bits and cross products about 84 bits. Each test below carries its derivation in the module and a test at the extreme values (every coordinate at ±(2^40 − 1)), as section 6.2 requires.

| Question | How | Integer width |
| --- | --- | --- |
| Do two triangles touch or cross? | The test of Devillers and Guigue (2002), which uses only orientation predicates | `i128` |
| Which features are closest (vertex, edge or face)? | Signs of dot products and of differences of their products, such as d1·d4 − d3·d2 (about 171 bits) | 256 bits |
| Is a point within c of a point, an edge's line or a plane? | Squared distance against c²; for a line, \|ap\|²·\|ab\|² − (ap·ab)² against c²·\|ab\|²; for a plane, (n·(p − a))² against c²·\|n\|² (up to 254 bits) | 256 bits |
| Are two edges within c, with closest points inside both? | (w·(u × v))² against c²·\|u × v\|² | 256 bits |

Triangle-to-triangle distance derivations are ported from GeometricTools (Boost licence, [10](../../../kit/notes/G01-evidence/10-github-sweep.md)) and re-certified with our predicates. Distances are reported as outward-rounded `f64` intervals; the decisions behind them are exact.

As built (G151): `geom_num::distance` holds the 256-bit comparisons and `geom-mesh::contact` the triangle test and closest features. A contact with any zero sign is reported as `Touch`, and `Cross` only when every sign was strict.

**Implicit vertices.** Touch and cross tests on plane-based polygons need only "which side of this plane is this point", exact within 384 bits. Distance comparisons on implicit vertices would need wider integers than section 6.2 allows. So, for distance only, such vertices are committed to the grid, widening the interval by at most (√3/2)·q per body.

**Analytic pairs in closed form.** Spare Construct's map asks for the narrow phase to use exact kernel geometry, not triangles. Most building pairs are planes, cylinders and spheres: pipes, ducts, beams and slabs. With their data on the grid (points, integer directions, and radii and clearances in whole steps), the common closest-feature cases are decided exactly:

| Pair | Exact test | Width |
| --- | --- | --- |
| Cylinder against a plane parallel to its axis (a pipe on a slab) | (n·p + d)² against (r + c)²·\|n\|² | 256 bits |
| Cylinders with parallel axes | \|w × a\|² against (r₁ + r₂ + c)²·\|a\|² | 256 bits |
| Cylinders with skew axes, closest points inside both lengths (crossing pipes) | (w·(a₁ × a₂))² against (r₁ + r₂ + c)²·\|a₁ × a₂\|², with exact parameter checks | 256 bits |
| Sphere against a point, line, plane, sphere or cylinder axis | Squared distances against the squared sum of radii and c | 256 bits |
| Cylinder axis against a box's edges and faces | As above, with exact parameter checks | 256 bits |
| A circular rim, a cone or a torus involved | Closed form in outward-rounded arithmetic, with no iteration | Certified |

A pipe resting exactly on a slab is an exact `Touch`, not a near miss. The closed forms live in `geom-intersect`, beside section 12's, and `geom-spatial` depends on `geom-intersect` directly, with no cycle and no trait in the facade (27, accepted in 32.13).

**Other curved shapes, through certified tessellations.** For NURBS, blends, offsets and sweeps, let d be the distance between the two meshes and Δ each body's total bound: its source's own certified bound (ε_fit for intersection curves, blends and offsets), plus the tessellation bound, plus the commit rounding. The true gap lies in [d − Δa − Δb, d + Δa + Δb]. If the whole interval is at or above c, the pair is clear; if below, it is within clearance. If it straddles c, only the faces near the closest points are tessellated again with their bound halved, and the test repeats. The floor needs no new constant: refinement stops once the tessellation part is no larger than the rest of Δ, because halving it again cannot narrow the interval much. A pair still straddling at the floor is reported as `NearLimit`, with the source bound and the rounding term given separately. `geom-spatial` does not read B-reps itself. The caller hands it a refiner, a small trait object that asks `geom-mesh` for a finer tessellation of named faces in a region.

**Overlap, proven.** For flat-faced Exact elements, a crossing in which every orientation sign is strict proves overlap at once. Only contacts with a zero sign go to the arrangement, which settles touch against overlap exactly and can return the exact overlap volume. For curved shapes, two tessellations that cross do not prove the true solids overlap, because the crossing may be shallower than the bounds. Overlap is proven by a witness point lying deeper than Δa inside A's mesh and deeper than Δb inside B's. The true surface lies within Δ of the mesh, so it cannot pass over the witness. Finding a witness may use heuristics; checking one does not.

**Overlap depth.** Spare Construct sets a tolerance per test, such as "ignore overlaps shallower than t". Depth is the radius of the largest ball inside both bodies. A witness gives a lower bound: its distance to both boundaries. An upper bound comes from branch and bound over the overlap's box. Distance to a surface changes no faster than position does, so a cell whose centre is less than t minus half the cell's diagonal deep in either body cannot hold a point t deep, and is dropped. A case that still straddles t at the floor is `NearLimit` against t. Depth is computed only when a test sets t.

**GJK, as a certified filter.** GJK (Gilbert, Johnson and Keerthi 1988, [doi:10.1109/56.2083](https://doi.org/10.1109/56.2083)) finds the distance between two convex shapes by walking their Minkowski difference; EPA (van den Bergen 2001) extends it to penetration depth. We follow parry's (Apache-2.0) and coal's (BSD-3) implementations as method references. GJK runs on the convex hulls of the certified tessellations, which enclose the true shapes once grown by Δ, so the hull distance minus (Δa + Δb) is a lower bound on the true gap. GJK works in `f64`, and its answer counts only through a certificate checked exactly: its separating direction is rounded to integers, and each hull's extreme vertices along it are compared in integers. A poor float step can make the filter useless, never wrong. EPA's depth means something only for convex parts ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md), section C), so it never decides anything. Approximate convex decompositions, such as V-HACD, never enter a decision; 19.6 offers one only as an output for physics engines.

## 19.11 Clash

Clash finds pairs of elements that overlap, or that come closer than their required clearance. This section settles the geometric half of Spare Construct's piece A13 ("Clash: broad and narrow phase, true-distance clearance"). A13 owns the product half: rules, ignore conditions, grouping into issues, BCF exchange, standard New Zealand clearances, whether live clash is on by default, how `NearLimit` is shown, and a benchmark of this method on a real model. If A13's benchmark shows this method is wrong, it says so, and this section changes through a decision note.

**Pipeline.**

1. **Broad phase.** The instance tree (19.12) lists pairs whose boxes come within c of each other. Rules supplied by the caller (same system, insulation on its own pipe, parts of one assembly) remove pairs before any geometry is read.
2. **Narrow phase.** For each pair: the certified GJK filter; then traversal of the two definitions' trees, in the pair's relative placement, to find candidate face pairs; then, per face pair, the exact mesh tests for flat faces, the closed forms for analytic pairs, and certified tessellations with refinement for the rest (19.10).
3. **Containment.** If no surfaces meet, one element may still sit wholly inside the other, such as a sleeve inside a wall. One vertex of each is classified against the other: a grid vertex by exact ray parity, with Simulation of Simplicity applied to the ray's start point only, so no perturbation of implicit points is needed ([05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 5); an implicit vertex by `geom-poly`'s exact winding tracing (section 11.3). Mirrored instances flip the sign.

**Outcomes.** Every pair gets one outcome, with witness points and the names of the faces involved:

```rust
pub enum Contact {
    Clear { gap: Interval },                          // proven: gap >= c
    WithinClearance { gap: Interval },                // proven: 0 < gap < c
    Touch,                                            // proven exactly: boundaries meet, interiors do not
    Overlap { witness: GridPoint, depth: Interval, volume: Option<Interval> }, // proven: interiors overlap
    NearLimit { signed_gap: Interval, threshold: Threshold, source: Length, rounding: Length },
                                                      // within the geometry's own bound of 0, c or t
    SurfacesCross { witness: GridPoint },             // raw meshes only: inside is undefined
}
```

- `Touch` is returned only when it is decided exactly: flat faces, and the analytic pairs of 19.10. Two walls sharing a face touch; a duct resting exactly on a beam touches. Neither is a clash unless the rules say so, and no tolerance is needed to tell touch from overlap.
- A curved pair whose gap is within the geometry's own bound of zero is `NearLimit`, never `Touch`, so no consumer, person or AI, can mistake a possible 5 µm penetration for a proven touch.
- A pair involving a `RawMesh` can be `Clear`, `WithinClearance`, `Touch` or `SurfacesCross`, never `Overlap`.

**No false hits, no misses.** A box is only ever used to find candidates, never to report a clash, so inflated boxes cannot produce hits; Spare Construct's map asks for exactly this. Every reported clash rests on an exact decision or a proven interval. Boxes are conservative, so the broad phase cannot drop a real pair.

**One answer per pair, whatever the order.** Each pair is evaluated in a canonical frame: the frame of the definition with the lower content key (or, for two instances of one definition, of the instance with the lower key), with the other rotated into it and rounded there. So clash(A, B) equals clash(B, A), and a pair's result is a pure function of the two definitions' content, their relative placement, c and the kernel edition. That is its cache key. Running out of the work-unit budget happens at the same point on every machine (section 23), so that result is cached with the budget in its key. A cancelled pair is never cached.

**Live and batch.**

- *Live:* an edit refits the moved instance's box, queries its neighbours and re-tests only pairs involving it. Identical floors of a tower, placed by whole-step translations, share one result per repeated arrangement.
- *Batch:* sets against sets, in fixed-size chunks in parallel, with results sorted by pair key. A pair that runs out of budget returns its own error and does not fail the list (section 10.1).

**Beyond static models.**

- **Swept volumes.** A door swing, a crane's reach, a vehicle's swept path or a cutting tool's path becomes a swept volume (section 13) and is clashed the same way.
- **Time of first contact.** For moving bodies, `geom-spatial` finds when a moving vertex first meets a moving triangle, or two moving edges meet, by the Tight Inclusion method (Wang et al. 2021, [doi:10.1145/3460775](https://doi.org/10.1145/3460775); MIT code at [6f84001a](https://github.com/Continuous-Collision-Detection/Tight-Inclusion/tree/6f84001a790a9d3362b7c13d410037140d83fa2c)). It subdivides time and space with inclusion tests that never miss a contact. Our port runs on linear motions between grid positions with outward-rounded inclusion tests. It reports the first contact time as an interval: Certified, never missing a contact, possibly reporting one within its stated bound. Its tests use the authors' Apache-2.0 time-of-impact sample and our own exact cases; the 2021 benchmark carries no licence, so it waits until the authors clear it (owner action G285, 32.31).
- **Scan against model.** Comparing a laser scan with the model (as built against as designed) uses the same distance query, point by point, from `geom-cloud` (section 17).

**As built (G147).** `geom-mesh::classify`: a ray up z from a grid point, its start moved by (ε², ε), so the mesh never moves. A three-plane point takes `beside`: a grid corner off the surface, then one exact trace with `geom-poly`, the point's wedge as the cutter.

## 19.12 Instancing for huge assemblies

A building with 2,000 identical doors, a tower of repeated floors, a car of 30,000 parts or a 50 km corridor of repeated barriers stores each shape once.

- **Definitions and instances.** A definition is a body or mesh with its tessellations per level and its own tree, built once and cached by content hash and kernel edition. An instance places a definition and copies no geometry, as IFC's mapped items do ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md), section C).
- **Two levels of tree.** The instance tree holds instance boxes. Each definition has its own tree in its own frame. A query enters a definition by transforming the query, rounded outward, into the definition's frame, so only the geometry the query touches is ever transformed.
- **Nested assemblies.** An instance may place an assembly with its own instance tree. Traversal descends with an explicit stack and a depth limit.
- **Placements use `geom-math`'s transform kinds.** Translations by whole grid steps, quarter turns and mirrors are exact (section 7), so an instance placed that way is exactly its definition, moved. A mirror flips orientation, and winding numbers and ray parity account for it. Any other rotation is held as an index into the document's shared table of rotations, rounds the definition's vertices to the grid when a query needs them, and makes the result Certified with that rounding in its bound. A scale, uniform or not, makes a new definition, transformed once by section 7's typed transforms, so a circle becomes an ellipse rather than a B-spline, as it does on IfcOpenShell's route ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md), section A1).
- **Frames.** A part in a fine frame (q1) placed in a building (q0) is compared in the fine frame, converting only the region the query needs, which is exact (section 6.1). If that region does not fit the fine frame's range, the comparison falls back to the coarse frame and is Certified. Neighbouring frames of a regional network differ by an exact lattice shift.
- **Memory.** The kernel has one instance record, 23.9's `Placed`, in `geom-topo`; this section defines no second one. It copies nothing and is at most 88 bytes, asserted by a size test: a handle to its definition, its placement (a grid shift with one of 48 signed axis permutations, or an index into the side table of general transforms) and its integer box, held once. A definition keeps its own frame, so the record needs none. The instance tree in `geom-spatial` stores only record indices in its leaves. Answers list record indices in ascending order, so they never depend on the tree, and the facade maps kit-core's permanent IDs to those indices.

The kernel's budget per instance is 23.1's share, at most 96 bytes, and the 88-byte record fits it. The tree adds a 4-byte leaf index and a share of its internal nodes: leaves of up to four instances give about one node per two instances, each a box and a child index, so about 28 bytes per instance, or about 14 with internal boxes stored as `f32` rounded outward (19.9). Record and tree together come to about 106 to 120 bytes. That is under Spare Construct's 256 bytes per placed instance, but over 23.1's share, which counts the record alone, so counting the tree in that share is raised for section 23. The 1,000,000-instance benchmark measures the total with the kernel's allocation counter. Pair caches belong to the caller and are counted there.

## 19.13 Guarantees at a glance, and what is still unsolved

| Operation | Result class | Fails with |
| --- | --- | --- |
| Tessellate | Certified(δ per face); Exact for polygonal faces | `BoundNotReached` |
| Certified level of detail | Certified(2^k·ε_fit) | as tessellate |
| Display simplification | Approximate, measured; display type only | never fails; reports its error |
| Mesh boolean | The least exact input, bounds summed | `NotClosed`, `UnboundedResult`, budget |
| Decimation, remeshing | Certified(ε) | budget |
| Offset, hollow, thicken | Certified(the band) | budget; band not met |
| Minkowski sum | Exact on grid vertices | budget |
| Polygon modelling | Exact, or Certified by the commit rounding | an edit that cannot keep its faces flat; budget |
| UV unwrapping and packing | Approximate, distortion measured; property data only | flipped or overlapping charts, with 16.4's remedies; budget |
| Convex decomposition | Approximate, measured both ways; never feeds a decision | budget |
| Heal | Exact, or Certified(movement up to ε_heal) | `NotClosed`, `ToleranceExceeded` |
| Reconstruct | Approximate, measured both ways | budget; undecided cells reported |
| Tet mesh | Approximate; boundary proven inside the envelope | budget; leftover triangles under `RequireAllInserted` |
| Distance and clearance | Exact decision, or a proven interval | budget |
| Clash | One `Contact` per pair | per-pair budget error |
| Time of first contact | Certified interval; never misses a contact | budget |

Where the open literature stops:

- **Guaranteed rounding on export.** Rounding an exact mesh to a file's floats so that no self-intersection can appear is possible in theory (Fortune 1999, [doi:10.1007/PL00009480](https://doi.org/10.1007/PL00009480)), but the construction is reported to need very many vertices (O(n⁴); unverified). Spare Kit keeps exactness inside its own format, writes grid vertices exactly to decimal formats, re-checks every export and reports any defect rounding introduced. It promises an honest report, not a guaranteed float file.
- **All-hexahedral meshing** of arbitrary solids is open. Spare Kit offers prisms and hexahedra for 2.5D bodies and tets for everything else.
- **Tessellation at cusps.** Where faces meet at zero angle, the bound may not be reachable above h_min. Spare Kit returns `BoundNotReached` with the location, never a mesh that crosses itself.
- **Repair of open soups** cannot recover intent that was never in the file. Reconstructed results are Approximate with measured deviation, and every step is in the log for a person or an AI to review.
- **Tangent contact of non-analytic curved shapes**, such as a NURBS duct resting on a NURBS shell, is decided only down to the geometry's own certified bound. Below it the kernel reports `NearLimit` with that bound, never a guess.

**Before building.** Section 29.17 lists clash, clearance and continuous collision detection; mesh simplification and remeshing; shells, offsets and thickening; and slicing as families no patent search has covered. It also says nobody has reviewed how 19.3's edge-first tessellation relates to the claims of US 10,614,195. So the pieces for tessellation (19.3), display simplification and decimation (19.4 and 19.6), remeshing and mesh offsets (19.6), slicing (19.5), distance and clash (19.10 and 19.11) and time of first contact (19.11) depend on section 29's build piece "Patent register" for their family. Each enters the Build stage only after a recorded search and owner review (29.17, rule 10).
