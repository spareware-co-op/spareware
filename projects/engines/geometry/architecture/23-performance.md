# 23. Performance and parallel work

*Part of the [Spare Kit geometry kernel architecture](../ARCHITECTURE.md). Decided in [G01](../../../kit/notes/G01-geometry-kernel.md); section numbers match across the set.*

Evidence: [05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) sections 2, 4, 7, 8 and 9; [01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) sections 1, 2, 3, 5 and 6; [03](../../../kit/notes/G01-evidence/03-rust-kernels-crates.md) sections 4 and 5; [09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md) sections 2 and 5; [08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md) sections B, C and D; [07](../../../kit/notes/G01-evidence/07-persistent-naming.md) section 7; [06](../../../kit/notes/G01-evidence/06-2d-drafting.md) section 6; [02](../../../kit/notes/G01-evidence/02-occt-parasolid-acis.md) section 3; [10](../../../kit/notes/G01-evidence/10-github-sweep.md) on point clouds, volume meshing and sweeps; [11](../../../kit/notes/G01-evidence/11-vetting-suggested-projects.md) on Truck; Spare Construct's [performance targets](../../spare-construct/ARCHITECTURE.md#performance-targets-and-testing); and the primary sources pinned where they are used.

The kernel is fast for the same reasons it is exact: whole-number coordinates, immutable values and pure operations. Speed never comes from bending a principle in section 3. Every fast path must return the same bits as the plain path it replaces. For filters and integer variants that is proven by construction; for caches, shortcuts and parallel runs it is tested on every pull request (23.13). Time is saved in five ways, biggest first: don't compute (stored geometry, caches keyed by content); compute less (only what changed, only what is near); compute in bulk (batch and n-ary operations); compute cheaply (shortcuts before exact arithmetic, fixed-width integers, compact memory); and compute in parallel, through one helper that cannot change a bit.

## 23.1 The targets, and the kernel's share

Spare Construct's ten targets are for the whole program: kernel, regeneration engine, renderer and interface together. The kernel gets a share of each. Meeting its share keeps the kernel from being the reason a target is missed. The owner accepted the shares (owner action G72, 32.16). They are for native builds on the reference machine, the owner's spare tower timed on its 8 performance cores (28.17), and are replaced by measured figures once the scenario benchmarks run.

| Target (whole program) | Kernel's share | What the kernel does in that time |
| --- | --- | --- |
| Open the 230,000-element model to first view in under 3 s; a 20-building block in under 5 s | 1 s; 1.5 s for the block | Decode the stored bodies and stored display meshes of the chunks in view, verify their hashes and run the cheap combinatorial check (23.11). Nothing is regenerated or re-tessellated. Neighbouring buildings arrive as stored low-detail meshes |
| Move a door in under 16 ms | 4 ms | Re-solve the door's sketch cluster (section 15), re-cut the host (23.5), check and name the result, re-tessellate the changed faces, re-section the changed elements for open plan views, and re-test their clashes (section 19) |
| Change a level height touching 2,000 walls in under 1 s | 600 ms | Regenerate the walls through the parallel helper: about 2.4 ms of kernel time per wall per core |
| Navigate 1,000,000 instances at 60 fps | Nothing per frame | The kernel is never in the frame loop. It hands the renderer one set of meshes per shared body, with levels of detail and their deviation, and an integer box per instance |
| Plan view: first draw under 500 ms, under 16 ms after an edit | 250 ms first; 4 ms per edit | Section and project each element in view, cached per element and view. Hidden lines are section 18 |
| Memory per placed instance: under 256 bytes plus shared type geometry | About 140 bytes | The one instance record, 19.12's `Instance` (56 bytes), its leaf entry in the instance tree (56 bytes) and its share of the tree's internal nodes (about 28 bytes), as 19.12 counts them. Shared geometry is stored once |
| Save in under 100 ms, never blocking | Nothing on the save path | Saving appends to the operation log. Encoding and hashing the bodies an edit changed runs in background compaction: at most 10 ms for a local edit, about 100 ms for the level change (derived) |
| Another user sees an edit in under 200 ms on a LAN | The same as the local edit | The other machine replays the operation through the same kernel and gets the same bits: 4 ms for a door move. A global edit takes its local time there too; fetching the changed chunks by content hash instead is Spare Construct's choice |
| Print a 100-sheet set to PDF in under 60 s | 40 s | Sections, projections and hidden lines for every view, views in parallel through the helper, reusing the per-element caches |

**How the door-move share was sized** (derived, order of magnitude only; replaced by the measurements of 23.2 and 23.3). Re-cutting a wall with 3 openings from its uncut body takes about 50 candidate face pairs and about 2,000 predicate calls. If 90% settle in the first three steps of 23.2 at about 2 ns, 9% in the filter at about 10 ns and 1% exactly at about 200 ns, the predicates cost about 10 µs. Building the faces, naming them, the cheap checks and re-tessellating the changed faces add about 1 to 3 µs per output face: about 50 to 150 µs in all. A host with 300 openings has about 2,000 output faces and needs about 3 to 8 ms natively, over the share. So a full re-cut covers hosts with up to about 50 openings, and larger hosts use the local re-cut of 23.5, whose cost does not grow with the host's other openings. The predicate mix is an assumption that the step counters of 23.2 measure.

**In a browser.** Results are the same bits, but slower. Wide multiplies cost 2 to 7 times as much as natively ([wide-arithmetic Overview L26-L28](https://github.com/WebAssembly/wide-arithmetic/blob/024d4ce1b28cee7fd006d9c5175e3b7ece52b429/proposals/wide-arithmetic/Overview.md#L26-L28)), and until WebAssembly threads reach stable Rust the kernel runs serially in one Web Worker (23.4). Estimated browser shares (derived, to be measured): a door move within 4 ms on hosts with up to about 10 openings; the 2,000-wall level change about 1 to 6 s serially, so it shows progress and can be cancelled, as Spare Construct already specifies for global edits, and it meets its 1 s target only in the threaded build; open and plan view within their shares for the chunks in view. Which targets must hold in a browser is Spare Construct's open question on browser-only use. The browser benchmarks report against these shares either way. Memory in a browser is in 23.9.

**Computational design** has a different shape: thousands of small operations per change, such as 10,000 facade panels, each divided, offset, extruded and cut. For that the kernel promises a small fixed cost per operation (proposed: at most 5 µs of overhead for a trivial operation on native targets), batch calls with one result per item, and a cache hit for every panel that did not change. Other programs' needs are in 23.12.

## 23.2 Exact predicates at full speed

Every topological decision is an exact predicate (section 6.2). In a building, many calls are not hard but are exactly zero: walls share faces, slabs sit at the same level, edges line up. A floating-point filter can only certify a sign that is clearly not zero, so every exact zero would fall through to the slowest path. The kernel therefore avoids arithmetic where the data already knows the answer, and uses the narrowest exact arithmetic that fits. Each call takes the first step that settles it.

| Step | What it does | Cost | What it settles |
| --- | --- | --- | --- |
| 1. Identity | Each plane is stored in canonical form: its integer coefficients divided by their greatest common divisor, with the sign fixed (the face records which side is material). Faces on the same plane share one plane entry, within a body and across the operands of one operation. "Is this face on that plane" is an index comparison, and a vertex defined by plane P lies on P with no arithmetic | One comparison | Coplanar faces and vertices on their own planes, the commonest degenerate cases in buildings |
| 2. Narrow exact | A magnitude check proves that every intermediate fits in 63 bits, and the predicate runs exactly in `i64`. Example: orient2d with coordinate differences under 2^31 steps (335 m at q0) | A few integer operations | Most plan and drafting tests |
| 3. Axis | Classifying an explicit grid point against a plane square to a frame axis is one integer comparison. For an implicit vertex (three planes meeting) it still needs the vertex's wide numerators, but skips the general plane product: about 300 bits instead of 384 (derived) | One comparison, or one narrower product | Levels, slabs, walls along the frame's axes |
| 4. Filter | The generated `f64` evaluation with a semi-static error bound (Meyer and Pion's method, as in Geogram's PCK, BSD-3; [05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 2) | A few tens of float operations | Cases in general position |
| 5. Exact | The fixed-width integer evaluation of section 6.2: `i128` for orientation, 256 bits for circle and sphere tests, at most 384 bits for plane-based tests | A fixed sequence of wide multiplies: no allocation, no loop, no rounding mode | Everything left, including every exact zero that steps 1 to 3 did not catch |

Section 6.2 said every predicate starts with its filter. Steps 1 to 3, and switching a filter off where measurement shows it does not pay, are now part of 6.2 (owner action G121, 32.22), on two conditions: every step is tested against the exact path, and a filter is switched off only per target, at build time, where the count benchmarks show it loses. Every step returns the same sign, so the amendment changes speed only. Programs should align a building's project frame with its main grid, so that most walls take step 3.

- **Filters on rounded inputs.** At B = 40, plane normals need up to 83 bits and offsets up to 125 bits ([05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 4), so their `f64` copies are rounded. Meyer and Pion's bounds assume exact inputs, and a bound that ignores input rounding can certify a wrong sign. The generator therefore marks every input converted from a wider integer as rounded (|x̃ − x| ≤ 2^-53·|x|) and adds that error to the bound. Tests put coefficients at their full 83-bit and 125-bit widths with results near zero.
- **Widths beyond 384 bits in code.** `geom-num`'s `I512` total path and `geom-math`'s exact stages up to 2,560 bits (6.2) are outside this cost model until an owner accepts them (31.7). Grid input never reaches the total path, so it costs nothing there; the cost of `geom-math`'s exact stages is unmeasured.
- **Fixed width makes the exact path affordable.** EMBER's plane-based booleans take 1.6 ms per boolean (geometric mean over 1,000 Thingi10K pairs of 1,000 to 100,000 faces) and run 5.5 times faster on 8 cores, with 26-bit inputs and at most 256-bit arithmetic ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 5). Spare Kit's 40-bit inputs need up to 384 bits in the deepest tests: six 64-bit limbs instead of four, so each schoolbook product costs about (6/4)² ≈ 2.25 times as much (derived). Only the deepest plane-based tests pay that. Our arithmetic follows EMBER's.
- **Whether to filter is measured, not assumed.** On x86-64 and aarch64 the `i128` orientation test is a short run of hardware multiplies, so on zero-heavy data its filter may not pay for itself. The 384-bit tests, and every wide multiply on WebAssembly, cost far more, and there the filter earns its keep (derived; measured as in 23.3).
- **Every step is counted.** Debug and benchmark builds count which step settled each call, per corpus (buildings, mechanical parts, near-degenerate fuzz input), so the mix is measured, not hoped for. These counters are statistics only, not the work units of 23.10.

Shared canonical planes also serve section 11: two operands on the same plane give the arrangement one plane, not two nearly equal ones.

## 23.3 Wide integers on WebAssembly

WebAssembly's 64-bit multiply returns only the low 64 bits. Rust's `i128` multiply therefore becomes a call to a library routine, `__multi3`, whose result travels back through memory ([Overview L76-L82](https://github.com/WebAssembly/wide-arithmetic/blob/024d4ce1b28cee7fd006d9c5175e3b7ece52b429/proposals/wide-arithmetic/Overview.md#L76-L82)). The wide-arithmetic proposal measures 128-bit arithmetic at 2 to 7 times slower than native ([L26-L28](https://github.com/WebAssembly/wide-arithmetic/blob/024d4ce1b28cee7fd006d9c5175e3b7ece52b429/proposals/wide-arithmetic/Overview.md#L26-L28)). It adds `i64.mul_wide_s`, `i64.mul_wide_u`, `i64.add128` and `i64.sub128`, and is at phase 4 ([proposals L25-L31](https://github.com/WebAssembly/proposals/blob/df6a2aca1cd9d779eb4f2f3e19dae8277f336015/README.md#L25-L31)). Its implementation list names Wasmtime, SpiderMonkey (Firefox), JavaScriptCore (Safari), LLVM and Rust, but not V8 (Chrome, Edge, Node) ([L280-L299](https://github.com/WebAssembly/wide-arithmetic/blob/024d4ce1b28cee7fd006d9c5175e3b7ece52b429/proposals/wide-arithmetic/Overview.md#L280-L299)). Which browsers ship it switched on by default is unverified.

The plan:

- **Width-aware exact code.** The generator that writes each predicate's filter (section 6.2) also writes its exact path. It knows every intermediate's width from the predicate's written bit budget, so it picks the cheapest product for each step. A 41-bit by 41-bit product, for example, needs two 64-bit multiplies (one operand split into 20-bit and 21-bit halves), not a general 128-bit multiply (derived; to be measured).
- **Four variants compared:** plain `i128` through `__multi3`; the generator's width-aware limbs; the wide-arithmetic instructions; and, as a reference, the method of Avnaim, Boissonnat, Devillers, Preparata and Yvinec, which finds the sign of small determinants of b-bit integers using only b-bit arithmetic ([doi:10.1007/BF02522822](https://doi.org/10.1007/BF02522822)).
- **Measured on** x86-64 and aarch64 natively, and wasm32 in Wasmtime, Node, Chrome, Firefox and Safari: each predicate's steps alone, then inside whole operations (a 300-opening wall cut, the 2,000-wall regeneration).
- **Decision rule:** each target ships its fastest variant. The browser package is built with and without wide arithmetic, and the page loads the one its engine supports.
- **Generated code is proven, not trusted.** Integer arithmetic has one right answer, so every correct variant gives the same sign on every target; unlike floating point, the choice of instructions cannot change a correct result. But generated limb code is new code that can be wrong, and Rust release builds wrap silently on overflow, so a wrong bit budget would give a wrong sign. Therefore the generator writes a bit-range certificate for every intermediate, and an independent checker re-derives it; Kani proves each generated limb step free of overflow within those ranges ([08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md) section D; whether Kani can also prove whole 384-bit predicates in reasonable time is unverified); `geom-num`'s CI release runs switch overflow checks on; every variant is tested at the extreme values (every coordinate at ±(2^40 − 1)); and the differential fuzzer checks every variant against a rational oracle (`num-bigint` and `num-rational`, or `dashu`, all MIT OR Apache-2.0; section 29.3).
- **`geom-num` already goes further (G02).** Its lints deny native arithmetic and lossy casts in kernel code (`clippy::arithmetic_side_effects`, `cast_possible_truncation`, `cast_possible_wrap` and `cast_sign_loss`), every fixed-width step is a checked method, each bit budget is asserted at compile time, and a total path or `BudgetExceeded` backs every budget (6.2). So no build profile can change an answer, and CI runs the golden digest in release both with overflow checks on and as shipped, without them. On stable Rust there is no widening or infallible multiply without native or wrapping operations (`u64::widening_mul` is unstable in Rust 1.99), so the plain-`i128` and width-aware-limb variants above would break that lint rule unless each site is allowed with its written bound, or their Kani certificate stands in for the check. Which rule governs generated code is open (31.7).

## 23.4 Deterministic parallelism: one helper

Parallel code is where determinism usually dies. Rayon's float sums and folds have no fixed order ([05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 7), and Manifold accepts races in its parallel builds and does not promise the same result across machines ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 3). Spare Kit has one parallel helper, and it is the only kernel code that may spread work over threads.

**Where it lives** (27, accepted in 32.13). `geom-num`'s one job is numbers, so the helper goes in a crate of its own in the bottom layer, `geom-run`: `no_std`, depending on nothing, holding the helper, its serial executor, the budgets, the work meter and the cancellation trait of 23.10. `geom-num` depends on `geom-run`, because its work-list engine charges work and checks cancellation (12.3). Kernel crates are `no_std` (section 21) and cannot start threads. So threads come from a small `std` adapter crate, `geom-pool`, in layer 13 beside the facade. It is the executor crate that 29.4's rayon row describes: it implements the `Pool` trait over rayon on native targets and over Web Workers (wasm-bindgen-rayon) in a browser that allows shared memory. `engine-geometry` depends on it only behind its `threads` feature, which is off by default, and may use `std` because it holds no kernel logic (27). A program that wants threads turns that feature on and passes its pool in with each call, as it passes its `Cancel` (23.10). So no kernel crate below the facade ever has rayon in its dependency graph, and neither does a default build of the facade. wasm-bindgen-rayon has its own row in section 29.4. With no pool, the helper runs the same chunks one after another, and the answer is the same. The adapter this section first proposed, `engine-geometry-pool` in `projects/engines/crates/` beside a `no_std` facade, is withdrawn.

```rust
// geom-run, as built in G04 (abridged; lifetimes and where-clauses left out)
pub trait Pool: Sync {
    /// Run every task exactly once, on any threads, in any order. Re-entrant:
    /// a task may call the helper again without blocking a thread.
    /// Must not panic, except to pass on a task's panic.
    fn run_all(&self, tasks: &mut [&mut (dyn FnMut() + Send)]);
}
pub struct Exec<'p> { pool: Option<&'p dyn Pool> } // None: serial, same answer

impl Exec<'_> {
    /// out[i] = f(i, &items[i], meter), in input order, as one phase of `meter` (23.10).
    pub fn map<T: Sync, U: Send>(&self, meter: &mut WorkMeter, phase: Phase, plan: ChunkPlan,
        items: &[T], f: impl Fn(usize, &T, &mut WorkMeter) -> Result<U, Stopped> + Sync)
        -> Result<Vec<U>, RunError>;
    /// The same with the function's own error: the lowest-numbered failure is reported.
    pub fn try_map<T: Sync, U: Send, E: Send>(&self, meter: &mut WorkMeter, phase: Phase,
        plan: ChunkPlan, items: &[T],
        f: impl Fn(usize, &T, &mut WorkMeter) -> Result<U, E> + Sync)
        -> Result<Vec<U>, RunError<E>>;
    /// A batch call (23.10): every item runs under its own budget, one result per item;
    /// a batch total is summed in the order of the caller's keys. Takes no meter.
    pub fn map_each<T: Sync, U: Send, E: Send, K: Ord>(&self, budget: BatchBudget,
        cancel: Option<&dyn Cancel>, phase: Phase, plan: ChunkPlan, items: &[T],
        key: impl Fn(usize, &T) -> K + Sync,
        f: impl Fn(usize, &T, &mut WorkMeter) -> Result<U, E> + Sync)
        -> Result<Vec<ItemResult<U, E>>, Interrupted>;
    // Also: find_first (the first match in input order, never "any" match);
    // filter_ordered (kept items in input order); scan_exclusive (prefix sums of integers);
    // sort_stable (by a total key: one answer whatever the chunks); and count_then_fill
    // (each item counts its outputs, then writes them at fixed offsets).
}
```

The rules, each enforced in code or CI:

- **Whatever the pool does, the answer is right.** A task run twice writes its result once, and a task the pool never ran is run on the calling thread when its result is read. A pool must not panic except to pass on a task's panic, and the helper neither catches nor wraps one (G04).
- **Fixed chunks.** A `ChunkPlan` is a constant chosen at each call site for the cost of one item, for example 64 items for boolean cells and 4,096 for point evaluations. It never depends on the thread count, core count, cache sizes or timing.
- **Ordered results.** Each chunk writes only its own slice of the output, so output order is input order. New entities get arena indices by `count_then_fill`: each item counts what it makes, an exclusive scan turns counts into offsets, and each item fills its own range. Indices are then in input order on any number of threads. Atomic ID counters are forbidden, as is the global counter that makes Manifold's mesh IDs depend on scheduling ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 2).
- **Ordered errors.** When an item fails, only higher-numbered items may be abandoned; lower-numbered ones still run. The error reported is always the lowest-numbered failure, the one a serial loop would hit first. `find_first` follows the same rule, as rayon's `find_first` does ([mod.rs L1675-L1680](https://github.com/rayon-rs/rayon/blob/ee0a00bdb1ab039e178a215ad5712fb7fa58e58f/src/iter/mod.rs#L1675-L1680)).
- **Every combine is order-free.** Integers (twice-areas, six-times-volumes, counts, work units) are added in accumulators whose width is written down so that no partial sum can overflow; then any order gives the same total. For example, twice-area terms of 40-bit coordinates are at most 2^81, so an `i128` holds the sum of up to 2^32 of them (derived). Minimum and maximum use section 21's total-order helpers, with ties broken by persistent name. Connected components (as in Manifold's winding-number pass, [01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 1) are labelled by their lowest-numbered member, through rounds of min-label propagation or a serial pass; both give the same labels. Concurrent union-find is forbidden. Tree-building costs, such as a bounding-volume hierarchy's surface-area cost, are integers.
- **Float sums whose order could vary go through `ExactSum`.** Any float reduction whose combine order depends on chunking, threads or container order uses `ExactSum`, a superaccumulator in `geom-num` (G25): a wide fixed-point number that holds the exact sum of doubles and rounds once at the end, an exact zero to +0. It is exact while the sum's magnitude stays below 2^1100, which allows at least 2^64 terms (each term counted once for every accumulator it reaches through merges); past that the sum is marked lost, and rounding reports it, never a wrong value. The method is Neal's ([arXiv:1505.05571](https://arxiv.org/abs/1505.05571)), who reports exact summation of large arrays in under twice the time of plain ordered summation; Demmel and Nguyen address the same need for parallel sums ([doi:10.1109/TC.2014.2345391](https://doi.org/10.1109/TC.2014.2345391)). Merging two superaccumulators is integer addition, so this is not a float reduction across chunks in section 21's sense. Sums in a fixed written order, such as NURBS basis sums and Horner steps, are already deterministic and stay plain. The helper offers no float reduce, and the kernel's `disallowed-methods` list bans `Iterator::sum` and `Iterator::product`, so every collection sum goes through `ExactSum` or a documented integer helper. For a collection, use `collect::<ExactSum>()`, `extend` or `add_iter`, or `add_slice` for a slice: from 512 terms these run Neal's large accumulator and stay within twice a plain ordered sum on a quiet machine (1.68 times at worst over 10^6 terms, G25). `ExactSum::add`, one term at a time, uses only the small accumulator and costs 3 to 6 times a plain sum. The large accumulator lives on the stack for one call, 41 KB, because `geom-num` has no heap (31.7, chapter 28).
- **Chunk boundaries never matter.** Because every combine is order-free, no result depends on where chunks start and end, which is stronger than section 21 asks. Chunk sizes can therefore be retuned for speed without a new kernel edition.
- **One pool, two levels.** The program's per-element work and an operation's inner work share one pool, which must be re-entrant (work-stealing pools such as rayon are). An operation splits inner work only above a fixed item count (Manifold stays serial below 10,000 elements for the same reason; [01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 3), so the many small operations of a regeneration run serially inside and in parallel across elements.
- **Tested where it matters.** The replay corpus runs with 1, 2, 3 and 8 threads on every target (section 21). On one native and one WebAssembly target it also runs with chunk sizes forced to 1, 7 and 4,096 and with every parallel threshold forced to 0, so the parallel paths really run on small corpus models. Every run must give identical hashes. On wasm32 the thread-count runs are skipped or run on one thread until a threaded WebAssembly target is tested (21). As built (G33): `geom-pool` adapts rayon 1.12.0 on native targets (`geom_pool::native::Rayon`: a pool of a fixed number of threads, `Pool::run_all` spawning each task into one `in_place_scope`), and its `tests/attack_g33.rs` holds every helper to the serial answer on rayon pools of 1, 2, 3 and 8 threads at chunk sizes 1, 7, 64 and 4,096, and the pool to its contract: every task once, re-entrant on one thread, a task's panic passed on. rayon's audit is `projects/kit/notes/G33-rayon-audit.md`. Every kernel crate's `clippy.toml` now bans std's thread-starting functions and `available_parallelism`, rayon's global and self-scheduling entry points, and the six atomic integer types a counter would use; `geom-pool`, built with the same file, uses only what stays allowed. The browser's workers are piece G456's.

**In the browser.** WebAssembly threads need shared memory, which browsers allow only on cross-origin-isolated pages, and Rust's threaded WebAssembly build needs a pinned nightly compiler that rebuilds the standard library ([wasm-bindgen-rayon README L25-L46, L106-L145](https://github.com/RReverser/wasm-bindgen-rayon/blob/4eea1fa55a965ad516ef9f9e9449704c7eac91c5/README.md#L25-L145), Apache-2.0). Until that reaches stable Rust, the browser runs the kernel serially in a Web Worker, or in a separately built threaded variant (section 32). The answer is the same bits either way.

## 23.5 Regenerating many elements at once

The regeneration graph belongs to the program (Spare Construct's engine, in the style of Salsa). The kernel makes parallel regeneration safe and cheap:

- **No shared state.** Every operation is a pure function of immutable values that are safe to share between threads. There is no global state, no lock and no cache inside the kernel. New persistent names (section 20.1) come back in each `OpOutput` as name nodes; the caller merges them into the document's name graph in element order. Merging is order-free anyway, because a `NameId` is a hash of the node's content: the same node interned twice is one node.
- **Results depend on the authored operations and current inputs, not on the order of edits.** Names contain the `OpPath` of the operations that made them, and an `OpId` is fixed when the operation is authored (section 20). So two people who reach the same parameters through different edits of the same authored operations get the same bits. The kernel's part is that n-ary operations sort their operands by persistent name inside, so a result never depends on the order a caller passes them. Keeping each host's uncut body and re-cutting it with its current cutters is the program's choice, which [08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md) section B recommends.
- **Waves.** Programs schedule regeneration in waves: wall bodies, then joins at each junction, then openings. Inside a wave items are independent and go through the shared helper. Results are published in element order.
- **Early cut-off.** When a regenerated body has the same content hash as before, nothing downstream of it re-runs (Salsa's backdating; [07](../../../kit/notes/G01-evidence/07-persistent-naming.md) section 7). In a level change, walls whose geometry turns out unchanged stop there.
- **Local re-cut.** Re-cutting a host from its uncut body costs work for all its openings, so a door move on a curtain wall with 300 openings would re-run 300 cutters. For such hosts `geom-bool` re-runs the arrangement only in the cells touched by the changed cutter's old and new boxes, and keeps the rest. That is exact only if a cell whose contents did not change produces exactly the same pieces. It does when cells split at fixed grid positions, whatever they contain, as an octree on the grid does (octree-embedded BSPs: Nehring-Wirxel, Trettner and Kobbelt 2021, [01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 5; whether their code splits this way is unverified), and when the output is assembled in persistent-name order. Then local and full re-cut give the same canonical encoding (derived). CI compares the two on every corpus model, and the full re-cut stays the reference. The evidence reports describe no published method that promises this equality, so it is new work; whether section 11's engine splits cells this way is an open question.

## 23.6 Batch, n-ary and preview operations

- **Batch calls** (section 10.1). One call takes many inputs and returns one result per item. Shared setup, such as the host's box tree and plane table, is done once. One failed panel out of 10,000 fails only itself ([09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md) section 5), and that includes running out of its own budget (23.10). Item i's `OpPath` is the batch's `OpPath` plus the item's own key (given by the caller, for example the panel's ID), so a batch and the same calls made one by one give identical names and bits. A test checks that.
- **Evaluation in structure-of-arrays form.** Curves, surfaces and fields evaluate N parameters per call, from and into flat arrays (all u values, then all v values). The compiler can then use the processor's vector units with no hand-written SIMD. This cannot change results: each lane does the same IEEE operation as scalar code, Rust never reorders float arithmetic unless asked ([05](../../../kit/notes/G01-evidence/05-exact-arithmetic-determinism.md) section 7), and relaxed SIMD stays off.
- **N-ary booleans.** Union, subtract and intersect take any number of operands in one arrangement (section 11). Each piece is kept or dropped from a vector of winding numbers, one per operand: EMBER's generalised winding-number vectors ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 5) and the idea behind Manifold's `BatchBoolean` ([09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md) section 5). The vectors are sparse and local: a cell holds entries only for the operands present in it, so a 1,000-operand union costs what its cells touch, not cells times operands. Cutting 300 openings is one pass over the wall, not 300 passes over a growing result.
- **Preview precision.** `OpContext`'s precision level (section 10.1) lets an interactive drag ask for a preview: curved constructions fitted to a coarser bound and tessellation at screen error. A preview result carries its true class and bound, is cached under its own key, and is never stored as final. Flat-faced work has no preview, because it is exact and already fast.

## 23.7 Spatial culling

Most of a boolean's work is finding which faces could meet.

- **Boxes that never miss.** Every face, edge and body carries an integer box on the grid, and overlap tests are exact integer comparisons. How much a box is padded depends on the entity's exactness:
  - Exact: no padding.
  - Certified(ε): the box of a certified enclosure (the control-point hull, which holds the curve only when every NURBS weight is positive, or interval bounds), inflated by ε and rounded outward to whole grid steps, because the true shape lies up to ε from the stored one (section 9).
  - Tolerant import bodies: inflated by each entity's tolerance, because operations must work within it (section 6.5).
  - Implicit vertices: each coordinate's `f64` filter value plus its error bound, rounded outward to the grid.
- **A box tree low in the stack.** A small, deterministic tree of integer boxes, 2D and 3D, has its own crate in layer 2, `geom-bvh`, on `geom-run`, `geom-num` and `geom-math` (27, accepted in 32.13). `geom-bool`, `geom-intersect`, `geom-2d` and `geom-mesh` use it without depending upward on `geom-spatial`, which builds mesh queries, distance and clash on top of it. `geom-terrain`, `geom-draw` and `geom-field` use it too. The tree is built top-down with integer surface-area costs and ties broken by index, in parallel through the helper.
- **Ordered work.** Candidate pairs are sorted by index pair before the narrow phase, as Manifold sorts its pairs ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 1), so the order of work never depends on traversal or threads. Traversals are iterative, with explicit stacks of capped depth (principle 13).
- **Local arrangements.** The arrangement is computed only in cells where faces actually meet, following EMBER's adaptive subdivision ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 5).
- **Never all pairs.** Truck visits every pair of faces of the two solids, though each pair then uses triangle sweep-and-prune and box rejection ([11](../../../kit/notes/G01-evidence/11-vetting-suggested-projects.md), Truck). A review rule forbids all-pairs loops in Spare Kit.
- Programs ask the same index "what touches this wall", "what is in this view" and "what can this duct clash with", so a local edit costs local work.

## 23.8 Caching by content

Caches skip work already done. They belong to the caller, never to the kernel (principle 7: no global state). The kernel's job is to make every cache key exact, so that a hit is the same bits as recomputing:

```rust
/// Hash of: kernel edition; operation name and version; the OpPath; the precision
/// level; and the canonical encoding of every input, frames and grid steps included.
struct CacheKey([u8; 32]);
struct CacheEntry {
    result: Result<OpOutput, OpError>, // deterministic errors are cached too
    trace: BudgetTrace,                // work and logical bytes at each phase boundary (23.10)
}
```

- **The `OpPath` is in the key,** because every name an operation creates contains it (section 20.2). Two identical facade panels are two operations, and their faces have different names. Reuse across operations is allowed only for operations whose schema says their geometry does not depend on names. Their name-free entry is keyed by the inputs' geometry without names, stores its result's names with the operation and the input names left blank, and a pure function `restamp(entry, op_path, input_names)` fills them in and recomputes every `NameId`.
- **The budget is not in the key; it is checked on every hit.** The entry stores how much work and logical memory each phase used. On a hit, that trace is compared with the caller's budget, and a caller whose budget is too small gets exactly the `BudgetExceeded` a fresh run would give. An entry made by a run that failed on its budget answers only calls whose budget is no larger. `Cancelled` and `OutOfMemory` are never cached.
- **Content hash.** A body enters a key by its content hash, which is its content ID from section 24.2: the SHA-256 root of a hash tree over the canonical bytes of its index and its chunks, each table cut into fixed runs of 4,096 rows and written in arena order (24.3). There is one scheme, and section 24 defines it. Arena order is fixed by the operation and its inputs (`count_then_fill`, 23.4; operands sorted by name, 23.5), so the same inputs give the same hash on every machine. Chunk boundaries never depend on what memory a body shares with an earlier version (23.9), and a new version rehashes only the chunks it changed. Equal encodings, not merely equal shapes: the same shape built another way, or with different names, gives a different key, as it should.
- **Edition and version in every key.** A result made by an older kernel edition or operation version is never reused after an upgrade (section 26.2). Preview and final results have different keys.
- **What callers cache:** operation results with their names and history; tessellations per body and level of detail; sections and projections per element and view ([06](../../../kit/notes/G01-evidence/06-2d-drafting.md) section 6); box trees per body version.
- **Why it is sound.** Content-addressed caching is only sound when operations are deterministic ([09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md) section 5). Determinism also makes concurrency harmless: two threads that compute the same key store the same bits.
- **Who owns what.** `geom-format` owns the canonical bytes (24.2, 24.3), so it also owns what is built on them: content hashes, `CacheKey`, assembled from those hashes and the other fields listed above, and a reference memo store, bounded by bytes, which the caller creates and owns (27, accepted in 32.13). It holds 24.3's deterministic CBOR rules and the content hash (written in safe, portable Rust, as principle 13 requires), adds the record layer (tags, flags, dependencies, checksums), containers and versions around those bytes, and never encodes a value a second way. The bottom-layer `geom-bytes` this section first proposed is withdrawn, and `engine-geometry` holds none of this logic (27). `geom-bool` (11.6), `geom-draw` (18.9) and `geom-spatial` (19.11, 19.12) key their own reuse values by content hash but sit below `geom-format`, so they cannot compute one themselves; how the hash reaches them is raised for 31.7.
- **Audit.** CI recomputes a sample of cache hits, restamped ones included, and compares the bits, names included. Any difference is a determinism bug.
- **As built (G105).** `geom-format`'s `cache` holds `CacheKey`, `CacheEntry`, the `MemoStore` (forgetting the entry used longest ago first, by a clock that counts calls) and `restamp`; `body` holds `BodyVersion`.
  - *The trace* is the run's budget and what it used, not a sample at every phase. A stored answer hits when the caller's budget covers what the run used, since a run stops only when a charge passes its cap and charges only add. A stored budget failure hits only under the same budget, narrower than "no larger" above: a smaller budget stops the run sooner with other numbers, and only the run's full sequence of charges could say which, so that call misses and its own run gives the exact failure.
  - *Name-free reuse* is a field of the schema, `name_free`; `CacheKey::name_free` gives no key without it. A body enters such a key by `BodyVersion::geometry_id`, the root of its hash tree without the name tables. Arena order comes from names (32.17), so equal geometry in another order has another ID: a miss, never a wrong hit.
  - *`restamp`* fills in the blanks (`BLANK_OP`, `Stamp::blank_input`) through `geom_op::Stamp`, name by name in the order the run made them, refusing anything not blank or not stamped yet, then publishes a body again so its arenas take the new names' order. Results take part through the trait `Restamp`; `NamedBody` is the first, and the first operation that sets `name_free` adds its own result, with its history. A stored error holds paths and names only the run knows, so it misses.
  - *Rehashing only what changed.* `BodyVersion::next` reuses a chunk's ID where every column of the chunk is the very chunk the version before holds, and `Builder::publish_named` keeps the input's chunk wherever a chunk comes out unchanged, so this holds for named bodies. Its one use of an address, `Column::shares_chunk`, answers only whether two handles are one chunk: it orders nothing and cannot reach the content hash (21). An operation that inserts a row in name order shifts the rows after it, and those chunks are hashed again (32.45).

## 23.9 Memory layout

- **Structure of arrays.** Each entity kind in a body's arena (section 8.2) is stored as columns, one per field: all face boxes together, all fin links together, as Manifold stores its halfedges ([01](../../../kit/notes/G01-evidence/01-manifold-mesh-booleans.md) section 2). A broad phase reads only boxes and a loop walk reads only links, so less memory moves. This is a requirement on section 8's arena piece, so the layout is in place before any operation is built on it.
- **Chunked bodies.** Columns are split into fixed-size chunks shared between versions. Editing 10 faces of a terrain of a million triangles copies a few chunks, not the body. Parallel chunks follow storage chunks. Chunk sharing is a memory detail that never reaches the content hash (23.8).
- **Compact planes.** Faces on one plane share one canonical entry (23.2). Coefficients are stored at the narrowest width that holds them (`i64` or `i128` each), with an `f64` copy for the filters, made once when the plane is made. Memory for plane storage at building scale is not yet measured (section 31).
- **Shared geometry, placed many times.** A shared body (a definition, in 19.12's word), such as a door, a fitting or a bolt, is stored once in its own frame, with its display meshes and levels of detail. Instances never copy it. The kernel has one instance record, 19.12's `Instance`, and 19.12 is the only place it is defined, with the crate that owns it and the instance tree that indexes it. It holds the instance's persistent `InstanceKey` (mapped at the facade from kit-core's permanent IDs), which definition, the frame and the placement; its integer box is held once, in the tree's leaf. The key is what lets a clash outcome (19.11) or a reference into an insert (14.10) say which instance it means. The record's memory, about 140 bytes per instance with its share of the tree, is counted in 19.12 and is the kernel's share in 23.1. The table of definitions belongs to the caller. Nested assemblies are instances in the same tree (19.12); the mates that move placements belong to the `geom-assembly` toolkit (15.15).
- **What a placed body is.** An instance's geometry is defined as its materialisation: the shared body made into its own body by the placement. For exact placements (grid shifts, quarter turns, mirrors), queries move the question into the shared body's frame exactly and answer it there, which gives the same answer as on the materialised body. For other rotations, the materialised body is rounded to the grid as section 7 says, re-validated, and labelled with its class; queries use it, made lazily into a caller-owned cache keyed by the shared body's content hash and the placement. A property test checks that every query on an instance equals the same query on its materialisation.
- **Memory is measured,** not guessed: bytes per wall body, per instance, per million triangles, and per operation. The logical bytes of 23.10 are the same on every machine; real peak bytes are measured per target with the pool off (23.13). As built (G80): a plain wall body (two regions, one shell, six planar faces, 24 fins, 12 line edges, 8 vertices) holds 16,740 heap bytes in 29 chunks on 64-bit targets and 15,024 on wasm32, beside the body's own 976 bytes (492; 968 and 488 before G81 added the names); its six planes (1,008 bytes a row) and twelve lines (592, 536 on wasm32) are most of it, because a pool row is the size of its kind's largest variant, while its topology rows take 1,308 bytes (`geom-topo`'s `body.rs` and `tests/attack_g80.rs`).
- **The browser's ceiling.** wasm32 can address at most 4 GiB, and a threaded build fixes its maximum memory when it is built (the wasm-bindgen-rayon example declares 1 GiB; [README L128-L145](https://github.com/RReverser/wasm-bindgen-rayon/blob/4eea1fa55a965ad516ef9f9e9449704c7eac91c5/README.md#L128-L145)). The browser kernel holds only the chunks in view and streams the rest, under a working-set budget fixed per build.

## 23.10 Budgets and cancellation

Every operation runs inside the budgets its `OpContext` carries (section 10.1):

```rust
// geom-run (sketch)
pub struct Budget { pub work: u64, pub logical_bytes: u64 } // fail the same way on every machine
pub struct BatchBudget { pub per_item: Budget, pub total: Option<Budget> } // batch calls (10.1)
pub struct WorkMeter { /* counts one item's work units and logical bytes, and polls Cancel */ }
pub trait Cancel: Sync { fn requested(&self) -> bool }      // the caller's: a flag, a deadline, a button
// As built in G04, a budget failure also says which limit, and counts in u128:
pub struct Exceeded { pub budget: Budget, pub kind: BudgetKind, pub phase: Phase, pub used: Usage }
```

- **Work units count only what fast paths cannot change.** An operation charges for quantities fixed by its definition and its output: input and output entity counts, pairs of overlapping integer boxes (a mathematical count, whatever culling finds them), and iterations of numerical methods whose iterates decide the output bits (Newton steps, certified subdivision levels). It never charges per predicate call, filter step, cache probe, tree node visited or allocation. Shortcuts, filters, caches, culling and pools therefore cannot change a count, and reference mode (23.13) counts the same. The charge schedule is part of each operation's version (section 26.2). The replay corpus stores golden counts, and a count that changes without a version bump fails CI.
- **Logical memory.** The memory budget counts the total logical bytes an operation reserves, from entity and scratch counts at fixed sizes per kind. Those sizes do not depend on pointer width, the allocator or the thread count. It is a total, not a peak, because a peak depends on how many chunks run at once. As built (G98): `geom-make` reserves 64 logical bytes for every row it builds or copies, beside the row's work unit; before that the Make and Transform families charged no logical memory, so no memory budget could stop them.
- **Checked at fixed phase boundaries.** In a phase with remaining budget R, each item runs with a cap of R. The phase fails with the lowest-numbered failure of any kind: an item's own error, or an item over R. Otherwise, if the items' total exceeds R, it fails with `BudgetExceeded` at the end of the phase. Otherwise R falls by that total. Serial and parallel runs compute exactly this. The count reported is what a serial loop would see: items above the failing one count zero. A total over R can be decided only after every item of the phase has run, because a later item's own error must still win. So a phase of n items, each under R, may do up to n × R work before it fails: the budget bounds a phase's work by its item count times R, not by R, and a huge phase of cheap items is stopped only by cancellation or by an item over R on its own (G04). Whether phases need a size limit is open (31.7).
- **Batch calls: one rule, defined here.** The phase rule above governs the parts of one operation. A batch call with one result per item (10.1, 23.6) is many operations, and carries a `BatchBudget`. Each item runs through `map_each` under its own `per_item` budget and the phase rule, so whether an item passes never depends on how many other items the batch holds or what they cost. If the caller also sets `total`, the work and logical bytes the items used are summed in item-key order once they have run. The item at which the running sum first passes `total`, and every item after it in key order, fail individually with `BudgetExceeded` naming the batch total; the items before it keep their own results. Serial and parallel runs give exactly this, and a parallel run may abandon items it already knows lie past that point. A batch-total failure belongs to the batch, not to the item, so it is never cached as the item's result. No batch divides its budget into equal shares, because then adding one unrelated item could make another fail. The rule applies to every batch, including 10.1's batch calls, 12.15's intersection pairs and 19.11's clash pairs. In `geom-run` (G04) an item's result is its value or an `ItemError`: `Failed`, `BudgetExceeded` (its own budget) or `BatchTotal`; a batch the caller cancelled or the machine refused returns `Interrupted` (`Cancelled`, `OutOfMemory` or `Internal`), and then no item has a result. `map_each` takes the caller's keys and no meter: it is only the top level of a batch, so called inside an item it would neither charge nor stop that item's meter, and code inside an item uses the calls that take a meter. An item over its `per_item` budget is reported under the batch's phase name, even when a phase nested inside the item failed. Items with equal keys are taken in input order, so a repeated key would make the batch-total failures depend on input order, which 10.1 rules out; so `geom-op`'s batch driver, which every batch entry uses, refuses a repeated key as `InvalidInput` before any item runs, and `map_each` keeps its order rule for callers that check keys themselves (G104; 31.7).
- **So budget failures can be model state.** `BudgetExceeded { budget, kind, phase, used }` is the same on every machine, thread count and build mode, and may be stored ("this fillet exceeded its work budget") without breaking replay. `kind` says which limit was passed, work or logical bytes; work is checked first when both are. `phase` is a name, not a number, so a stored failure reads the same in every build. `used` is what a serial loop would count: for a phase, everything before the phase plus the items up to and including the failing one; for a batch item over its own budget, that item's use; for a batch total, the items' use summed in key order up to and including the item at which the total was passed. It holds `u128` counts, because totals of `u64` charges can pass `u64::MAX` (G04). A budget that can fail an operation in a shared model is fixed by the operation's version or recorded in the log, never set per machine. G23 attacks these rules in `geom-run`'s `tests/attack_g23.rs`: seeded property tests that a phase or a batch gives the same result, the same `Exceeded` record and leaves the same use and stop on the serial executor and on thread pools at every chunk size, and that under per-item budgets each item gets exactly the result it gets alone; hand-worked cases of the phase cap, the lowest-numbered failure, the end-of-phase total and the key-order batch total; exact logical bytes per kind; and the meter asking the caller's `Cancel` exactly every `POLL_EVERY` charges.
- **Real memory is different.** Large allocations (arenas, scratch buffers) reserve fallibly, and a refusal returns `OutOfMemory`. Like `Cancelled`, it is never written to the log or stored, and nothing is published. Small allocations cannot fail softly in Rust: the standard handler prints a message and aborts ([alloc.rs L644-L657](https://github.com/rust-lang/rust/blob/19833af7224424e8b53e288097d56b6af43d5bcf/library/alloc/src/alloc.rs#L644-L657)). The logical budget keeps operations far below real memory, so this happens only when the whole machine, or the browser's memory, is exhausted.
- **Time belongs to the caller.** The kernel reads no clock (section 10.1). A time limit is a deadline that the caller's `Cancel` turns into a cancellation. Cancellation is the only stop that is not deterministic, and it can never affect the model: a cancelled operation publishes nothing.
- **Polling.** The work meter and long inner loops read the cancellation flag at fixed intervals: one atomic load. Target: an operation stops within 1 ms of cancellation on native targets. `geom-run` reads the flag every 64 charges (`POLL_EVERY`) and before each chunk (G04). Its one measurement, taken while other builds held the CPU at 100%, gave a median of 1.8 µs from cancellation to stop and a worst case of 3.5 ms, over the target. G83 measures it through the operation contract (`OpContext::run`, `geom-op`'s `tests/attack_g83.rs`): an operation charging one unit a step, cancelled from another thread, stopped in a median of 2.1 µs and at worst 5.4 µs over 51 runs on a development machine with other builds running, and the test holds the median under 1 ms. Whether 64 suits costly items is unmeasured (31.7). Cancellation is cooperative and never unwinds, because WebAssembly builds cannot catch an unwinding panic (section 10.1; [07](../../../kit/notes/G01-evidence/07-persistent-naming.md) section 7).
- **In a browser.** A deadline needs no shared memory: the caller's `Cancel` inside the worker reads the clock itself. Only a person's cancel button, on a page without cross-origin isolation, cannot reach a running worker, so the page ends the worker. That discards everything the worker holds (decoded chunks, name graphs and caches), not only the operation. The program reloads the chunks into a new worker from the main thread's copy, which costs about the open share for those chunks. It is expected only when a person stops a long global edit by hand, and its cost is measured (23.13).
- **Errors say what to do** (section 22): which budget, the phase, the work used so far, and remedies such as preview precision or a smaller batch.

## 23.11 Opening fast and safely

- **Display data is stored.** Section 24 must store display meshes and levels of detail per shared body and per element, each with its deviation, its exactness class and the kernel edition that made it. Without them a cold open would tessellate every element in view: at an estimated 20 to 100 µs per flat-faced element, 230,000 elements take about 5 to 25 s of kernel time, or about 1 to 4 s on 8 cores (derived), over the share.
- **Levels of detail are honest.** A simplifier's error is an estimate, so a level of detail is Approximate(ε) with a measured ε, unless its distance to the source is bounded by interval arithmetic, triangle by triangle, which makes it Certified. Levels of detail are display data, never operation inputs. The simplifier is ported to Rust from meshoptimizer's method (MIT; [08](../../../kit/notes/G01-evidence/08-standards-coverage-testing.md) section C) so that it is deterministic, because its output is stored and audited.
- **An edition upgrade does not slow opening.** After an upgrade every cache key misses, but stored display data from an older edition stays usable, because it is labelled display data, not a result the model depends on. It is regenerated lazily in the background. Stored bodies are the model itself and open as they are (section 26.2).
- **Checks on open.** The cheap combinatorial check always runs, because it is what keeps the kernel's own loops finite. A content hash proves the bytes are intact; it does not prove they are valid, or who wrote them. Each chunk records the version of the checker that last passed it. If the reader's checker is newer, or section 24 cannot establish where the file came from, the geometric checks run lazily in the background, chunk by chunk, and findings become structured model warnings (section 22).
- **A bad chunk never stops the file.** A chunk that fails a check opens read-only. Its elements carry a structured error, and they are never used as operation inputs until they are healed; healing is an operation in the log. The rest of the file opens normally.

- Every change over 1% in the deterministic gates is listed in the run's summary and as annotations on the pull request's checks (G06). The jobs have read-only tokens, and pull requests from forks get no write token, so a comment on the pull request itself would need a separate trusted workflow (31.7).
- **Miss counts are judged through estimated cycles.** Instructions and estimated cycles are gated at 5% on every benchmark, whatever their size. A miss count is not gated on its own, at any size: every change in it is listed in the run's report, beside its benchmark's estimated cycles, and it is judged through them. Gungraun computes estimated cycles as L1 hits + 5 · last-level hits + 35 · RAM hits ([callgrind/mod.rs L110-L126](https://github.com/gungraun/gungraun/blob/a11cdc156da6134f281302f889c1d25fa44e00da/crates/gungraun-runner/src/runner/callgrind/mod.rs#L110-L126); instructions and data accesses, plus 4 per L1 miss and 30 more per last-level miss), so every miss is priced in them and no rise in what the misses cost can pass unseen. Miss counts are not gated because code and data layout alone move them, at every size, in benchmarks a change never touched. PR #212's aarch64 leg (run 40136795440) failed with I1mr and ILmr 2 → 3 on `exact_sum` benchmarks; a count below 20 cannot show a 5% change smaller than one event. G18a then gated miss counts of 20 or more at 5%, but its own first run, which changed only the gate's configuration and its build's dependency features, raised L1 misses on two `exact_sum` rounding benchmarks 4.7% and 6.9% on x86-64 (339 to 355, 218 to 233), instructions unchanged and estimated cycles up under 0.1%. Building the measured trees as one codegen unit (#408, below) did not stop it. Every merge with that build failed both count gates on miss counts of 20 to 700 alone, with instructions within 5% and estimated cycles up at most 0.29%, and needed a hand check and a merge record (32.12): #404 (`exact_sum/add_slice/typical` D1mr 623 → 685, `dual/jacobian_interval/extreme` D1mw 106 → 114), #408 (D1 misses of 21 to 45, +9% to +18%), #420, which changed only manifest lint tables (`exact_sum/add_slice/typical` D1mr 622 → 683, aarch64 D1 misses of 21 to 28 up 10% to 25%), and #421 (`newton/*_4` I1mr +32% to +135%). A gate that fails every merge on counts that follow layout checks nothing, so the kernel owners decided on 2026-10-31, settling 31.7's question, to judge every miss count through estimated cycles. The rule is the same on every leg, x86-64 and aarch64; `geom-bench`'s `callgrind` module applies it, in integers, to the summary files Gungraun writes (`--save-summary`), read through Gungraun's own summary model, and fails the gate if any benchmark the run lists has no complete summary (G18a). The measured runs build `geom-bench` without that judge (`--no-default-features`), so the benchmark binary does not change with the tool that judges it.
- **One codegen unit for the measured builds.** Both trees' measured builds, the benchmark binaries Callgrind runs and the fuel guests, compile every crate as one codegen unit. The workflow sets it for both trees (`CARGO_PROFILE_BENCH_CODEGEN_UNITS=1`, and `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` on the guests' build step), not a profile in the tree, because the merge base has no such profile and a pull request could edit one. Cargo's default for a non-incremental release build is 16 units, and more units "may produce slower code" ([Cargo's profile reference, codegen-units](https://doc.rust-lang.org/cargo/reference/profiles.html#codegen-units)). rustc splits `geom-bench` by module and merges the parts down to 16, so a new benchmark module moves the split. Functions that shared a unit and were inlined can then land apart and become calls, in benchmarks the change never touched. G53's root-isolation benchmarks did exactly that (PR #401): `dual/jacobian_real` rose 9% to 14% in instructions on both legs, while built as one unit, or with G53's `geom-num` under the merge base's `geom-bench`, every `dual` count stayed the same to the instruction. A count that follows the build's split rather than the code is not a regression, and the gate could not tell the two apart. In one unit LLVM sees each crate whole, so what is inlined depends on the code alone; the Rust Performance Book recommends one unit for runtime speed ([Build Configuration, Codegen Units](https://github.com/nnethercote/perf-book/blob/a05dd0f15595e98aef45e5a15072c2a71dbe37ba/src/build-configuration.md)). Gungraun's advice on inlining is about crate boundaries: benchmark from a separate workspace member, as `geom-bench` is ([best_practices.md](https://github.com/gungraun/gungraun/blob/a11cdc156da6134f281302f889c1d25fa44e00da/docs/src/best_practices.md)); it says nothing about codegen units. The limits do not change; only the gate's build takes longer. The counts are those of a one-unit build, which can differ from a default build's: the gate measures a change between two builds made the same way, not absolute cost.
- **What 5% means for the cheapest operations.** Each benchmark runs its operation over a batch of inputs in a loop that loads, `black_box`es and stores each one, so the count includes the loop, which dilutes a regression. Measured in fuel, the loop costs about 27 to 33 per input, so the gate trips when the operation itself rises by about 5.3% for `orient2d`, but by about 46% for interval negation, whose operation costs about 4 per input (G06). Whether the cheapest benchmarks need tighter limits is open (31.7).
- **Not built yet.** `geom-bench` (G06) gates DHAT heap but not logical bytes, golden work counts, reference mode or scenarios, which need the work meter, caches and operations of later pieces. No board piece yet owns the per-benchmark logical-bytes gate (31.7). Benchmarks written before `geom-bench` existed, `geom-math`'s transform benchmark (G03), `geom-run`'s helper benchmark (G04) and `geom-num`'s maths and `ExactSum` timing tests (G05, G25), are wall-clock harnesses under no count gate (31.7).
- **The gate guards itself through review.** The limits are passed by the workflow, not set in the code under test, but a pull request can still edit the workflow and `geom-bench`. The guard is a kernel owner's review of those files, which `.github/CODEOWNERS` assigns to the owners (32.5).
- **As built (G107): the reference runner.** `geom-bench`'s `reference/nightly.sh` runs on the reference machine each night (28.17) and times every benchmark of the catalogue with `geom-bench-guest time <name> <ms> <threads>`: six rounds of 150 ms each, and the median of the last five, after each thread's batch has passed its golden check. That is divan's sample-and-median design in one small program, because divan 0.1.21 writes no machine-readable results and runs in no browser, and the same program must time every engine the same way. At 1 and 8 threads: the numbers layer has no pool, so 8 threads are 8 copies of the benchmark at once, one per thread natively and one per Web Worker in a browser, where the kernel runs serially in one worker (23.4); a benchmark with a pool, such as G451's scenarios, will take the count as its pool size. Natively, the timed build is the Windows one, cross-built in WSL with llvm-mingw and pinned by an affinity mask to the performance cores Windows reports: one core for 1 thread, all eight for 8, as 32.16 asks. The browsers are Chrome (the installed browser) and Playwright's Firefox and WebKit, on a page served with cross-origin isolation, so each timer is as fine as it allows (5 µs in Chrome, 20 µs in the others). Safari itself runs only on macOS and the co-op has no Mac, so WebKit, Safari's engine, stands in for it (31.7). A sampler records how busy the whole machine is each second; a timing taken while it was busier than its own threads explain, by more than 10 points, is marked disturbed. `geom_bench::timings` assembles each night into a text record, `history/<night>-<run>.txt` on the repository's `kernel-timings` branch, and writes `report.md` beside it: each share of 23.1 against the full-scale scenario that will measure it (`scenario/<share>/full`, from G451; "not measured yet" until then), the quiet timings that moved by more than 5% since the night before, how each group scales from 1 to 8 threads and from native to each browser, and the disturbed and failed jobs. No job starts unless it can end by 08:00. The runner reports and never blocks; G452 makes it a gate.
- **A nightly miss.** The change responsible is found by bisection. Spare Construct says a target miss blocks any change that misses it; wall-clock noise rules that out per pull request, so a nightly miss blocks further merges to `main`, except the fix or a revert, until the target is met again. The owner accepted this, with a same-night rerun to confirm a miss before the block starts (owner action G449, 32.42).
- **Toolchain bumps** move every baseline. There are no stored baselines: every run measures the merge base afresh, so a baseline is re-recorded by merging the change that moves it (G06). A pull request that changes only the toolchain builds the merge base with its own pinned toolchain and the change with the new one, so the comparison lists every change the bump causes, reviewed by the kernel owners. Rises over 5% still fail the gate; `geom-bench`'s written procedure then asks for a kernel fix first, or an owner's decision recorded in the decision log before the gate changes (32.12). A benchmark the merge base lacks is listed, never gated, until it merges; one a change removes fails unless `retired.txt` names it.
- **Proven or tested.** Filters and integer variants are proven equal to the exact path by construction (23.2, 23.3). Caches, shortcuts and pools are tested equal in reference mode. Reference mode applies to the whole kernel the rule [09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md) (section 2) sets for fast field evaluators: a fast path is allowed only if it agrees bit for bit with the plain one.
- **CI cost.** The forced chunk sizes and thresholds of 23.4 run on one native and one WebAssembly target only, not on the whole section 21 matrix.

The suite lives in `geom-bench`, its corpora in `geom-test`:

- **Micro benchmarks:** each predicate at each step of 23.2, the wide-integer variants per target, `ExactSum`, hashing, encoding and decoding.
- **Operation benchmarks:** at least one per operation (principle 12), on small, typical and large inputs. Operations on fixed-size inputs, most of the numbers layer, are benchmarked by input class instead, such as typical, degenerate, nearly degenerate, extreme and overflowing; only the wide integers take a size, their limb count (G06). `geom-bench`'s coverage test fails on any public `geom-num` function that is neither benchmarked nor listed, with its reason, in `catalogue::UNMEASURED` (accessors, constants, functions that refuse every input, one-call wrappers). That exemption list is a rule kernel owners accept or reject (31.7).
- **Scenarios,** built from a seed by deterministic generators. The building generator is calibrated against the real 230,000-element model's statistics (elements by category, openings per wall, shared bodies, levels), with a calibration report; anonymised real projects are added later.
  - Spare Construct: every row of 23.1, plus a cold open with and without stored display meshes, a browser worker reload, and a 20-building block.
  - Computational design: 10,000 facade panels changed all at once and 1% at a time; a 1,000-operand union.
  - 2D: a drawing of 1,000,000 entities (open, pick, snap, hatch regeneration, arc-heavy offsets).
  - Point clouds: a 1,000,000,000-point index; snapping on the loaded set.
  - Mechanical and car: a part with 40 filleted edges, a feature-tree rebuild, a network of curvature-continuous blends, an assembly of 10,000 parts.
  - Civil and survey: a 50 km corridor swept at 1 m stations; a terrain from 10 million points with breaklines.
  - Circuit boards and manufacturing: a copper pour around 10,000 pads and vias; clearance checks across 100,000 objects; a 1,000,000-move toolpath's swept volume; a lattice part sliced into 1,000 layers.
  - Free-form and meshes: meshing a lattice field; evaluating a subdivision surface with many extraordinary points; a tetrahedral mesh of a large part; a boolean between two scans of 2,000,000 triangles.

## 23.14 What the kernel never does for speed

- Never makes a result less exact, skips the checker's cheap groups, or decides topology on rounded data to go faster.
- Never lets thread count, core count, timing, memory pressure or cache contents choose an algorithm or change a result or a work count. Input size may choose, because it is the same everywhere.
- Never iterates a hash map, sums floats in a varying order, or uses fast-math, relaxed SIMD or `algebraic_*` operations (section 21).
- Never computes a result on the GPU, and never generates machine code at run time. A JIT needs `unsafe`, which principle 13 forbids, and Fidget's JIT does not run on WebAssembly ([09](../../../kit/notes/G01-evidence/09-freeform-subd-implicit.md) section 2). Display may use the GPU on the kernel's output. Any exception would live outside the kernel, pass reference mode bit for bit, and come through a decision note.
- Never accepts a caller's unchecked promise to skip work, as OpenCascade's Glue option does when it skips face-face intersection on the caller's word ([02](../../../kit/notes/G01-evidence/02-occt-parasolid-acis.md) section 3). A hint is checked, or ignored.
- Never keeps a global cache or a mutable static, and never regenerates a model just to open it.
- Never recurses without bound: traversals and subdivisions use explicit stacks of capped depth.
- Never unwinds to cancel, and never aborts on a large allocation.
- Never ships a fast path that is not shown bit-identical to the plain one: proven for filters and integer variants, tested in reference mode for everything else.
