# G36: Verus proofs of the predicates' exact paths, by twins or inside `verus!`

*Piece G36, Spare Kit geometry kernel. Decision note from a spike. Written 2026-10-25 by Claude Opus 5.5 for the owners. Proposed: an owner accepts it by merging the pull request that carries it.*

## The answer in plain words

The kernel's exact predicates (which way three points turn, which side of a plane a point lies) must never give a wrong answer. Tests check many inputs; a proof checks all of them. Chapter 28.7 proposed proving them with Verus without putting Verus into the code that ships: the generator writes a second copy of each predicate's integer code, a "twin", with the proof notes added, Verus checks the twin, and CI checks that the twin, notes removed, is the shipped code exactly. Nobody had done this before, so the plan was to try it on one predicate first.

It works. The generator now writes orient2d's twin and Verus proves it. For every input on the grid, the exact path never overflows, and it returns exactly the determinant the predicate is defined by. A test confirms the twin's code is the shipped code, token for token. The same method proved orient3d too, in 7 seconds.

**Recommendation: keep the twins.** They need no new dependency in the kernel and no exception to the licence rule. The fallback, writing the code inside Verus's `verus!` macro, is not needed.

## 1. The question

Chapter 28.7 asks for proofs that cover the code that ships, and offers two routes for the predicates:

- **A. Generated twins.** `geom-gen` emits a Verus-annotated twin of each integer path; CI verifies the twin and checks that, annotations removed, it is token for token the shipped code. No precedent was known.
- **B. `verus!` with erased ghost code.** The predicate code is written inside Verus's `verus!` macro, and Verus erases the proof code when the crate is compiled normally. This makes Verus's `vstd` library and macros build dependencies of `geom-num`: a DEPEND inside a kernel crate, which chapter 29.1 allows only for `libm`. It needs an owner's exception to 29.1, a written audit (29.20, rule 3) and a ledger row.

The board's done-when for G36: "The generator emits a Verus-annotated twin of orient2d's integer path; CI verifies it and checks token equality with the shipped code; a written decision between twins and verus! with erased ghost code."

## 2. What the spike built

- **The twin.** `geom-gen`'s new generator `verus-orient2d` writes orient2d's twin from its description (since G38, [`verus/generated/orient2d.rs`](../../engines/geometry/crates/geom-num/verus/generated/orient2d.rs), a module of `geom-num`'s Verus crate). Its `value` is written by the same emitter function (`value_item` in [`predicate_emit.rs`](../../engines/geometry/crates/geom-gen/src/predicate_emit.rs)) that writes the shipped `value` in `geom-num`'s generated `orient2d.rs`; the twin adds only a `#[verus_spec]` attribute and a `proof!` hint before each product. The attribute says: if every coordinate is on the grid, the result is `Some(v)` with `v` equal to the description's value over the mathematical integers. Each hint applies one lemma, that a product of factors bounded by the certificate's bounds is bounded by their product, which Verus's linear arithmetic cannot see alone.
- **The model.** Above `value`, the twin models `geom_num::grid`'s `Coord` (an `i64` its type keeps within ±(2^40 − 1)) and `P2`. The model is the trusted part: it states the invariant `geom-num`'s `Coord` keeps, and `get` returns the value. Its bound is written from `geom_num::grid::COORD_MAX`, and a test checks it.
- **The checks.** `kernel-dev.yml`'s new `verus` job installs a pinned Verus release (checked against its SHA-256) and verifies the twin on every pull request. `geom-gen`'s `tests/verus_twin.rs` tokenizes both committed files (with `proc-macro2`), removes the twin's annotations, and requires the two `value` items to be equal token for token, doc comment and attributes included. It also requires the comparison to fail on a changed operator, a changed name, an added statement, a changed doc comment or a removed attribute, on either side. `cargo run -p geom-gen -- check` keeps the committed twin current.

## 3. Evidence

All runs used Verus `0.2026.10.18.7d82994` (MIT) with the Rust 1.99.1 compiler that release names.

| Run | Result |
| --- | --- |
| orient2d's generated twin | `verification results:: 7 verified, 0 errors` |
| orient3d's twin, generated by the same code to a scratch file | 7 verified, 0 errors, in 7 seconds |
| orient2d's twin with its claim changed to the value plus one | fails: 6 verified, 1 error |
| orient2d's twin with the grid widened to the whole `i64` range | fails: the subtractions can overflow |
| orient2d's twin with the grid widened to 2^62 − 1 | verifies, correctly: (2^63 − 2)^2 · 2 < 2^127, so the path holds well past the grid; the proof is about the arithmetic, not the grid's choice |
| The token comparison, on the committed files | equal; and unequal on each of the five seeded changes, on both sides |

So the proof is not vacuous: a false claim fails, and so does a domain where the code would overflow.

Verus's attribute syntax made the twin simple. Verus documents `#[verus_spec]` for adding specifications to ordinary Rust functions, with proof code erased when Rust builds the code ([exec_attr.md](https://github.com/verus-lang/verus/blob/7d829946231d6413a398f6e4160cdfe951261dad/source/docs/guide/src/exec_attr.md), MIT). The twin is therefore ordinary Rust syntax plus attributes and `proof!` macros, so a Rust tokenizer reads it and the comparison is a token comparison, not a Verus parser.

## 4. Options and recommendation

| Option | Kernel dependency | Owner exception | Drift between proof and code | Cost |
| --- | --- | --- | --- | --- |
| **A. Generated twins (built)** | None: the twin is never compiled by Cargo | No | Ruled out by generation from one emitter function and by the token check | One Verus run per twin in CI (seconds) |
| B. `verus!` with erased ghost code | `vstd` and Verus's macros in `geom-num`'s build | Yes (29.1, 29.20 rule 3, a ledger row) | None: one copy | Every `geom-num` build goes through Verus's macros |
| C. `#[verus_spec]` on the shipped code, behind `cfg_attr` | None in a normal build (the attribute is compiled out) | Probably not, but Verus syntax would sit in kernel sources | None: one copy | Verus would have to check all of `geom-num`, or mark the rest external; a `check-cfg` entry for Verus's configuration name |

**Recommendation: A.** It meets 28.7's rule that proofs cover the code that ships, adds nothing to the kernel's build, and needs no exception. B is no longer needed as a fallback. C is the natural simplification if the twins ever become a burden. It is not needed now, and it would put Verus's syntax into kernel sources.

## 5. Open risks and next steps

- **The model is trusted.** The twin proves `value` correct given the model of `Coord`. That `geom-num`'s `Coord` really keeps |v| ≤ 2^40 − 1 rests on `Coord::new`'s checks and their tests, not on this proof. A Verus model of `geom-num`'s constructor would close it.
- **Only point inputs in `i64` and `i128` are covered.** The twin emitter refuses rounded inputs (`plane_side`: no model of their range check yet) and steps wider than `i128` (`incircle`, `insphere`: no Verus model of `geom-num`'s wide integers). Chapter 28.7's Verus proofs of the wide integers (G37) come first; then their twins follow the same pattern.
- **Verus moves fast.** It publishes releases weekly, and each names its own Rust compiler. The job pins one release and its compiler; updating means changing the four values in `kernel-dev.yml` together and rerunning. A Verus that no longer accepts the twin fails the job, never passes it silently.
- **Verus and Z3 are trusted.** As with any proof tool, a bug in Verus or in the Z3 solver it uses could accept a false proof. The exact-oracle tests of 28.6 stay.
- **Next:** the board's Verus pieces: the wide integers (G37), then the orientation and circle predicates (G38, where orient3d's twin already verifies) and the plane-based and implicit-point predicates (G39).
