# CON-A7-F1-P2: recipe evaluation

CON-A7-F1-P2 (recipe evaluation, [FEATURES.md](../FEATURES.md)) with the parts of CON-A7-F1-P3 (named types and type tables) and CON-A7-F1-P6 (limits on a recipe) that evaluation needs. First half: job 4.4 of the build plan, piece A57 (values, formulas, steps, the cache). Second half: job 5.5, piece A59 (sketches solved at each type's values, named types and the type table, limits). A hosted family cutting its host is job 6.4. What a recipe gives when evaluated is written in [construct-families' FORMAT.md](../crates/construct-families/FORMAT.md), "Evaluation"; the code is `construct_families::evaluate`.

## The questions

A recipe ([the format note](CON-A7-F1-P1-recipe-format.md)) holds parameters, formulas, sketches with constraints, and solid steps. Evaluating it for one type means working out the values, turning each sketch into a profile, and running the steps through the kernel's `Engine` interface, kept per type. Things the format leaves to evaluation had to be decided: how a constrained sketch is solved at a type's values and from where; the order things are worked in; what a void cuts; what the cache is keyed by; what a type table is; and what limits one evaluation keeps.

## Evidence

- The format has no void flag and no "cut everything before" step: its steps are `extrude`, `subtract` (a target and a tool, both earlier steps) and `unite`, the operations the `Engine` trait names. A void is therefore an extrusion that a `subtract` uses as its tool.
- The single-swing door's elevation sketch holds its widths and heights as constraints with formula lengths (`width / 2`, `height`). Its stored points are drawn at 820 by 2040 mm, the default type. Any other width moves points, which only a solve can do.
- construct-solver solves a sketch from its points and radii as drawn by least-change damped Gauss-Newton steps: among all moves that meet the constraints best, the shortest, so geometry nobody constrained stays where it was drawn. It rounds its answer to the grid by its own rule (halves to even) and measures every constraint again after rounding, within the model tolerance, refusing rather than storing loose. Its work is counted in steps against a budget, never in time; it uses no clock, no random start and no hash-map order. It says why a sketch is not solved: over-constrained (with the conflicting constraints), not converged (with the unmet ones), refused at rounding, rank too close to call.
- construct-formulas works out a table of parameters in any order with loops refused and units checked, and reads a single length formula against given values (`evaluate`, `value_of`). It caps one formula (1,000 characters, 32 levels of nesting, 16 conditionals, number sizes) but not how many a recipe has.
- The format's types are a list of `{key, name, values}` with one `{parameter, value}` per value. It had no type table.
- The `Engine` trait takes a profile's corners either way round and any vector; the test engines and solidcore's engine are judged by one suite. A solid is made only from profiles' corners, swept and combined.

## Decision

- **Sketches are solved from where they are stored.** A sketch a step uses is built as the solver's sketch (points, lines, arcs before circles, constraints, each one to one, every constraint length its formula's value in grid steps), its points and radii as stored, and handed to `construct_solver::solve`. The stored geometry is the start because it is the author's intent: the least-change answer from it is the shape nearest what was drawn (the right one of two mirror answers, an unconstrained corner left where it is), and the same start gives the same answer on every machine and every run. The solved points and radii are taken as the solver gives them: already on the grid by its own rounding rule, so nothing here rounds again. An under-constrained sketch evaluates, as drawn where it is free. A sketch the solver refuses is refused with `Reason::NotSolved` and the solver's own error, at the first constraint it names (or curve or point; or the sketch itself), never built from geometry that does not meet its values. No method was added to construct-solver for this: `solve` and `Sketch::with_positions` are enough. Sketches no step uses (the door's plan symbols) are not read.
- **Order.** Values first (each type value checked as construct-params checks it, defaults for the rest, then every formula, refused at the first parameter in recipe order whose own formula fails); then the steps in recipe order, each sketch solved the first time a step uses it. The engine is checked first: it must work on `Q0`, the step construct-params' lengths are in.
- **Heights.** An extrusion runs from the lower of `start` and `end` to the higher, along the plane's normal (`xy` +z, `xz` +y, `yz` +x); equal heights are refused. A corner lies at the plane's offset plus the lower height.
- **What a void cuts.** Exactly the target its `subtract` step names, nothing else. A step a later step uses (a target, a tool, a united part) is that step's input and is not drawn; every other step is one of the family's solids, in recipe order.
- **Named types and the type table.** A recipe's named types are its built-in types in order, then its type table's rows in order. The type table is a new optional member of format 1, `type_table`: `columns` (the parameters each row sets) and `rows` (`key`, `name`, and one stored value per column). It is the way a catalogue of sizes is written: one line per type instead of a list of pairs each. It is additive: optional, written only when present, so every recipe that read before reads the same and keeps its bytes and content id; nothing that validated before is loosened. A row is a type exactly as a built-in type is: one set of keys and of names for both, and it becomes a family type the same way. A schema cannot hold a row's value count to the columns, so the checker does (`ProblemKind::ValueCount`), and evaluation reads a named type's values strictly (`TypeValues::of`): a row with no value for a column, or with more values than columns, or a value not of its parameter's kind and units, is refused naming the type and the parameter (`Place::TypeValue`).
- **The cache key.** The recipe version's content id, then every parameter without a formula in recipe order with the type's value or its default in stored text, then any other value given (which evaluation refuses, so it is never kept). No clock, address or hash order: the same inputs give the same key everywhere. Two types with the same values share their solids (a table row repeating a built-in type is built once); a changed value is a new key and builds only that type. A refusal is not kept. A recipe's named types are evaluated one by one through the cache (`Evaluator::evaluate_types`); one type's refusal does not stop the rest. Evaluations are handed out shared (`Arc`), so the engine stays free to mesh them.
- **Limits are counts, never clocks.** A wall-clock limit would make the same recipe evaluate on a fast machine and be refused on a slow one; a count is reached at the same place everywhere. `evaluate::Limits` holds four, for one evaluation, each counted where the work is about to be done and refused before it is done, with `Reason::LimitReached` naming the limit at the place it was reached:
  - solver steps, all sketches together (default 4,000: twenty sketches at the solver's own default budget of 200); each sketch is solved with what is left as its budget;
  - solid steps, one per step run (default 1,000);
  - formula work, the bytes of formula text worked out (default 256 KiB): each parameter's formula and value as the formula table reads it, and every plane, constraint and extrusion formula; construct-formulas caps one formula, this caps how many;
  - result size, the profile corners handed to the engine, holes included (default 100,000).
  The defaults are far above what the example families use (the door uses under a hundredth of each) and small enough that one evaluation cannot hold a server for long. What an evaluation used is returned with it (`Evaluated::used`), so a caller can see how near it came. The cache is not limited here: it keeps one entry per type a caller asks for, and `Evaluator::forget` drops a recipe version's.
- **Errors** are values: the step being built, the place (type, a type's value, parameter, plane, sketch, sketch item, constraint or step) and a reason with text for a person.
- No method was added to the `Engine` trait and no new engine operation is asked for, so the interim register gains no row.

## What the next jobs need

- Job 6.4 (hosted families): the hosted opening (`hosting.opening`) is not evaluated here. Its sketch goes through the same `resolve` in `src/evaluate/sketch.rs` (solved at the type's values, within the same limits), and the cut belongs to the host's build (construct-regen's kernel builder).
- Job 6.5 (door and window templates): write templates' types as built-in types or a type table; every named type is evaluated by `Evaluator::evaluate_types`. Draw each sketch at the default type: the solve starts there, so a type far from the drawing still lands on the shape nearest it, but a sketch whose mirror answer is nearer for some type must hold its side with a `point_line_distance` side or a constraint that fixes it.
- Job 7.6 (load and reload): an evaluated family is keyed by the recipe's content id and the values read; reloading a changed recipe is a new content id, so every type of it is evaluated again, and `Evaluator::forget` drops the old version's. A recipe that reaches a limit is refused with the limit named, so loading can show it.
- A real engine: `tests/evaluate_suite/mod.rs` is generic over `Engine`; the program that links an engine (the server, under its `kernel` feature) includes it through `#[path]`, as it does construct-regen's kernel suite. That is the wiring job's, since it touches the server.

## Open risks

- The solver finds the answer nearest the drawing, not every answer: a type far enough from the drawing that a mirror answer is nearer would flip that part. The templates' sketches should hold their sides (job 6.5).
- The solver is interim (construct-solver's header names the kernel pieces that replace it); its answers are pinned by its own tests and by the sizes here, which judge any solver behind `solve`.
