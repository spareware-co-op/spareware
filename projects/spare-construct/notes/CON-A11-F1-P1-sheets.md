# CON-A11-F1-P1, P2: Sheets are elements, viewports place views on them and keep their alignment as data

**Status, 2026-11-24:** Decided for the build (piece A74). The crate `construct-sheets` follows it; the stored form is in its [FORMAT.md](../crates/construct-sheets/FORMAT.md). This is the data and commands half: drawing a sheet, title blocks, the page and printing are later jobs.

## The question

A drawing set is made of sheets. Each has a number and a name, a paper size, a few facts a title block prints (who drew it, who checked it, when it was issued, which revision) and views placed on it. Views existed (A56) but nothing could hold one on paper, and nothing kept the way viewports line up across sheets when the model changes.

## The decisions

- **A sheet is an element record of the sheets category, a viewport one of the viewports category, neither with a shape.** As a view is: records are the truth (main's ruling 7), nothing is built from them, and `has_shape` is false for both so regeneration and packages pass them over. Their kinds are in construct-categories' kind table.
- **Paper lengths are `Length`, the kernel's grid step (1/6,400 mm), held in the one stored spelling.** A standard size (ISO 216, A0 to A5, landscape or portrait) is a key and an orientation, with its sides in the code as whole millimetres: they are exact and need no stored length. A custom size is two stored lengths, each from 50 mm to 5 m (the bounds only keep a typo from making a sheet no printer can print and keep every sum far from overflow). 297.5 mm is `length:q0:1904000`. Paper has its own frame: origin the lower left corner, x right, y up (the page and PDF will flip it as they need).
- **A sheet number is text, unique in the document without regard to case, at most 32 characters.** Real numbers are `A101`, `S-02.1`, `E3`: no format is imposed. A refusal names the number. Names are not unique (two sheets may both be "Ground floor plan" in two disciplines).
- **Sheet parameters are the ordinary parameter system.** The standard ones (drawn by, checked by, approved by, issue date, revision, revision date, revision description, discipline) are text parameters of the instance with fixed IDs, bound to the sheets category. The first `sheet.create` of a document writes them into the table in the same step; values are set with `element.param`, which now accepts a sheet (it is the one record without a shape that holds parameter values). A title block reads them with the reader that reads every parameter, so there is nothing sheet-specific to read. The issue date is text (`2026-11-24`) because construct-params has no date kind; the project's own issue date is held the same way. The alternative, parameter commands of the sheet's own, would have needed a second reader for the title block job.
- **A viewport has a view, a centre on the paper, a title flag and two optional alignments; it has no scale and no size.** The feature text gives a viewport no scale of its own, so it takes its view's: nothing is stored twice and a view that changes scale redraws the viewport. Its size is the view's extent over the scale, worked each time ([`Sheets::layout`]), so a stored outline never goes stale when the model changes. The title shows the view's name when on.
- **A view is on one sheet, once.** The feature text does not allow a view on several sheets, so a second placement is refused, naming the sheet it is on. A legend or a schedule that people do put on many sheets is a later rule for those kinds; this one is the safe default and is one function to relax.
- **Position is the viewport's centre.** Centres do not move when an extent changes (a corner would), which is what people expect of a view that grows. Moving a viewport sets the centre exactly, to the grid step. A centre must be on the paper (edges included); an outline may run over the edge (layout reports `on_paper`), because a viewport half off the sheet is a drawing problem to show, not data to forbid, and the feature text does not forbid it.
- **An alignment is data, and the position is worked from it.** A viewport may follow another on the same sheet across the paper and up it, each with an anchor: `min` (left or bottom edge), `centre` or `max` (right or top edge). It follows by the same anchor, so two views of different sizes keep the same left edge, centre or top whatever they become. The alignment is two stored keys, not a position. [`Sheets::layout`] resolves it every time from the views' extents and scales, so when a view's extent changes (a wall is drawn, a crop is set) the aligned viewports move with nothing written. Alignments to itself, to a viewport of another sheet or round a loop are refused (per axis, the two axes being independent). A viewport that is aligned on an axis is not placed by hand there; the alignment is taken away first and the position the viewport had before stays stored. This was chosen over rewriting the follower's stored position on every change of its leader, which would be a write per move, would touch pieces another person may hold claims on, and would be stale the moment a view's extent changed with no command at all.
- **Rounding.** The outline's half width is the extent over twice the scale, rounded up to a whole step, so an outline never holds less than the drawing (at most 156 nm too large per side); everything else is exact integer arithmetic in `i128`. A view with no extent is a point: no outline, no width in an alignment.
- **A view's extent is given to the layout, not stored.** Crop regions and datum extents are later view jobs, so today the server gives a plan the box of the elements it cuts and sees (whole millimetres, the shapes' own boxes) and the other kinds none. `ViewFacts` is the one seam: when a crop exists, the server gives its size and nothing in this crate changes.
- **Commands, through the log.** `sheet.create`, `sheet.set`, `sheet.delete`, `viewport.create`, `viewport.set`, `viewport.align`, `viewport.delete`: one undo step each, claims on every piece written, refusals in the crate's words, a set that changes nothing writes nothing. Deleting a sheet deletes its viewports in one step; a viewport others follow is not deleted; a view that is placed is not deleted (`view.delete` asks). The generic commands do not go behind them. An undo is turned back if it would leave a viewport on a view that is gone, a number taken twice or an alignment to nothing: `undo_rules` rebuilds the document's sheets through the same rules.

## Why

- Centres plus anchored alignments are what the work of laying out a set needs (the same left edge for every plan, centred sections), and keeping them as relations is what lets them survive the model changing under the sheet.
- One reader for parameters means the title block job (8.6) and schedules (7.9) read a sheet's drawn-by exactly as they read a wall's fire rating.
- Nothing about the drawing is stored on the sheet; a sheet is a few facts and relations, so a package or a replay needs nothing else.

## Not decided here

Guide grids and saved positions of the feature text's second part are not built (guide grids need the drawing of a sheet to be useful, and saved positions are what the stored centre already is). Title blocks, revisions and sheet collections are their own parts (A11-F1-P3, A11-F3-P1, A11-F1-P4). Drawing a sheet, the page, the browser package and printing are later jobs. Formulas on sheet parameters are not worked through holders yet: a sheet is not among the elements `holders` walks, so a formula parameter bound to the sheets category is checked when defined and shown when read but a change to its inputs does not re-check sheets. Phases and design options on sheets are not stored yet, as on views.
