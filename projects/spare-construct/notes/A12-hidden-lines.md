# A12: Drawing engine: hidden line removal for plans and sections

**Status, 2026-11-22:** the end state this note's first version chose (the kernel's chapter 18) stands. What the first version did not give is the road from today's code to it, the sources behind it, or what Spare Construct builds meanwhile; this version adds those. Where the two differ, "Where this version differs from the first" says so with the evidence.

## The question

How does Spare Construct turn the 3D model into the 2D line drawing of a plan, section or elevation: which edges are visible, which hidden, which cut by the view plane, and how the result becomes lines with the right pen (cut or projection, by category) at the view's scale? The map's method is to "project edges and occluders and resolve visibility in 2D on a spatial grid, in parallel by tile", cached per element and cleared through the regeneration graph ([ARCHITECTURE.md](../ARCHITECTURE.md), Views and drawings). The piece asks how open tools do it and for a recommended method. The drawing engine (jobs 8.1, 8.2, 9.1 and 9.2 of the build plan) is built from this note.

Sources were read on 22 November 2026. Reading depth is stated for every source: "source" means the code itself at the commit named; "full text" or "abstract only" for papers. "Unverified" marks anything not confirmed in code or on an official page. Nothing was built or run here, so no speed is measured; derived figures say so.

## What the first version decided, and what holds

The first version of this note (commit `5743e9c`) found that the kernel's map had already answered the piece: chapter [18](../../engines/geometry/architecture/18-drawings.md) takes Appel's quantitative invisibility on exact predicates, with depth bands, rules (not tolerances) for coincident and edge-on cases, named line sources and a per-item incremental cache; the build is [G386 to G405](../../engines/geometry/architecture/30-build-order.md). It left four things to Spare Construct: the view range, the graphics rules, the representations each element sends, and the cache in the regeneration graph. All of that holds and is not repeated below except where this note adds to it.

## The known methods

The core choice is how visibility is decided for an edge piece.

| Method | How | Exactness | Cost | Curved faces, silhouettes | Coincident faces, slivers | Line to source |
| --- | --- | --- | --- | --- | --- | --- |
| Object space, exact: split every edge at every crossing, test each piece | Edge against each face that could hide it, in projection ([Appel 1967](https://doi.org/10.1145/800196.806007); [Loutrel 1970](https://doi.org/10.1109/T-C.1970.222898); [Galimberti and Montanari 1969](https://doi.org/10.1145/362912.362921)) | Exact if the arithmetic is | Worst case cubic in the edges when every segment is tested against every face (Wikipedia's summary of the methods before 1984; the papers were not read) | Only the smooth-surface papers treat true silhouettes (below); mesh methods give the tessellation's silhouette, which moves with the tessellation | Assumed absent ("general position"); the Bénard and Hertzmann tutorial says the literature "has largely ignored" them (full text, section 4 and appendix C) | An edge piece carries its edge |
| Quantitative invisibility (QI) | Each point has a count of surfaces in front; the count changes only at events (crossings behind an outline, piercings, cusps), so rays are rarely needed (Appel; tutorial 4.1 and 4.7, full text) | Exact in object space, but one wrong test propagates along the chain, which Blinn (via Wikipedia) calls unstable | Fewer ray tests than testing every piece | As above | The tutorial's QI rules assume non-interpenetrating solids and generic position | Natural: counts live on edges |
| Sweep and output-sensitive algorithms | Plane sweep over projected edges: Ottmann, Widmayer and Wood 1985 (DOI 10.1080/00207168508803482) O((n+k) log² n); Nurmi 1985 (10.1007/BF01935366) O((n+k) log n); Devai 1986, quadratic bound (abstracts and secondary summaries only) | Exact in theory; no robust implementation found | Worst-case bounds in n edges and k crossings; no constants stated anywhere read, and building plans have k far below n² | Not treated | Not treated | Not treated |
| Image space: depth or ID buffer, edge extraction | Render faces to a buffer, find edges by image processing (Saito and Takahashi 1990 and Decaudin 1996, abstracts only; Hertzmann 1999 course notes, partly read), or test sampled line points against an ID buffer ([Northrup and Markosian 2000](https://doi.org/10.1145/340916.340920), full text; Cole and Finkelstein 2009, full text) | Sampled: aliasing; a visible part smaller than a pixel is lost (Northrup, footnote 1) | Interactive on a GPU: 9.6 frames a second for 300,000 triangles with one item buffer, 0.52 at 9x supersampling (Cole and Finkelstein, Table 1, 2009 hardware) | Silhouettes of the tessellation only | Sub-pixel slivers lost; coplanar overlap decided by buffer order | Strongest: the ID buffer gives the source edge directly (Northrup, 5.1) |
| Hybrid: exact feature curves, split at silhouette and intersection crossings, one visibility test per piece (a ray from the piece's middle) | The tutorial's "view graph" (4.3, 4.5); in code: solidcore, csgrs, Krbn, three-edge-projection (all below) | Exact crossings, then one test per piece; the test is only as exact as the arithmetic under it | One test per piece plus the crossings, which a spatial index keeps local | Closed-form silhouettes for quadrics (Krbn); NURBS by Elber and Cohen 1990 (abstract and secondary summaries) or by tracing | Needs rules: see the kernel's 18.6 | Easy: every piece keeps its parent edge |
| Smooth-surface contours | Bénard, Hertzmann and Kass 2014 (10.1145/2558307, full text): a new triangle mesh per view whose contours have the smooth surface's topology; ConTesse 2023 (10.1145/3544778, full text) proves the conditions | Accurate topology on smooth surfaces | Minutes per view (7 to 26 minutes for mesh generation in 2014; mostly under 2 minutes in 2023, one thread) | The only methods that treat silhouettes and cusps correctly | Generic position assumed | Through the smooth surface |

Four points from the sources decide the choice.

1. **Robustness is the hard part, not speed.** The tutorial (full text, section 4 and appendix C) says visibility "can be very sensitive", that a large curve's visibility may rest on a single test, and recommends exact predicates, symbolic tie-breaking and following pointers rather than numerics. Edelsbrunner and Mücke 1990 (full text, partly read) give the tie-break, with the caveat that it picks an arbitrary but consistent answer: which of two coincident faces wins needs an explicit priority rule, which the kernel's 18.6 states.
2. **Plans and elevations on grid axes are the degenerate case.** Every wall face in a plan is exactly edge-on. A method that assumes general position fails there first, and every open code below shows it with tolerances of 1e-4 down to 1e-16 for "edge-on".
3. **Sampling cannot be exact.** Image-space methods and screen-space scans lose thin features by design; they suit previews, not construction drawings.
4. **No source gives a building-scale timing for any method** (searched, none found). The only figures are old (Markosian 1997, a 200 MHz workstation: 65,000 triangles at 30 frames a second, silhouettes only) or anecdotal (below).

## What the kernel side has, and what it plans

- **Code.** `geom-draw` (`projects/engines/geometry/crates/geom-draw/src/lib.rs`) is 31 lines: a header and `#![forbid(unsafe_code)]`, status "scaffold only", for pieces G387, G389 to G405. `engine-draw2d` (`projects/engines/crates/engine-draw2d/src/lib.rs`) is 5 lines: "No code yet". `construct-views` is 6 lines saying it waits on this note. `geom-solidcore` wraps `Modeller::plane_section` (a plane through a point with a normal, returning curve pieces read by parameter) and `Modeller::meet` (where two solids meet), and nothing for projection or hidden lines. So today: no drawing code in the kernel, one cut call, and a header-only 2D engine.
- **Plan.** Chapter 18 specifies `draw(ctx, DrawInput)` with per-view bands, `DrawItem` roles (`Cut`, `NeverCut`, `NoOcclude`), the line classes, `Source` and `LineRef`, and a `reuse` cache; chapter 14.6 specifies hatches. The build order has G386 (corpus and benchmark scenes), G387 (view input), G388 (exact view predicates), G389 (sections of every body kind), G394 (exact hidden lines for plane-based bodies), G395 (bodies that run into each other), G396 (curved), and G397 to G405 (canonical form, classes, checker, references, incremental engine, storage). All are unbuilt as of this note.
- **What solidcore already has, found by reading its source.** solidcore is the Rust port of a commercial B-rep library, under Apache-2.0, pinned by the kernel at commit `1d8e14b46dedccbb03572956e7c708782fef1b8f`. The kernel's 18.1 says its hidden-curve module "was not studied here". It is studied now, at header and API level only (the 2,295-line `hcr.rs` was not read through):
  - `Hcr` takes one B-rep, a view vector or transform, and two tolerances (`approx_tol_3d`, `ang_tol_rad`). `compute_global_visibility` finds silhouette curves on the faces, then for each edge splits it at the projected crossings with silhouettes in front and classifies each interval by one ray from the interval's middle (a fixed parameter, 0.534567) against all the scene's surfaces through a grid and a ray tracer (`compute_curve_visibility`, `is_point_visible`). It exposes `visible_curves()` and `invisible_curves()` as exact curve objects, not polylines.
  - `project_brep_onto_plane` and `create_silhouette_curves` in `api_projection.rs` set it up as the whole B-rep seen from beyond its box, with tolerance the box size times 1e-6 (or a tenth of the B-rep's own tolerance if smaller) and 10 degrees.
  - Its own header states what is missing for us: the copy of edge and face attributes onto the output curves "is not ported: curves carry no attribute list here". So an output curve does not say which element or face it came from. Whether the scene can hold many unjoined bodies (our elements) is unverified; the repository's fixtures include an "extra wire admission" case only.
  - The method is the hybrid of the methods table, float and tolerance based. The kernel's 18.6 rules (count re-tests, coincident rules, piercing events, intersection seams) are not in what was read; whether a body running into another gets its seam drawn is not shown.
  - Determinism: its header records that the original's hash-order traversal was replaced by an explicit order (`silhouette_edges` newest first) because the original's order was not reproducible; the rest is unverified.
  - WebAssembly: solidcore is about a million lines (`geom-solidcore/Cargo.toml`); the kernel keeps it in a separate workspace and CI job. Whether it compiles to wasm32 is unverified. Treat it as server side.
  - The plane section (`planar_section.rs`, `create_planar_section_curves`) returns curves; closed regions are assembled by the caller. It is already wrapped; the exact integer cut for plane-based bodies is G389.

## How the cut is made, and how a cut region is filled

- **The cut.** Kernel 18.4 fixes the rule: the cut region is the closure, within the plane, of the body's interior met with the plane; a body that only touches the plane is not cut; a face in the plane is never a cut. Plane-based bodies (most of a building) are cut exactly by classifying each vertex against the plane and keeping the crossing points implicit. Today's wrapped call returns curves by parameter; for flat solids it is good enough as an oracle for a first cut engine, not as the engine (floating curves, no element or face names).
- **Region and fill.** The cut region's loops become Cut curves keyed by element, body region and material (18.4). Same-material regions of joined elements (a wall layer through a junction) merge by a 2D union that keeps each edge's source: the pattern iOverlay's `EdgeOverlay` gives (kernel evidence 06, section 2); i_overlay and Clipper2 above are the permissive choices, and three-edge-projection merges silhouettes with Clipper2 the same way. The fill is the kernel's 14.6 hatch: line families with whole-number directions, exact crossings with the boundary, an island rule, dashes by arc length, a count before any line is made. It is a specification only today; `engine-draw2d` will draw fill and lines at true weight. A solid fill or a GPU pattern is the fallback on screen; the vector PDF writes the same families. Material patterns on faces seen in elevation (brick courses) are the kernel's 18.8 model surface patterns, anchored by name.
- **Overlap.** Overlapping cut regions of different elements are listed in the diagnostics, and item priority says which draws on top (18.4). This is where walls and the floors they cut into get their drawing order.

## Keeping every line tied to its source

The rule from 18.8: each drawn line keeps `Source { element, entity, what }`, with `what` an edge span, a cut, a contour branch, an intersection or a supplied curve; coincident lines keep all their sources; overrides and dimensions store a `LineRef` (element, source name, class, span), never an index. What others do:

| Tool | How the link is kept | Weakness |
| --- | --- | --- |
| OCCT, TechDraw | Position in the output list | Breaks when the model changes; the kernel's evidence 06 (section 6) notes TechDraw's unimplemented similar-geometry search |
| IfcOpenShell | One run per product, GUID written to the output group | Per product only; occlusion between products needs the pre-filter and a second pass |
| three-edge-projection | `ProjectionEdge.mesh` per edge | Per mesh; to link by element, make one mesh per element |
| csgrs | A handle per segment | Part level |
| Northrup and Markosian | A pointer to the source edge on every stretch | Image-space tolerance of 2 pixels; edges only |
| solidcore `Hcr` | None on output curves | Must be rebuilt by matching, the failure above |

What Construct needs for this: every candidate edge has a name that survives edits. In the kernel that is `NameId` (persistent naming, chapter 20). In the interim engine (below) there is no kernel naming yet, so a name is the element id plus the recipe's face and edge index in its fixed build order, marked weak as the kernel marks unstable branch keys. Whether the geometry seam's `Built` carries face and edge names today is not confirmed here (`construct-model/src/geometry.rs` records a name scheme number per document; the stand-in builds boxes).

## From line to pen

A drawn line has a class (Cut, Outline, Boundary, Intersection, Sharp, Smooth, Sewn, Iso, Axis, Supplied), a visibility (Visible, or Hidden with its count), a band (Overhead, Primary, Beyond) and a source whose element gives its category and subcategory. The pen is a pure lookup in Construct's own data (A8-F3-P1 and P2): (category, subcategory, cut or projection, band, visibility, view scale, phase, overrides) gives a weight, a pattern, a colour and a halftone. Cut means class Cut; projection means every other class; Overhead gives an overhead pattern; Hidden gives a hidden pattern or nothing. The kernel returns exact model-unit curves and never a width: weights are paper millimetres, applied at display and export, because the sheet placement holds the scale as an exact ratio (18.2). Line weights by scale are a table keyed on scale; nothing in the engine changes with scale. The view range supplies the four planes of the bands (top, cut, bottom, depth); whether Construct simplifies the number or kind of planes is the map's open question and a separate small decision piece, as the first version said.

## Speed

Target, from the map: first draw of a plan under 500 ms and under 16 ms after an edit, unmeasured (the kernel's G450 and G451 build scenario generators and Construct target scenarios for it).

What the sources show: no published building-scale figure for any method; OCCT's exact algorithm has user reports of an 8 MB STEP model taking 1.5 hours and overflowing the stack near 20,000 edges (a forum thread, anecdotal, not a benchmark); the Rhino host engine took 1.7 s single-threaded on one 5,000-segment site model (its author's comment); the buffer methods are interactive but sampled.

Derived estimate, not measured: a plan of a building has a few thousand elements; a plan sees only what the view range keeps (the bands drop most elements above the cut or far below); faces seen exactly edge-on hide nothing, so the occluders are the horizontal faces only; candidate edges are of order 10^4, and with a spatial index each is tested against tens of faces, so of order 10^5 to 10^6 exact predicates, which is tenths of a second in a browser if each is a handful of integer multiplies. The two factors this hides are the wide-integer cost on WebAssembly (2 to 7 times native, kernel 23.3) and how many events leave the fast filter.

The method that meets the target is the kernel's: per-element stage 1 cached by content hash, visibility recomputed only for chains whose boxes overlap a changed item's old or new footprint, early cut-off if stage 1 is unchanged, and an incremental result equal to a full one bit for bit (18.9). Others do the same: US patent 4901252 (abstract only) re-checks edges only against changed objects; Bentley's documentation (Cached Visible Edges; documentation only) builds its cache incrementally, and a user note there says a per-reference cache can leave one reference failing to hide another, which is the bug the kernel's rule (recompute chains overlapping the footprint) prevents. In a browser the kernel runs serially in one worker until threaded WebAssembly is stable (kernel 23.4), so there is no per-view parallelism and the cache matters more.

## Decision

**The notes lean to this.**

1. **End state: the kernel's chapter 18, unchanged.** Exact object-space hidden lines on plane-based bodies with Appel's counts and re-tested chains (G394), piercing events and seams (G395), certified curved (G396), pieces keyed and sorted for the same bytes everywhere (G397 to G402). The sources support it: every open implementation read decides visibility with tolerances or samples, and the tutorial and OCCT's tolerances show why that fails on grid-axis drawings.
2. **Meanwhile, Construct builds its own small engine for the flat-faced part, behind the shape of the kernel's `draw`.** Walls, slabs, roofs and openings are plane-based and, in plans and elevations on grid axes, almost all geometry is axis-aligned. That case is decidable exactly with integer arithmetic on millimetre coordinates, and it is the case every tolerance-based code gets wrong. The engine is `construct-hidden` (jobs 8.2 and 9.1), reads solids through the geometry seam, and is written to `DrawInput` and `DrawingCurve` of 18.2 and 18.8, so the kernel's G394 can replace it under the same tests. Curved bodies (circular columns, round walls, pipes) come from solidcore's `Hcr` through `geom-solidcore` once its spike (step 1) answers the open questions, and are listed in the interim register with the pieces that replace them.
3. **Sampling is not used for a result**; a test-only raster sampler of our own may serve as an oracle (kernel 18.11 already allows it).
4. **LGPL and GPL code is studied only.** OCCT, TechDraw, IfcOpenShell, SolveSpace and Blender are read for method and cited; nothing is copied or linked. Any use of OCCT's HLR in tests runs out of process, as kernel 18.11 says.

### Where this version differs from the first

- The first version recommended closing A12 against the kernel's chapter alone. The end state is right, but the chapter is a specification: `geom-draw` is 31 lines of header, `draw` is unbuilt, and the kernel's own build order puts the plane-based hidden lines at G394 behind G388 and G389. Waves 7 to 9 of the build plan need lines before that. So the recommendation gains a second part (item 2 above), which the first version did not give. It does not replace the first.
- The first version said no LGPL or GPL source was read. This version read some, for method only (table above). Kernel 29.20 rule 6, as chapter 18 cites it, requires observations of LGPL source to go in a method note in `geometry/methods/`, checked by a second reviewer, before code is written; this note is not that note. Steps 5 to 7 below must not start from this note's OCCT summary alone: the owed method note is a precondition, or those steps work from the papers and the permissive code only.
- The OCCT tolerances found here (a fraction of the model's size, up to a hundredth, in face tests) agree with the kernel's reading at `53706f7`, and were read again at `4dbfdcc`: the finding holds in the current source.
- The kernel's 18.1 says solidcore's hidden-curve module was not studied; it exists as `Hcr` and is Apache-2.0. That does not change the end state (it is tolerance-based and drops the source link), but it is the only working exact answer for curved bodies the project owns, so the interim engine uses it behind the seam.

## Open risks

- **The kernel's drawing engine is not built.** Steps 5 to 7 duplicate part of G394; if G394 lands first, drop them. Building meanwhile is the owner's decision.
- **Exactness in the interim engine.** The width of the integers needed is derived only for the kernel's general case; see step 6.
- **`Hcr` is untested for our use:** element links, many bodies, speed and wasm32 are unknown until step 1. The fallback is the flat-solid engine for curved bodies drawn as polygons from a mesh, marked Approximate.
- **Study-only summaries are not reviewed.** The OCCT, SolveSpace and Blender summaries need the second reviewer the kernel's rule requires before code leans on them.
- **No building-scale timing exists in any source;** the 500 ms and 16 ms targets are unmeasured and the estimate above is derived.
- **The view range model** is still the map's open question and fixes the planes the engine takes.
- **Truth tests.** Plans and sections compared with another program's output (Gate C, CON-A2-F9-P5) depend on how such output may be exported; not settled here.

## Could not verify

Appel 1967, Sutherland, Sproull and Schumacker 1974, Loutrel 1970, Galimberti and Montanari 1969, Weiler and Atherton 1977, Ottmann, Widmayer and Wood 1985, Nurmi 1985, Devai 1986, Elber and Cohen 1990, Saito and Takahashi 1990 and Hobby 1999: full text not read (publisher blocks or paywalls), so claims about them come from abstracts or secondary summaries and say so. Sutherland et al.'s complexity claims were not confirmed. Some DOIs conflict between indexes (Elber and Cohen, Saito and Takahashi, Galimberti and Montanari). The visibility algorithm of Freestyle (Grabli et al.) was not read. How OCCT maps output edges to sources is not documented in anything found. Whether `Hcr` draws intersection seams, whether it builds for WebAssembly, whether many unjoined bodies work in one scene, and whether three-edge-projection's WebGPU path is deterministic: unverified.
