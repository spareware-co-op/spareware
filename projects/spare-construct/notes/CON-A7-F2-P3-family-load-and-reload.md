# CON-A7-F2-P3: families stored in the document, loaded, reloaded and swapped

CON-A7-F2-P3 (load and reload), [FEATURES.md](../FEATURES.md): job 7.6 of the build plan, piece A73. The code is construct-families' [`stored`](../crates/construct-families/src/stored.rs) (what a document keeps of a family, and what it takes), construct-regen's [`families`](../crates/construct-regen/src/families.rs) (the record, and how a placed copy is built from it) and construct-api's [`cloud::loading`](../crates/construct-api/src/cloud/loading.rs) (the commands). The stored forms are construct-families' FORMAT.md, "A family in a document", and construct-model's FORMAT.md, "A placed family".

## The questions

Where a document's families live, so that a document opens and builds the same on a server without the library it came from; how a placed copy names its family; what a document checks before it takes a recipe; what a reload keeps and what refuses it; how a swap and a generated type fit in; and what becomes of documents written before, whose copies name library recipes by content id only.

## Evidence

- A document's parameter table, types, levels and views are already element records of no shape, listed by kind and read as the log stood when regeneration reached them (construct-model's FORMAT.md). The regenerator rebuilds whatever a changed record is listed as read by (`reads` rows).
- A placed copy (piece A64) names its recipe version by content id, the SHA-256 of the recipe's one written form, so the same id is the same recipe wherever it is read.
- The builders take a recipe and nothing else (`Geometry::build`, `build_hosting`); the recipe a builder is handed is filled from records first (`recipe_at`: parameters, wall, floor and roof types, levels), both for a command's check (`At::Now`) and for regeneration (`At::Regenerated`).
- The evaluator works within limits (solver steps, solid steps, formula bytes, corners) and can work out each solid's box without an engine (`extents`); a wall's builder cuts only upright rectangular openings.
- The generator (piece A70) makes one family recipe from specs, a type table row each, and `verify` checks every type again from its stored rows.

## Decision

- **A family is a record of the document**, kind `family.recipe`, its element id the family's permanent id, holding the recipe in its one written form, its content id and its source (`library:<id>`, `text`, `generated:<template>`). It has no shape and is listed by kind like a type. It is read strictly: a record the writer would not write is refused, so a tampered recipe or content id is found when it is read. One family per permanent id in a document; another version comes in by a reload.
- **A placed copy names its family by permanent id** (`family_id`, the record's element id) beside the version it names by content id. The builder is handed the copy's recipe with the record's recipe text filled in (`recipe`, never stored), checked against the content id, so the builders need no library and no state of their own: the content is in what they are handed, the cache key is the content id as before, and a server without the library builds the same bytes. The copy's `reads` row names the record, so a family's record written again builds its copies and their walls.
- **Documents written before** (copies with no `family_id`) are **resolved from the library as a fallback**, not loaded on first use. Their records are history: rewriting them when they are first read would be a change outside the log, and a read that writes would make a read-only view, a replay or a second server answer differently. Their content id names one exact recipe, so the library's recipe of that id is exactly what they were placed with; a server without it reports `FamilyMissing` by name, as before. A reload or a swap through the log moves such a copy onto the family in the document, as an ordinary undoable entry.
- **New copies always name a family in the document.** `family.place` of a library family the document does not hold loads it in the same entry (its record the first change, so it is regenerated before the copy that reads it), and one undo takes both back.
- **What a document takes** (`loadable`): the written form at most 256 KiB, the reader, the checker against the project's categories and materials, at least one type, and every type it names evaluated within the evaluator's default limits (each solid's box, no engine) with a wall-hosted family's opening cut by the same rule a builder cuts it by. A family that would not build is refused when it is loaded, naming the type, never later at a placed copy.
- **A reload** replaces the record and writes every copy at the new version in one entry, keeping its place, host, type and values. It is refused, naming the copy and changing nothing, when a type a copy is of is gone, a value a copy holds is no longer one a copy may hold, or the copy would no longer cut its wall cleanly (each copy is seated again with every other already at the new version, by the kernel builder's own rules, as a placement is); and when the recipe is of another family, the same version, or another kind (a door family stays a door family, since a copy's kind and category come from it). A family loaded as text is reloaded from text; one loaded from the library may be reloaded from it by name.
- **A swap** changes one copy, or every copy of one type of one family, to a type of the same family or of another of the same kind, at the same place on the same host; the values the other family takes are kept and others dropped (undo brings them back). A copy that would not fit is refused by name.
- **A generated type** is made by the generator from one spec and checked by its `verify` before anything is stored: a new family of the document (source `generated:<template>`), or a row added to a family the generator made from the same template, which must still be as the generator writes it apart from its rows; the addition is then a reload, every copy kept.
- **Every command goes through the one log**, one entry each, so one undo takes back all it wrote. The generic `element.*` commands refuse a family's record, naming the command to use. An undo that would leave a copy without the version of its family it names is refused (`"That can't be undone: F-1 would be left without its family, ..."`). A family still placed is not removed; its copies are named.
- **The server lists** the document's families first (in the order of their ids), with their source and how many copies are placed, then the library's families it does not hold, on the families route the page's family tool reads.

## Owed

- The page: listing the document's families apart from the library's, loading and reloading from it, swapping, and the generator's form; the two-browser test of those; the browser package rebuilt with them.
- Reading a spreadsheet row or a supplier catalogue into generator specs.
- A project's own library (CON-A7-F9) in place of the templates baked in at build time, which then stop being the fallback for old copies only when every document has been reloaded.
