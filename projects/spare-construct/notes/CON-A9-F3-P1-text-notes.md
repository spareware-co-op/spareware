# CON-A9-F3-P1: Text notes are records of a view, styles are records they read, layout is worked and never stored

**Status, 2026-11-24:** Decided for the build (piece A78). The crate `construct-text` follows it; the stored form is in its [FORMAT.md](../crates/construct-text/FORMAT.md). This is the data and commands half: drawing text in a view or on a page, editing it in the page, text on a sheet, dimensions, tags, keynotes and spelling are later jobs.

## The question

A drawing says things in words: "verify on site", a list of general notes, a callout with a leader to the thing it names. The feature text for this part is one line ("multi-line text with styles, lists, fonts and leaders"), so the list of what a note holds is ours to choose. Nothing in a model could hold text in a view.

## The decisions

- **A note is an element record of the text notes category that belongs to one view; a style is a record of the same category.** As sheets and views are: records are the truth (main's ruling 7), nothing is built from them, and `has_shape` is false for both, so regeneration and packages pass them over. Their kinds (`text-note`, `text-style`) are in construct-categories' kind table. The feature text does not give text to a sheet, so a note belongs to a view only; text on a sheet is a later part (a sheet's own annotation layer), and a note's `@text.view` key is the one place that would widen.
- **A note's fields.** The lines of text (one paragraph per line, joined by a line feed in the record), an anchor, a wrap width (absent: no wrapping), an alignment (left, centre, right), a list kind (none, bullet, number), a rotation, the style's ID and its leaders. The feature text names lists, so the list kind is the note's: every line of a list note is an item. It is not per paragraph because a note that is half list and half prose is two notes, and the Revit-like habit this replaces is one text box per block. The feature text has no rotation; we chose one stored angle (construct-params' `Angle`, within one turn either way) because a note along a sloped wall or a rotated view is ordinary drafting, and it costs one key.
- **The anchor is the box's top left corner, in the view's own coordinates, as `Length`.** The same exact number type the views and sheets use (the kernel's grid step, 1/6,400 mm), never a float. Text size is on paper, not in the model: a style's size is the paper height of the font's em, so it does not change with the view's scale. How a page turns the view's coordinates and a paper size into pixels is the page's job.
- **A style is a name, a font by name, a size on paper, bold, italic, underline, a colour and a line spacing.** The font is a name only: no font file and no metrics are stored, since those belong to the machine that draws. Spacing is a whole percentage (50 to 300) of the font's own line height. A style's name is unique in the document without regard to case, as a sheet's number is. Styles do not inherit from one another yet.
- **A note holds only its style's ID.** Changing the style changes every note that reads it, with no note rewritten (a test shows the notes' records byte for byte unchanged). A style that notes read is not deleted: the refusal names how many. An undo that would leave a note on a style that is gone, or a name taken twice, is turned back.
- **Leaders are stored on the note, numbered, in the view's coordinates; they are not tied to an element.** A leader is a list of two to 32 points ending at an arrowhead kind (none, open, filled, dot, slash). The feature text does not bind a leader's end to an element, so none is bound: a leader is where it is drawn, and deleting an element changes no leader. The tag job (8.3), which does follow its element, owns that binding; it will add a reference key, and version 1 records read with none. A leader's number is one past the largest the note has, found by the command from the record, so replaying the log gives the same numbers. The note holds at most 32 leaders.
- **A view that holds notes is not deleted; the refusal names how many.** The rule the sheets already use for a view that is placed is the one followed (`view.delete` refuses and names what to do first). The alternative, a view's delete taking its notes with it, would put many pieces in one step across claims another person may hold, and cannot be asked "are you sure". Deleting a sheet deletes its viewports because a viewport is the sheet's; a note is the view's, and the view is the larger thing.
- **Layout is worked, never stored.** One function, `lay_out`, gives a note's lines (marker, text, block start, indent, width, top) and its box from the record, the style and font metrics. Line breaks are the Unicode line breaking algorithm's, through the `unicode-linebreak` crate (Apache-2.0, pinned), so no break rule is written here. Every width is the metrics' thousandths of the size times the style's size, rounded up to a whole grid step, so a box never holds less than the text; a word wider than the width keeps a line of its own and is not split. A list item's marker hangs at the left and its continuation lines sit under the first line's text. The box's top left corner is the anchor and it runs right and down; its rotation is the drawing's to apply.
- **Font metrics come from the caller (interim).** `engine-text`, which is meant to own font loading, shaping and paragraph layout, has no code yet (its own header says so), and the server has no font files. So `lay_out` is given a `FontMetrics` (the advance of a text in a face and the face's line height, in thousandths of the size, whole numbers) and no table of widths is held here. The tests use a fixed-width stand-in (`FixedWidth`) and say so. When `engine-text` exists, one `FontMetrics` over it replaces whatever a caller supplies and nothing else changes. The server's listing lays notes out only when it is given metrics (`Service::with_font_metrics`); with none the notes are listed with no layout and `laid_out` false, and nothing is guessed.
- **Commands, through the log.** Twelve: `text.style.create`, `.set`, `.delete`; `text.note.create`, `.text`, `.move`, `.style`, `.layout` (width, alignment, list and rotation together, since they are the box's own shape), `.delete`; `text.leader.add`, `.move`, `.remove`. One undo step each, claims on every piece written, refusals in the crate's words, a set that changes nothing writes nothing. The generic element commands do not go behind them. Empty text is refused (a note with nothing to say is a mistake), as is a wrap width that is not above zero, a size that is not above zero or is over 500 mm, a spacing outside 50 to 300 and a leader with fewer than two points.

## Why

- Notes that read a style by ID are what makes "change the text size of every general note" one edit, and what a template of styles needs.
- Keeping layout out of the record means a change of font, of style or of machine never leaves a stored box stale, and the same record gives the same bytes everywhere. The price is that the drawing computes layout; the exact function and its tests are here so it need not decide anything but the metrics.
- Putting the metrics behind a trait means the day a shaping engine exists nothing but one implementation changes, and no test is written against a particular font.

## Not decided here

Text on a sheet; runs inside a line (a bold word in a regular line); styles that inherit; numbering that continues across notes; leaders bound to an element (job 8.3); a note's rotated bounds; where in the page text is drawn and edited (a later lane); a font list for the page to offer (the page and server must supply fonts and metrics together). Phases and design options on notes are not stored yet, as on views.
