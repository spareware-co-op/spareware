# CON-A10-F1-P1: A schedule is a stored query; its rows are worked out, never stored

**Status, 2026-11-24:** Decided for the build (piece A76, the data and commands half of job 7.9). The crate `construct-schedules` follows it; the stored form is in its [FORMAT.md](../crates/construct-schedules/FORMAT.md). Totals, grouping, formula columns and editing values from a schedule are the second half (job 8.8).

## The question

A schedule lists the elements of one category as a table and stays true as the model changes. The feature text (CON-A10-F1-P1) says "live queries over elements with fields, filters, sorting, grouping and totals" and nothing more, so the form of each part is chosen here.

## The decisions

- **A schedule is an element record of the schedules category with no shape**, as a view is: a name, the category it lists, its fields, filters and sorting, and staging. Records are the truth (main's ruling 7). The rows are a pure function of the schedule and the elements ([`rows`](../crates/construct-schedules/src/rows.rs)), run on every read; nothing about them is stored, so there is no cache to keep true and a row appears, changes and leaves exactly as the elements do.
- **Which categories.** Any category of the table that holds model elements or datums, a subcategory included (a schedule of a subcategory lists only its elements; a schedule of its parent lists both). Annotation, view, analytical and import categories are refused by name: nothing there is listed.
- **Four kinds of field**, each with one stored spelling: `name`, `type` (the type's name), `parameter:<id>` (by the definition's permanent ID, so renaming a parameter changes no schedule) and `quantity:<name>`. A category "has" a parameter when its binding gives it (construct-params' `parameters_of`), a quantity when [`QUANTITIES`](../crates/construct-schedules/src/field.rs) gives it to its top-level category. The quantities are the product's own exact read-only rows, by the name they are shown under: a floor's area, perimeter, thickness, volume and mass; a roof's areas, thickness, volume, mass and ridge height; a room's state, area, perimeter and volume. The server reads them from the same code as its parameters view (`Context::view_cut`, with a floor's openings cut out, and a room's measures), and a test in construct-api compares every cell with the product's row, so a quantity cannot drift from what the page shows. Not listed as fields: a roof's pitch (its kind is a slope or an angle by how the roof is set, which one field kind cannot follow) and the per-layer quantities (their number follows the type's layers). Both are in the handover.
- **Values are exact and carry their unit.** A cell is the value in construct-params' stored spelling and the same shown in the document's units. Nothing passes through a float: lengths, areas and volumes are whole grid steps, a slope is a ratio compared by cross-multiplication in 128 bits, a number is a decimal.
- **Filters.** A field, one of eight comparisons (`equals`, `not_equals`, `less`, `less_or_equal`, `greater`, `greater_or_equal`, `contains`, `begins_with`) and a value; all must hold. The value is typed text read as the field's own kind reads it (`0.9 m`, `11 m2`, `oak`), stored in the stored spelling. A number compared with text is refused (the definition's words say the value is not a length); the comparison must suit the kind (`contains` on a length, an order on a choice, are refused). A row with no value for the field (a parameter nobody set, a room that is not enclosed) fails every filter on it, `not_equals` included: nothing can be said of what is not there. `equals` on text is exact; `contains` and `begins_with` ignore case. There is no "is empty" test yet.
- **Sorting.** Fields in order, each ascending or descending. Numbers by exact value. Text by one stated rule: lower-cased with Unicode's own mapping, then the exact text, so `a` sorts before `B` and `a` before `A`. The feature text asks for no natural or locale ordering, so none is used (`D10` sorts before `D2`); adding a locale-aware collation is a later choice and would be one function (`text_order`), and the package for it would be pinned and its licence noted here. A row with no value sorts after every row that has one, in either direction. Rows left level are in element ID order: the order is total, so the same on every machine and run. A sort or filter field need not be one of the schedule's columns.
- **Refusals, by name, with the reason:** a field the category does not have (`Doors have no field quantity:Area.`), a filter comparing a number with text, a comparison that makes no sense for the kind, an unknown category or one with nothing to list, a name already taken (case aside), a field or sort key given twice, an unknown schedule, a category change (a schedule's category never changes: make another).
- **A field that has gone does not break the schedule.** Reading never applies the rules, so an old document always reads; if a parameter is taken off the category later, the schedule still reads, its cell is empty and `Schedule::check` says so in words (the server's list shows it as `problem`). An undo that would write a schedule that no longer stands is turned back, as for views.
- **Six commands through the log, one file.** `schedule.create`, `schedule.rename`, `schedule.fields`, `schedule.filters`, `schedule.sorting` and `schedule.delete`, in construct-api's `cloud::schedules`, in the shape of the view commands: one record written, one undo step, the claim taken, a refusal in the crate's words. Fields, filters and sorting are each set as a whole list (an empty list clears), which is what a table editor sends. A set that changes nothing writes nothing. The generic element commands do not go behind them: `element.create`, `element.set`, `element.move` and `element.delete` of a schedule are refused naming the schedule command, and a schedule has no shape (`has_shape` is false), so the regenerator and a package pass it over.
- **Read-only server view.** `GET .../schedules` lists them and `GET .../schedules/<schedule>` gives one with its rows, as of the stored records at that read, behind the same `model.read` access as the other views.
- **The page shows a schedule as the server gives it (A76, second half).** The project browser has a Schedules group beside the views: each schedule listed, one made from a name and a category (the categories come from `GET .../schedule-categories`), the open one renamed and deleted there, all through the six commands. Opening one shows a table in a dialog: a heading for each field, a row for each element, each value as the server shows it with its unit. The table is read from `GET .../schedules/<schedule>` and read again after every entry of the log for the model (an edit, an undo, a redo, another browser's edit; claims change no row and are skipped), so the page keeps no rows and has no copy of the row logic. The same read carries `offered`, every field the category has with its kind and the comparisons that fit it, so the fields, filters and sorting are edited from what the server offers; each edit sends the whole list through its command, and a refusal is the server's words in the part where it was made. Choosing a row selects that element in the model.
- **Interim: phases.** A schedule's staging is the two phases every project starts with, as for views, in one place (`views::phases`).

## Why

- A table stored with its rows would be wrong after the next edit and would need invalidation; a query is right by construction and costs one pass over the elements, which the server already makes for its parameters view.
- Parameters by definition ID and quantities by name match how the product already names them, so the schedule and the properties panel cannot disagree.
- Exact comparison and a stated text order keep to the rule that nothing here depends on a machine, a locale or a float.

## Not decided here

- Grouping, totals and formula columns (job 8.8), editing a value from a schedule, key schedules and note blocks, the sheet, view and revision lists.
- Drawing a schedule on a sheet.
- A natural or locale ordering of text, and an "is empty" filter.
