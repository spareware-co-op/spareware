# Spare Construct app

The browser app, on the [demo's](../demo/index.html) layout. The server sends the demo's own page unchanged and adds these files, so the ribbon, palettes, view tabs and status bar are the real ones and stay in step with it. Everything the demo shows that isn't connected yet says so, rather than showing sample data.

- [connect.js](connect.js): puts live data into the page: sign-in, hubs, projects, folders, the plan and 3D views, the Wall and Door tools, types and parameters, Share, Bridge, Take in and links.
- [view3d.js](view3d.js): what the 3D view draws: one batched mesh per element type, with elements of the same shape sharing one geometry. The renderer of note A04 replaces this file. [view3d-check.html](view3d-check.html) measures it against one mesh per element.
- [pkg](pkg): the same geometry the server builds with, compiled for the browser. `server/scripts/build-shapes.sh` makes it, from `crates/construct-shapes`.
- `pkg-kernel` (not committed): the geometry kernel's builder over solidcore's engine, compiled for the browser, which the page loads for a document whose edition is the kernel's (`construct.kernel`). `server/scripts/build-shapes-kernel.sh` makes it, from `server/shapes-kernel`; only a server built with its `kernel` feature serves it.
- **Workshop**, the discipline for parts, assemblies and drawings, is the demo's own page ([demo/workshop](../demo/workshop)), which the server serves at `/workshop/`. Its parts are built by the geometry kernel, compiled for the browser (`crates/construct-workshop`, made into `demo/workshop/pkg` by `server/scripts/build-workshop.sh`). Its parts and its assembly are elements of the open model, written through the same edit log as walls and doors (`element.create`, `element.set`, `element.delete`), so a part survives a reload and everyone on the model sees it change. They have no place in the plan, so connect.js finds them by kind (`/api/projects/<project>/models/<model>/kind/workshop.part`) and hands them to the page as `spare.workshop`. The server's stand-in geometry doesn't build them and records so; the page builds them with the kernel.

- **Parameters**: selecting an element shows its category, its type and its parameters with units, as the server reads them (`/api/projects/<project>/models/<model>/parameters/<element>`). An instance value is typed into its field and sent as `element.param` through the same edit log; the server reads the text with its units and turns a wrong unit or kind back with its reason, which the page shows. Types and the parameter table are records with no shape, so the plan leaves them out. The element's type is a list of its category's types in the palette, sent as `element.type`.
- **Types and Project parameters**: two dialogs, opened from the Manage tab or the buttons under an element's parameters. Types lists the types of a category (the selected element's, or one chosen from the server's list of categories) and makes, renames, copies and deletes them and edits their values (`type.create`, `type.rename`, `type.duplicate`, `type.delete`, `type.set`). Project parameters lists every parameter with its kind, who holds its value and the categories it is bound to, defines a parameter and binds it to categories chosen from a checklist (`parameter.define`, `parameter.bind`). The lists come from the server (`/catalog`, `/project-parameters` and `/types` under `/api/projects/<project>/models/<model>/`), values are typed and shown as the server formats them, and a refusal is shown in the server's own words beside what caused it. Nothing is checked in the page. Undo and redo cover each command, as they do any edit.
- **Levels**: a dialog opened from the Manage tab lists the model's levels lowest first, with each name, elevation (as the server formats it), whether it is a storey and how many elements are tied to it (`/api/projects/<project>/models/<model>/levels`), and makes, renames, moves and deletes them (`level.create`, `level.rename`, `level.elevation`, `level.storey`, `level.delete`); a refusal, such as deleting a level elements are tied to, is the server's reason beside the level. Show makes the plan show that level and ties each wall or door drawn there to it. The floor plans in the browser show Level 1 and Level 2, the levels the old drawings' integers name.

- **Walls**: the Wall tool draws a layered wall between two points, straight along x or y, as one `wall.draw` edit. Its options in the properties palette choose the wall type (the model's wall types, listed with their layers at `/api/projects/<project>/models/<model>/wall-types`) and the top (a level, by default the one above the plan's, or a height typed there); the base is the plan's level. Walking from the first point to the second, the exterior is on the right. A model with no wall types gets the server's default ones, sent through the log as `wall.type.create`. A refusal is the server's reason under the options. The plan draws each layer in its material's cut colour and the 3D view in its surface colour (the display's `parts`, on either edition); a material the server doesn't list is drawn in a neutral colour. A door placed on a layered wall is hosted on the side clicked.

An element here is its recipe. The page builds it through the package its document's edition names and draws what comes back, an outline and a mesh, so it doesn't change when the geometry does. A recipe that reads records (a layered wall's layers from its type, a top tied to a level) is filled by the server, at `/api/projects/<project>/models/<model>/filled/<element>`, as its regenerator fills it; the page builds that, fills it again when a type, a parameter or a level changes, and compares it with the server's bodies only from that point of the log on. A browser that can't build a document's edition draws the server's stored shapes and doesn't edit.

The desktop shell and the wgpu viewport come later, on top of `construct-api`.
