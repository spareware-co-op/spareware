# The Spare Construct cloud format, version 1

This is a published format under [EXTENDING.md](../../../../EXTENDING.md), section 3. It sits on top of the kit's [store format](../../../kit/crates/kit-store/FORMAT.md), which holds the keys, rows, log entries and versions every program shares; this page adds what Spare Construct keeps. **We may stop writing an old version. We never stop reading it.** [`src/keys.rs`](src/keys.rs), [`src/rows.rs`](src/rows.rs) and [`src/element.rs`](src/element.rs) are the reader library.

## Inputs and what is derived

An element's record holds its inputs, and the edit log is the truth about those. A shape is never the truth: it is built from the record's recipe, and every row marked *derived* below can be deleted and made again from the log, byte for byte. `spare-server regenerate` does exactly that, and `spare-server verify` rebuilds every shape and compares it.

So derived rows aren't in any log, a log entry's `changes` name input records only, and a package or a replay needs nothing else to reach the same model.

## An element

The kit's `p:<project>/record/<hash>` holds an element, named by the SHA-256 of its row, and `p:<project>/piece/<document>/<element>` points at the current one. A document is a model in a team's WIP folder.

| Field | Meaning |
| --- | --- |
| `id`, `document` | Its permanent ID, and the document it belongs to |
| `kind`, `name`, `props` | What it is |
| `level` | An integer, read for ever as the level it names (below, "Levels"); every record written from this version writes `0`, and an element's level is its tie in `props` |
| `placement` | `{x,y,z}` in whole millimetres, each exactly 6,400 of the geometry kernel's grid steps, the unit every other Construct length is stored in ([note CON-A2-F3-P1](../../notes/CON-A2-F3-P1-stored-units.md)). Outside the recipe, so a move rebuilds nothing and every door of one type shares one body |
| `recipe` | How to build it |
| `references` | What it is hosted on or built against |

A recipe is the kernel's envelope (architecture chapter 24):

| Field | Meaning |
| --- | --- |
| `owner`, `schema` | Who owns the operation, and their schema version |
| `op`, `op_version` | The operation, named for what it makes: `wall.layered`, `wall.straight`, `door.single`, `family.instance`, `block` |
| `args` | Its arguments, sorted by name. Numbers are whole; the stand-in recipes (`op_version` 1) give lengths in whole millimetres, exact multiples of the grid step, and a recipe that needs a finer length gives grid steps under a new `op_version`. A `wall.layered` recipe holds its lengths as stored lengths instead (below, "Walls"). An argument may instead name a parameter, `{"param":"<id>"}`, read the height from the element's base to its top tie, `{"tie":"top"}`, or read the layers of the element's wall type, `{"wall":"type"}` (below) |

A reference (chapter 20) points at part of a shape by persistent name, never by position in a list. A hosted door points at a face of a wall, not at the wall:

| Field | Meaning |
| --- | --- |
| `doc` | `null` for this document, otherwise `{id, version}`: the linked document, and the version the reference was made against |
| `element` | The element holding the part |
| `name`, `kind` | Its persistent name, and what it is, such as `face` |
| `want` | `one`, `allpieces` or `carrier`, for when what it named has been split |
| `signature` | Kept only to suggest a repair. Resolving never guesses from it |

### Hosted elements

A hosted element (a door) sits on a face of its host (a wall), at an offset along that face and up it, and moves with its host: its record is not rewritten when the host moves or lengthens. A `wall.straight` hosts on its two sides, and so does a `wall.layered` that runs along x or y; a layered wall at an angle hosts nothing yet (a door is a box along an axis, and a placed family turns only by quarter turns: below, "Placed families"). The reader is [construct-regen's `hosting`](../construct-regen/src/hosting.rs).

| Where | What |
| --- | --- |
| `references` | One reference of kind `face`, `doc` `null`: `element` the host, `name` the persistent name of the face, one of the host's sides (`exterior` or `interior`) as the document's builder names them, `want` `carrier`, `signature` that face's role |
| `props` `@host.along` | How far along the face from the host's start (`end0`), a stored length (`length:q0:<steps>`) |
| `props` `@host.up` | How far up the face from the host's base, a stored length |
| `level` | The host's, when it was placed |
| `placement` | Where it sat when a command last wrote it. Where it sits is read from its host: the host's placement, plus, in the host's frame, the offset along its axis, the offset up, and across it flush with the face's side (along x the exterior is at y = 0, along y at x = the host's thickness), so a door as thick as its wall fills it. On a layered wall: along its line from its start, the way it runs, and across it flush with that side's finish face, to the nearest millimetre. Offsets are whole millimetres, as every placement is |

A record with one offset and not the other, an offset that is not a stored length, or offsets without exactly one such reference does not read as hosted: it is built as failed (`BadHost`). One whose host is gone is built as failed (`HostMissing`).

A plain opening through a wall (`opening.wall`) is hosted exactly so, and cut through its wall's whole thickness; a floor opening (`opening.floor`) is hosted on its floor by one such reference to the floor's top face and no `@host.*` keys, its outline drawn in the floor's own frame, so it sits where its floor does ([construct-openings' format](../construct-openings/FORMAT.md)).

**An older record.** A `door.single` written before offsets were stored, with a reference of kind `face` (`doc` `null`) and no `@host.*` keys, is hosted by the element that reference names, and sits where its own placement puts it: its place in its host is the difference of the two placements. Its host is built with it, but it stays where it was placed when its host moves. `hosted.move` writes its offsets, and from then on it moves with its host ([note CON-A4-F3-P1](../../notes/CON-A4-F3-P1-hosting.md)).

### Placed families

**A placed family** (recipe `construct/family.instance`, op version 1; job 6.4, [note CON-A7-F3-P2-hosted-families](../../notes/CON-A7-F3-P2-hosted-families.md)): an element made from a family recipe ([construct-families' format](../construct-families/FORMAT.md)), such as a door or a window of the library's templates. It is hosted as a door is ("Hosted elements", above), on a side of a layered wall along x or y. The reader is [construct-regen's `families`](../construct-regen/src/families.rs).

| Where | What |
| --- | --- |
| recipe `family` | The family recipe version, by its content id (`sha256:` and 64 lowercase hexadecimal digits: the SHA-256 of the recipe's one written form) |
| recipe `type` | The key of a type the recipe names, a built-in type or a type table row (`d900x2100`) |
| recipe `value.<key>` | The value this instance holds for a parameter each instance holds (a window's `sill_height`, a door's `swing`), in stored text (`length:q0:5760000`); none is the parameter's default. Flat strings, so the recipe reads no record. A value for a parameter the type holds, or one worked out, is refused when it is set and when evaluated |
| `references`, `props` `@host.along`, `@host.up` | As a hosted element's. `@host.along` runs from the wall's start to the family's insertion point, the middle of its opening; `@host.up` from the wall's base to the family's origin (a door's foot; a window's floor line, its sill above that at the recipe's own sill height) |
| `kind` | What people call it: `door` for a family of the doors category, `window` for windows, `family` for any other |
| `props` `@category` | The family's own category (doors 300, windows 400), written by `family.place`; generic models only where the family names a category the table lacks. What lists and counts by category reads it here (the kind alone would say generic models) |

Derived, never stored: where it sits and how it is turned. It is seated on its wall ([`hosting::seat`](../construct-regen/src/hosting.rs)): its origin on the wall's centre plane (the library's frames are centred on the family's `y = 0`), each coordinate the nearest millimetre, and turned about its z axis by quarter turns so that its `+y`, its front, points out of the side it is hosted on, never mirrored. The builders are handed its recipe with that turn as `turn` (0 to 3 quarter turns, anticlockwise from above). A family hosted on a `wall.straight`, or on a layered wall at an angle, is the build failure `NotAHost`.

On the kernel's edition its solids are its recipe's, evaluated for its type (construct-families' `evaluate_turned`) through the engine, each a `parts` entry of both displays with its material and its step's key as its `function`; it names no face. Its wall cuts its opening (the outline its recipe's `hosting` declares, solved at its type's values) through every layer, on the same path and by the same rules as a box door's, in the same words with `family` in place of `door` (`"family F-1: it crosses the wall's end"`); the opening's faces are named by the family's key as a door's are. An opening whose outline is not an upright rectangle is refused (`OpeningNotRectangle`). The stand-in draws each solid as its box, worked out without an engine, and cuts nothing. A recipe the builder's family source does not hold is the build failure `FamilyMissing`, a type it does not name `FamilyType`, an evaluation it refuses `FamilyRefused` or `OpeningRefused`, each naming the family. Its `reads` row is a hosted element's: a wall moved or its type changed builds it again with its wall, and a change to its own record (its type, or the recipe version it names) builds its wall again.

Its commands (job 7.1, [note CON-A7-F3-P2-hosted-families](../../notes/CON-A7-F3-P2-hosted-families.md)) are `family.place`, `family.retype`, `family.move`, `family.flip`, `family.set` and `family.delete`, in "Commands" below. They go through the one log, take the claim on the element as a door's do, and each is one undo step. A refusal is in words and names the family (`"family F-1: it crosses the wall's end"`, `"Fixed window has no type w1x1; its types are ..."`, `"Width belongs to the type of Fixed window: change its type to change it."`). The page lists the library for its family tool at `/api/projects/<project>/models/<model>/families`: each family with its permanent id, content id, category, types and the values each placed one holds.

Interim: the family source is the library's templates baked in at build time; families stored in the document and loaded there are job 7.6.

### Categories, types and parameter values

Every record a command writes carries its category, and an element of a type names its type, in `props` under keys that start with `@`, which a permanent ID never does. The keys and the type record are [construct-types' format](../construct-types/FORMAT.md); the values are [construct-params' stored text](../construct-params/FORMAT.md).

| `props` key | On | Value |
| --- | --- | --- |
| `@category` | Every record written from this version | The category's ID ([construct-categories](../construct-categories/FORMAT.md)) in decimal. An element's is its kind's: the recipe's `op`, with its `owner` in front when that is not `construct` (`workshop.part`). A type's is its own |
| `@type` | An element of a type | The type's permanent ID. The type is of the element's category |
| a parameter's ID | An element, or a type | Its value of that parameter, in its stored text (`length:q0:5248000`). An element holds only parameters each instance holds; a type only those the type holds |

Any other key is plain text, kept and read as it is, so a record written before this version still reads. An element reads a parameter from its own value, then its type's, then the binding's default ([construct-types' `resolve`](../construct-types/src/resolve.rs)). An element with no type has the instance parameters its category is bound to.

A **type** is a record of kind `type`, written by construct-types; it lists every parameter bound to its category. A document's **parameters** are one record, element ID `parameters`, kind `parameters`, at level 0 and placement `{0,0,0}` with no references, recipe `{"owner":"construct","schema":1,"op":"parameters","op_version":1,"args":{}}`, and one `props` entry, `@parameters`: the project parameter table's stored bytes ([construct-params, "Project parameters"](../construct-params/FORMAT.md)). Neither has a shape: neither is built, and both are listed by kind. The [reader library](../construct-regen/src/parameters.rs) reads both strictly.

A recipe argument `{"param":"<id>"}` is filled, before the shape is built, with the value the element reads for that parameter: a length as whole millimetres, a whole number as it is. Nothing holding a value is the build failure `UnsetParameter`; another kind of value, or an ID that is no parameter's, `BadParameter`. The type and the parameters are read as they stood at that point of the log, so a shape is the same however the log was reached.

### Levels

A level is a record of kind `level` in the levels category, with its elevation and whether it is a storey; elements are tied to a level by its ID with an offset, and a wall's top may be tied to another level. The level record, the tie keys (`@level`, `@level.offset`, `@top.level`, `@top.offset`) and the rule that reads the old integer `level` are [construct-levels' format](../construct-levels/FORMAT.md). In short: a record with a tie is on its tie's level; with none, `0` is on no level and any other integer `n` on the implied level `n` (ID `1`, `m1` below zero; `Level n`; `(n - 1) x 3000 mm`, or `n x 3000 mm` below zero), which has no record until a command changes it.

An element's base sits at its level's elevation plus its offset, worked out by construct-levels' `height_of`. A recipe argument `{"tie":"top"}` is filled, before the shape is built, with the height from the base to the top tie, as whole millimetres for the stand-in recipes; a height that is not, or a tie to a level the model does not have, is the build failure `BadLevel` or `MissingLevel`. Levels are read as they stood at that point of the log, so a shape is the same however the log was reached, and moving a level writes no element: the regenerator builds what is tied to it again ([reader](../construct-regen/src/levels.rs)).

### Walls

A wall is one of two record forms, both of kind `wall` in the walls category ([note CON-A4-F2-P1-wall-shape](../../notes/CON-A4-F2-P1-wall-shape.md)).

**A layered wall** (`wall.layered`, op version 1), as `wall.draw` writes it: drawn as a line between two points, its layers read from its wall type, standing between its ties.

| Where | What |
| --- | --- |
| `level`, `placement` | `0` and `{0,0,0}`: its line is in the model's plan, and its ties are its levels |
| `props` `@type` | Its wall type: a type of the walls category whose `@system.wall` block holds its layers and core ([construct-walls' format](../construct-walls/FORMAT.md)). The document's parameters define `wall.location-line` and `wall.flipped` and bind them to walls; `wall.type.create` writes them when they are missing |
| `props` `@level`, `@level.offset`, `@top.level`, `@top.offset` | Its base tie, when it has one, and its top tie, when its top is tied ("Levels", above) |
| `props` `wall.location-line`, `wall.flipped` | Its own location line and side, when it has its own; else the binding's defaults, the wall centreline and not flipped |
| recipe `start`, `end` | Its reference line, each `[x, y]` as two stored lengths (`length:q0:<steps>`). Walking from `start` to `end`, the exterior is on the right; flipped, on the left |
| recipe `height` | `{"tie":"top"}`, the height from its base to its top tie, or a stored length. A whole number of millimetres also reads |
| recipe `layers` | `{"wall":"type"}` |

Before it is built, `layers` is filled from the wall type ([reader](../construct-regen/src/walls.rs)): from the exterior face to the interior face, each layer's `function` and `material` and its two faces' offsets from the reference line, `exterior` and `interior`, stored lengths positive toward the exterior side, laid out round its location line. A top tie is filled as a stored length. The type, the parameters and the levels are read as they stood at that point of the log, and its `reads` row lists them, so a change to its type's layers or to a level builds it again and writes no wall. Each face is put on the grid once, by one exact integer rule ([`wall_plan`](../construct-regen/src/wall_plan.rs)), so two layers that meet share their face exactly. A layer with no thickness (a membrane) has no solid. On the kernel's edition each layer is a solid of its own, every door's opening cut through every layer; its faces are named `base`, `top`, `exterior`, `interior`, `end0` and `end1` under `construct/wall.layered`, and `face.<k>` between layer `k - 1` and layer `k`; each display lists one `parts` entry per solid. The stand-in builds it as one box of its whole thickness, its corners to the nearest millimetre, its faces named `box.<role>`; its displays list one `parts` entry per layer with a thickness all the same (each the prism on that layer's strip), so a view draws the layers on either edition. A recipe whose layers or line cannot make a wall is the build failure in the plan's words (`ZeroLength`, `TopBelowBase`, `BadLayers`, `NoWallType`, `BadWallType`).

**Joins are derived, never stored** ([note CON-A4-F2-P2](../../notes/CON-A4-F2-P2-wall-joins.md)). Two layered walls meet when one's line comes within the model tolerance (0.01 mm) of the other's (an end on an end, an end on the other's line, or the lines crossing), on the same base level with overlapping heights. Where two walls along the plan's axes meet square at their ends (an L), or one's end lies on the other's line away from its ends (a T), they are joined by layer priority: at an L the strongest layers meet first (on the mitre when equal, the stronger running through otherwise) and the rest wrap the corner on their own side; at a T each layer of the abutting wall stops at the first layer of the through wall, from its near face, as strong or stronger, and the through wall's weaker layers on that side are cut back to let it in. Before it is built, a wall that meets another has its recipe filled with an argument `joins` ([reader](../construct-regen/src/joins.rs), rule in [construct-walls](../construct-walls/src/joins/mod.rs)): `layers`, each layer's pieces in plan (none for a layer with no thickness, two where a T cuts it back), each piece a list of `[x, y]` corners as stored lengths in the wall's own frame, counter-clockwise; `outline`, the whole wall's; `with`, the IDs of the walls it is joined with; and `unjoined`, a sentence for each wall that meets it and is not joined with it (more than two walls at a point, a cross, an angle other than a right angle or off the plan's axes, walls in line, a T that would cut the through wall in two, a joint with no room). A wall that meets none has no `joins`, and one in a stored record is dropped when the recipe is filled: nothing about a join is ever written in a record, and no command writes one. On the kernel's edition each piece is a solid of its own, listed in the body as a layer, every door's opening cut from each piece it reaches, and the display's outline is the joined outline; the stand-in still builds one box. The walls the filling read are listed in the wall's `reads` row (`joins`, below).

**The old box** (`wall.straight`: `length`, `thickness`, `height` in whole millimetres, placed by its corner, its exterior at y = 0 of its frame) reads and builds exactly as before, on both editions: the same bodies, face names and hosting. Nothing rewrites it into a layered wall. The kind is retired for new walls: the page's wall tool and the seed draw with `wall.draw`, so new walls are written only as `wall.layered`. What still reads `wall.straight` is every record written before (an older document's walls and its packages) and an `element.create` of one from an older page or a test, which the server takes as any record it can read.

**What the page reads for walls.** A model's wall types, each with its layers and core as `wall.type.create` takes them and its whole thickness, the materials with the colours a view draws them in (`#rrggbb`, `cut` where the plan cuts them, `surface` seen beyond), and construct-walls' default wall types as `wall.type.create` arguments: `/api/projects/<project>/models/<model>/wall-types`. An element's recipe filled as the regenerator fills it, with `head`, how far the log had got when it was read (`recipe`, or `failed` with the build failure's `code` and `message`): `/api/projects/<project>/models/<model>/filled/<element>`. The page builds a recipe that reads records from this, and compares what it built only with a checkpoint whose `through` is at or past that `head`.

### Floors

**A floor** (kind `floor`, recipe `construct/floor`, op version 1, the floors category), as `floor.create` writes it: drawn from a closed boundary with any number of holes, its layers read from its floor type, its top face standing on its level ([note CON-A4-F4-P1-floor-from-boundary](../../notes/CON-A4-F4-P1-floor-from-boundary.md); the record, the boundary's stored form and the type's `@system.floor` block are in [construct-slabs' format](../construct-slabs/FORMAT.md)).

| Where | What |
| --- | --- |
| `level`, `placement` | `0` and `{0,0,0}`: its boundary is in the model's plan, and its tie is its level |
| `props` `@type` | Its floor type: a type of the floors category whose `@system.floor` block holds its layers from the top face down. A floor type reads no parameter of the document's table, so the floor commands define and bind none |
| `props` `@level`, `@level.offset` | Its tie: its top face at the level's elevation plus the offset, its layers below |
| recipe `boundary` | The stored boundary: the outer loop and the holes, each edge with its permanent ID, which names the floor's side face there. `floor.create` and `floor.boundary` also take a `constraints` list in the boundary (a sketched outline: dimensions, right angles, parallels, fixed points, in construct-slabs' format, each length as typed text `value`), and the stored sketch then holds them |
| recipe `layers` | `{"type":"layers"}` |
| recipe version, `slope`, `edges` | Version 1 for a flat floor; version 2 for one with a slope arrow (`slope`) or slab edges (`edges`), set by `floor.slope` and `floor.edge`, in construct-slabs' format. A sketched outline keeps its constraints in its `boundary`'s sketch |

Before it is built, the recipe is filled from the floor type ([reader](../construct-regen/src/slabs.rs), through [`parameters::recipe_at`](../construct-regen/src/parameters.rs) as a layered wall's is): `loops` (the outer loop anticlockwise, then each hole clockwise, each corner `{"id","at":[x,y]}` in grid steps) and `layers` (each `{"function","material","thickness"}` in grid steps, from the top). Its `reads` row lists the parameters record and its type, and its level as every element's, so a change to its type's layers or a move of its level builds it again and writes no floor. On the kernel's edition each layer with a thickness is a solid of its own, the boundary with its holes extruded; its faces are named `top`, `bottom`, `face.<k>` between layer `k - 1` and layer `k`, and `side.<edge ID>` under `construct/floor`. The stand-in builds the box around its outer loop, its faces named `box.top`, `box.bottom` and `box.side.<edge ID>`. A floor whose type or boundary cannot be read is the build failure `NoFloorType`, `BadFloorType` or `BadBoundary`, in construct-slabs' words. What a floor reads back (area, perimeter, thickness, volume and mass, and each layer's volume and mass) is worked out from its boundary and its type whenever it is read, and never stored.

### Openings and shafts

**A wall opening** (kind `opening`, recipe `construct/opening.wall`), **a floor opening** (kind `opening`, recipe `construct/opening.floor`) and **a shaft** (kind `shaft`, recipe `construct/shaft`), each op version 1 and of the openings category `1600` ([construct-openings' format](../construct-openings/FORMAT.md); [note CON-A4-F3-P2](../../notes/CON-A4-F3-P2-openings-and-shafts.md)). A wall opening and a floor opening are hosted (above); a shaft is not: its base and top are tied to levels (`@level`, `@level.offset`, `@top.level`, `@top.offset`), its recipe's `height` is `{"tie":"top"}`, filled as a stored length, and its `reads` row lists both levels. A floor is built with its openings and with every shaft of its document that passes wholly through its thickness, read by their kind rows each time the floor is built; a shaft built again builds every floor of its document again. On the kernel's edition each is a hole through every layer of its host; their faces are named as a tool's, `tool(<ID>).jamb.start`, `.jamb.end`, `.head`, `.sill` in a wall, `tool(<ID>).side.<i>` in a floor. Each is drawn on its own with no solid: a wall opening as its rectangle in its wall's plane, a floor opening as its outline, a shaft as its outline and a ribbon up to its top; its body is its recipe's canonical JSON and it names no face. A shaft ending inside a floor's thickness is that floor's build failure (`ShaftEndsInFloor`), and is refused where it is made. Their commands are `opening.place`, `opening.draw`, `opening.size`, `opening.move`, `opening.outline`, `opening.delete`, `shaft.create`, `shaft.outline`, `shaft.reach` and `shaft.delete` ("Commands", below); a floor's area, volume and mass, as the page reads them (`/parameters/<floor>`), are those after the cut, by the same code, the outlines that cut it being more holes in its boundary. `/filled/<floor>` also says what cuts it (`cut_by`: `cuts`, each outline's key and corners in grid steps in the floor's frame, and `shafts`, each as the floor's builder is handed it: key, filled recipe and placement), so a page that builds the floor with what cuts it and draws its holes agrees with the server.
### Roofs

**A roof** (kind `roof`, recipe `construct/roof`, op version 1, the roofs category), as `roof.create` writes it: one loop of straight edges as its footprint, what each edge does (its overhang, and its pitch where the roof rises from it), its layers read from its roof type, its base on its level. The form (flat, mono-pitch or gable) is worked out from which edges have a pitch. The stored form of the record, the edges and the filled recipe, and every rule the footprint, pitch and overhangs must keep, are in [construct-roofs' format](../construct-roofs/FORMAT.md); the decisions are in [note CON-A4-F4-P3-simple-roof](../../notes/CON-A4-F4-P3-simple-roof.md).

| Where | What |
| --- | --- |
| `level`, `placement` | `0` and `{0,0,0}`: its footprint is in the model's plan, and its tie is its level |
| `props` `@type` | Its roof type: a type of the roofs category whose `@system.roof` block holds its layers from the outer face down. A roof type reads no parameter of the document's table, so the roof commands define and bind none |
| `props` `@level`, `@level.offset` | Its tie: its base at the level's elevation plus the offset |
| recipe `footprint`, `edges`, `layers` | As construct-roofs' format gives them; `layers` is `{"type":"layers"}`, read from the type when it is built |

Before it is built the recipe is filled from the roof type and its shape worked out ([`roofs`](../construct-regen/src/roofs.rs), through [`parameters::recipe_at`](../construct-regen/src/parameters.rs)). What a roof reads back (area, slope area, thickness, volume and mass, a sloped roof's pitch, a gable's or a hip roof's ridge height, and each layer's volume and mass) is worked out whenever it is read, and never stored. A hip roof, a hip at one end, a rectangle turned off the axes, an L or other right-angled footprint and an uneven gable are solved by construct-roofs (job 6.2); slopes of two pitches meeting at a hip or a valley, a pitch on a footprint that is not right-angled, a verge or two overhangs on a footprint with an inside corner, an overhang on a footprint off the axes and a hole through a roof are refused, in construct-roofs' words naming the edges.

**What the page reads for roofs.** A model's roof types, each with its layers as `roof.type.create` takes them and its whole thickness, and the materials with the colours a view draws them in (`/api/projects/<project>/models/<model>/roof-types`); where it has none the page sends `roof.defaults`.
### Rooms

**A room** (kind `room`, recipe `construct/room`, op version 1, the rooms category): a point on its level, a name and a number, and an upper limit, the level above (its top tie) or a given height ([note CON-A4-F7-P1-rooms](../../notes/CON-A4-F7-P1-rooms.md); the record and its recipe are in [construct-rooms' format](../construct-rooms/FORMAT.md)). Before it is built, its loop is found from the walls of its level as regeneration has reached them ([reader](../construct-regen/src/rooms.rs)), by each wall's finish face toward the room, and its recipe filled with `height` (a stored length) and `loops` (the outer loop anticlockwise, then each hole clockwise, each corner `{"at":[x,y],"wall"}` in grid steps). Its `reads` row lists its levels and the walls its loop runs along; a wall that changes, is made or is deleted builds again every room on the levels it was and is on, and every room that lists it, and a room that changes builds again the other rooms of its levels, so a room follows its walls and its record is never written. On the kernel's edition it is one solid, its loops extruded from its base up to its height, faces `bottom`, `top` and `side.<k>`; the stand-in builds the box around its outer loop. A room whose walls do not close round it is the build failure `NotEnclosed`, and a second room in one loop `Redundant`, naming the first; the record stays. Its area, perimeter and volume are worked out exactly whenever they are read, and never stored. The server reads them back with the room's state: `/filled/<room>` carries `room` (`state`: `enclosed`, `not enclosed`, `redundant` or `refused`; `words`: why there is no area; `area`, `perimeter` and `volume` as text in the document's units, only when enclosed), and `/parameters/<room>` lists `room.state`, and when enclosed `room.area`, `room.perimeter` and `room.volume`, read-only; `/rooms` offers the next free number. Rooms are placed, renamed, renumbered, moved, given another upper limit and deleted by `room.*` commands ("Commands", below).

**Warnings** are not stored: the list of the problems a model holds (a room not enclosed, two walls overlapping along their length) is worked out from the document each time it is read, as a pure function of its walls and rooms ([crate](../construct-warnings/FORMAT.md), [note CON-A2-F7-P1](../../notes/CON-A2-F7-P1-warnings.md)); the server reads it at `/warnings`, read-only.

### Formulas

A parameter's definition may carry a **formula** of other parameters, by name, in [construct-formulas](../construct-formulas/FORMAT.md)' language: the definition's `formula` field in the parameters record, in its one spelling (`Width - 2 * Frame`), and nowhere else. Its value is **derived**: worked out whenever it is read, by construct-formulas' `work_out` over the values the holder reads for its other parameters (its own, its type's, the defaults), in the order they depend on each other ([the reader library](../construct-regen/src/parameters.rs), `Context::worked`). It is never stored as a value, so no record holds a copy that could disagree with its formula, and an input change writes only the input. Its inputs are the element's own record, its type and the parameters record, and a change to any of them builds again every element whose recipe reads a parameter (`reads`, below), so a shape follows its formulas with nothing else kept.

- A formula passes construct-formulas' check over every parameter of the table, and over the parameters bound to each category, which are what it sees on an element: an unknown name, kinds that do not fit, a loop (its members named), and a type parameter's formula that uses an instance's are refused when it is defined, changed or bound.
- A parameter with a formula takes no value from a person and no default. While it has one, a value stored under its ID is not read. Taking the formula away gives each holder (each element of its categories for an instance parameter, each type for a type one) the value the formula last gave it, as its own value, in the same entry; a holder it gave none keeps none.
- Renaming a parameter rewrites every formula that names it, in the same entry, in the one spelling. A name a formula can't use (a space, say) is refused while a formula uses the parameter.
- A result that can't be worked out (a division by zero, a number too large) is the reason where the value is read: the properties panel shows it, a parameter whose formula uses it says it fails (`Width fails: ...`), and a shape that reads it is the build failure `BadParameter` with that reason. The command that would make a formula fail where it worked before is refused with the reason: `element.param`, `element.type`, `type.set`, `parameter.bind`, `parameter.change`. Others (`element.create`, `type.create`, `type.duplicate`, undo and redo) are not refused for it; the failure is shown.
### Grids and reference planes

A grid line is a record of kind `grid`, in the grids category (3700), and a reference plane a record of kind `refplane`, in the reference planes category (3800). Each has a permanent ID, a name (a plane's may be empty), no level and no placement, and its geometry in its recipe as exact stored text. The recipes are `construct` operations `grid.line`, `grid.arc`, `refplane.vertical` and `refplane.horizontal`, schema 1, op version 1. The whole form, and what reading refuses, is [construct-grids' format](../construct-grids/FORMAT.md). They are built by the datum builder in construct-regen: a display of a ribbon and an outline, with no faces.

### Workshop's elements

Workshop, the discipline for things that are made (feature map area CON-A27), keeps its parts and its assembly as elements like any other, changed by the same commands. They sit at level 0 and placement `{0,0,0}`: a part is a definition, like a type, and has no place in the plan of its own.

| Kind | Recipe `op` | `args` |
| --- | --- | --- |
| `workshop.part` | `part` | `params` (each `{name, value, note, kind}`, where `kind` is `length`, the default, `angle` or `count`), `features` (the history, in order, each `{id, type, name, ...}`), `end` (how many features are built; the rest are rolled back), `material` |
| `workshop.assembly` | `assembly` | `instances` (each `{id, part, name, at, grounded}`, where `part` is a `workshop.part` element's ID) and `joints` (each `{id, name, type, a, b, origin, axis, min, max, value, unit}`) |

The recipe's `owner` is `workshop`, schema 1, op version 1. A value is a whole number, or text: a number with a fraction written as its decimal text (`"8.5"`), so no hash depends on how a float prints, a parameter's name, or a formula of parameters with units, such as `"width / 2 - 4 mm"`, in the formula language of [`construct-formulas`](../construct-formulas/src/lib.rs). A formula is stored as written. The element's `name` is the part's name. The stand-in edition doesn't build these, and says so (`UnknownOperation`): the Workshop page builds a part in the browser with the geometry kernel (`construct-workshop`), and the server will too once a document's edition is the kernel's.

## A document

`p:<project>/model/<model>` holds a document's header, including `edition`: `{engine, version, name_scheme}`, what builds its shapes, and, when a geometry engine of the kernel builds them, `report`: the engine's own account of itself, `{engine, version, steps_per_mm, tolerances, answers}` (its name, its version or pinned source, its grid step in steps per millimetre, each tolerance as `{name, value, unit}` with the value as decimal text, and which part answers each operation as `{operation, case, by}`). An edition without an engine, such as the stand-in's, has no `report` key, so editions written before it existed read and compare as they did. Two editions are the same only when every field, the report's included, is the same. A document runs one edition. Moving to another is an ordered operation that reports what changed; a server or browser without that edition doesn't build it, because it would give different bytes under the same recipe. A browser in that position is a viewer of the stored shapes.

`element.*` commands refuse a type or the parameters record, and a grid or a reference plane (and a recipe of theirs): each has its own commands. `element.delete` of a grid says so, naming `grid.delete` (`"<name> is a grid: delete it with grid.delete."`), and of a reference plane, naming `plane.delete`; picking one (`element.claim`, `element.release`) is allowed. Nor do the generic commands go behind the floor commands: `element.create` of a floor (`"A floor is made with floor.create, which checks it as a floor."`), `element.set` of a floor's recipe (`floor.boundary`, `floor.dimension`, `floor.slope` or `floor.edge`), `type.create` of a floors type (`floor.type.create`), and `type.rename`, `type.duplicate` and `type.delete` of a floor type (`floor.type.rename`, `floor.type.duplicate`, `floor.type.delete`) are refused, naming the command to use. Nor do they go behind the room commands: `element.create` of a room (`"A room is placed with room.place, which checks it as a room."`), `element.set` of a room (`"Kitchen is changed with room.rename, room.number, room.move or room.upper, which check it as a room."`), `element.move` of one (`room.move`) and `element.delete` of one (`room.delete`) are refused, naming the command to use; picking one (`element.claim`, `element.release`) is allowed. A room whose walls change is built again by regeneration and has no command for it. In the same way they do not go behind the wall commands: `element.create` of a layered wall (`"A layered wall is drawn with wall.draw, which checks it as a wall."`), `element.set` of a layered wall's recipe or of a recipe that would make one (`wall.draw`), `type.create` of a walls type (`wall.type.create`), and `type.rename`, `type.duplicate` and `type.delete` of a wall type holding its layers (`wall.type.rename`, `wall.type.duplicate`, `wall.type.delete`) are refused; a straight wall and a walls type without layers (only an older document holds one) are the generic commands' as before. They refuse a view too, naming the view command to use: `element.create` of a view (`"A view is made: use view.create."`), `element.set` or `element.move` of one (`"A view is changed: use view.set, view.rename or view.duplicate."`) and `element.delete` of one (`"A view is deleted: use view.delete."`). Nor do they go behind the sheet commands: `element.create` of a sheet or a viewport and `element.set`, `element.move` or `element.delete` of one are refused, naming the command to use; `element.param` does set a sheet's parameter values. ### Undo and redo

An undo is an entry like any other, after everything before it; nothing is ever taken out of the log. Which step it reverses is not in its arguments: it is read from the log, the same way every time, so a server that starts again or a replay of the log on an empty store gives the same answer ([`construct_api::cloud::undo`](../construct-api/src/cloud/undo.rs)).

- **A step** is one applied entry, in that document, by that person, of `element.create`, `element.move`, `element.set`, `element.delete`, `element.param`, `element.type`, the eight parameter and type commands, `hosted.place`, `hosted.move`, the six family commands, the ten opening and shaft commands, the seven level commands, the six wall commands, the nine grid and reference plane commands, the eight floor commands, the fourteen roof commands, the five view commands, the six schedule commands, `edit.undo` or `edit.redo`, with every change it records; an entry other than an undo or a redo is a step only if it changed a record, so the move to where it already is that a click on an element sends is none: a `parameter.bind` that wrote the parameters record and every type of its categories is one step. A run of `element.move` entries of one element by one person, with no other entry of theirs in that document between, is one step (one drag; the drag's `element.claim` starts the next run). Nothing else is a step, and nothing else is undone.
- **The order is each person's own.** Ordinary steps and `edit.redo` go on the person's undo order, `edit.undo` takes the newest off; `edit.undo` goes on their redo order, `edit.redo` takes the newest off, and an ordinary step empties it. Other people's entries change neither. A turned-back entry is no step.
- **What it writes.** For each piece the step changed, from the record before its first change of that piece to the record after its last: a column the step changed goes back to what it was, if it still holds what the step left; every other column keeps what it holds now. The columns are `kind`, `name`, `level`, `placement`, `recipe`, `references` and each `props` key, compared exactly. A piece the step made is deleted, and one it deleted comes back. The undo's own `changes` are these, before and after by content ID, as for any command. A redo is the undo of the undo, so it writes the same way.
- **What turns it back**, whole, with nothing written: another person's live claim on a piece it would write (`"<name> is working on this."`); a column the step changed that someone has changed since, a piece someone deleted since, or a piece the step made that someone has changed since (`"<name> has changed <record's name> since."`); a record it writes that the document's rules can't read, such as an element whose type is gone (`"That can't be undone: "` and the reader's words; when it writes a type or the parameters record, every record of the document is read again; when it writes a grid or a reference plane, every grid and plane is read again and no two grids, or two named planes, may share a name), or that would leave a hosted element without its host (`"That can't be undone: <name> would be left without its host, <host>."`); an element it would leave tied to a level no longer in the model (`"That can't be undone: <name> would be tied to level <id>, which is no longer in this model."`; when it writes or takes away a level, every element of the document is checked); nothing to undo or redo (`"There is nothing of yours to undo in this model."`, and the same for redo).

`document.checkpoint` is written by the server after regenerating. Its arguments are `{"through":n,"bodies":{element:body}}`, and it changes nothing: it is in the log so that every browser watching gets it in order with the edits it covers, and compares the bodies it built itself (note A05).

## Package files

A package is one JSON file in file storage, named by its hash: `{project, document, edition, seq, elements}`, each element as `{element, built, display}`, with the coarsest display inline. Finished shapes travel with it because a host draws a linked document and never regenerates it.
